    Timers, Event Loop y Asincronía en Node.js

    Introducción: El Chef y la Cocina Infinita

    Imagina por un momento que estás gestionando la cocina de un restaurante con una estrella Michelin, pero con una peculiaridad muy específica: solo hay un chef principal.

    En un restaurante tradicional (como funcionaban los servidores antiguos tipo Apache/PHP), si entraban 50 pedidos, contratabas a 50 cocineros (hilos/threads). Si un cliente tardaba en decidir, el cocinero se quedaba de brazos cruzados esperando.

    En Node.js, nuestro único chef (el Single Thread) es una máquina de eficiencia absoluta. No espera a nadie. 1. Recibe una comanda (petición). 2. Si es picar cebolla (tarea rápida de CPU), lo hace al instante. 3. Si es hornear un pavo durante 2 horas (tarea de entrada/salida o I/O, como leer una base de datos), no se queda mirando el horno. Mete el pavo, pone un temporizador, y pasa inmediatamente a atender la siguiente mesa.

    Cuando el pavo está listo, el horno avisa ("ding!"), y el chef vuelve a ese plato en cuanto tiene un milisegundo libre. Este sistema de avisos y gestión de tiempos es lo que vamos a dominar hoy: Timers, Asincronía y el famoso Event Loop.

    Como vimos en el tema anterior sobre Módulos Principales, Node.js nos da las herramientas. Hoy aprenderemos cómo el motor que hay debajo las ejecuta sin bloquearse jamás.

    1. Asincronía y modelo de ejecución en Node.js

    Para ser un desarrollador Backend en TypeScript competente, debes tatuarte este concepto en la mente: Bloquear el hilo principal es un crimen.

    Conceptos Clave

    Definición: Programación Síncrona (Blocking)

    Modelo donde cada tarea debe completarse antes de que comience la siguiente. Si una tarea tarda (ej. leer un fichero grande), todo el programa se detiene ("se congela") hasta que termina.

    Definición: Programación Asíncrona (Non-blocking)

    Modelo donde el programa inicia una tarea y continúa ejecutando el resto del código sin esperar. Cuando la tarea termina, se notifica al programa (mediante un callback, promesa o evento) para procesar el resultado.

    Arquitectura Event-Driven

    Node.js no sigue el modelo tradicional de "hilo por petición". Utiliza un modelo guiado por eventos. El servidor consta de un solo hilo que acepta conexiones y delega las operaciones pesadas.

    Ejemplos Prácticos en TypeScript

    Ejemplo 1: El desastre síncrono (Bloqueante)

    import * as fs from 'fs';

console.log('1. Inicio del programa');

try {
  // ⚠️ ESTO ES PELIGROSO EN SERVIDORES WEB
  // El hilo se detiene aquí hasta leer todo el archivo
  const data = fs.readFileSync('archivo_gigante.txt', 'utf-8');
  console.log('2. Archivo leído:', data.slice(0, 20) + '...');
} catch (err) {
  console.error(err);
}

console.log('3. Fin del programa');

// SALIDA:
// 1. Inicio del programa
// 2. Archivo leído...
// 3. Fin del programa

    Ejemplo 2: La elegancia asíncrona (No bloqueante con Callbacks)

    import * as fs from 'fs';

console.log('1. Inicio del programa');

// El chef mete el pavo al horno y sigue trabajando
fs.readFile('archivo_gigante.txt', 'utf-8', (err, data) => {
  if (err) {
    console.error('Error leyendo:', err);
    return;
  }
  // Esto se ejecuta en el futuro, cuando el disco duro termine
  console.log('3. Archivo leído (callback):', data.slice(0, 20) + '...');
});

console.log('2. Fin de las instrucciones principales');

// SALIDA:
// 1. Inicio del programa
// 2. Fin de las instrucciones principales
// 3. Archivo leído (callback)...

    Ejemplo 3: Asincronía moderna con Async/Await

    import * as fs from 'fs/promises';

async function leerArchivo() {
  console.log('1. Inicio de la función');

  try {
    // 'await' pausa solo esta función, no el hilo principal del servidor
    const data = await fs.readFile('archivo_gigante.txt', 'utf-8');
    console.log('3. Archivo leído (await):', data.slice(0, 20) + '...');
  } catch (err) {
    console.error(err);
  }
}

console.log('Inicio Global');
leerArchivo();
console.log('2. Fin Global (el servidor sigue vivo)');

    Comparativas

    Característica Síncrono (Blocking) Asíncrono (Non-blocking)
    Uso de CPU Ineficiente (tiempos muertos esperando I/O) Eficiente (siempre trabajando)
    Escalabilidad Baja (necesita más RAM/Threads para escalar) Muy Alta (miles de conexiones con poca RAM)
    Complejidad Baja (fácil de leer secuencialmente) Media/Alta (requiere gestión de control de flujo)
    Caso de uso Scripts CLI simples, inicialización de apps Servidores Web, APIs, Microservicios

    Arquitectura Single-Threaded y Event-Driven

    Node.js corre en un solo hilo principal (V8 Engine). Esto significa que no puedes hacer dos cosas a la vez en el código JavaScript. Sin embargo, Node.js delega las tareas pesadas (I/O, Red, Criptografía) al sistema operativo o a un pool de hilos internos (libuv), permitiendo el paralelismo real fuera de tu código JS.

    sequenceDiagram
    participant JS as Main Thread (V8)
    participant Libuv as Libuv / OS
    participant DB as Base de Datos

    JS->>Libuv: Petición a Base de Datos (Async)
    Note right of JS: JS sigue ejecutando<br/>otras líneas de código
    Libuv->>DB: Consulta SQL real
    DB-->>Libuv: Resultados
    Libuv-->>JS: Evento: "Datos Listos" (Callback)

    2. Si Node.js es single-thread, ¿cómo es posible que pueda leer 10 archivos "a la vez"? (Pista: Piensa en quién hace realmente el trabajo sucio).
    3. Analiza el Ejemplo 2: ¿Qué pasaría si el archivo tarda 0.0001ms en leerse? ¿Cambiaría el orden de los logs?


    2. El módulo Timers en Node.js

    Los timers en Node.js no son parte del estándar ECMAScript (JavaScript puro), sino que son parte de la API que Node.js (y los navegadores) implementan sobre el lenguaje. Sin embargo, hay diferencias cruciales.

    Conceptos Clave

    Definición: Módulo Timers

    Conjunto de funciones globales que permiten ejecutar código en un momento futuro, ya sea una vez o repetidamente. En Node.js, estas funciones están disponibles globalmente, no necesitas import (aunque existen en node:timers).

    Diferencias con el Navegador

    En el navegador, los timers dependen del objeto window. En Node.js, dependen del objeto global. Además, Node.js implementa funciones específicas como setImmediate que no son estándar en todos los navegadores.

    Ojo al dato: El tiempo no es exacto

    Cuando dices "ejecuta esto en 100ms", le estás diciendo a Node: "ejecuta esto como muy pronto en 100ms". Si el Chef está ocupado picando 50kg de cebolla (CPU bloqueada), tu timer esperará.

    Ejemplos Prácticos en TypeScript

    Ejemplo 1: Uso básico global

    // No necesitamos importar nada para lo básico
console.log('Inicio');

setTimeout(() => {
  console.log('Esto se ejecuta tras 1 segundo (mínimo)');
}, 1000);

console.log('Fin');

    Ejemplo 2: Importando desde node:timers (Buenas prácticas TS)

    A veces, para tipado estricto o testeo, preferimos importar. 

    import { setTimeout } from 'node:timers/promises';

async function esperar() {
  console.log('Esperando...');
  // Esta versión devuelve una Promesa, ideal para async/await
  await setTimeout(2000); 
  console.log('¡Han pasado 2 segundos!');
}

esperar();

    Ejemplo 3: Cancelación de Timers

    const bomba: NodeJS.Timeout = setTimeout(() => {
  console.log('¡BOOM!');
}, 3000);

// Decidimos cortar el cable rojo a los 1.5s
setTimeout(() => {
  clearTimeout(bomba);
  console.log('Bomba desactivada.');
}, 1500);

    Tabla: Navegador vs Node.js

    Característica Navegador (Chrome/Firefox) Node.js
    Objeto Raíz window.setTimeout global.setTimeout
    Valor de retorno Un número entero (ID) Un objeto Timeout complejo
    Precisión Limitada por la tasa de refresco (aprox 4ms min) Depende del ciclo del sistema, muy precisa
    setImmediate() No estándar (solo IE/Edge antiguos) Nativo y fundamental

    2. ¿Por qué el tipo de dato de retorno de setTimeout en TypeScript para Node es NodeJS.Timeout y no number?
    3. Investiga qué sucede si pones un setTimeout con tiempo 0.


    3. Timers fundamentales

    Vamos a diseccionar las tres herramientas principales para controlar el tiempo.

    setTimeout(callback, delay)

    Ejecuta una función una sola vez tras un retraso mínimo.

    setInterval(callback, delay)

    Ejecuta una función repetidamente con un intervalo de tiempo entre ejecuciones.

    setImmediate(callback)

    Esta es exclusiva y especial. Se ejecuta al final del ciclo actual del Event Loop, justo después de las operaciones I/O y antes de los timers.

    Diagrama de Flujo de Timers

    graph TD
    A[Inicio Script] --> B{¿Hay código síncrono?}
    B -- Sí --> C[Ejecutar Call Stack]
    B -- No --> D[Event Loop]

    D --> E{Fase Check?}
    E -- Sí --> F[Ejecutar setImmediate]

    D --> G{Fase Timers?}
    G -- Sí --> H[¿Pasó el tiempo?]
    H -- Sí --> I[Ejecutar setTimeout/Interval]

    Ejemplos Prácticos en TypeScript

    setTimeout() y clearTimeout()

    Ejecuta una función una vez, tras un retraso mínimo.

    Ejemplo 1: Cancelación de un timer 

    const bomba: NodeJS.Timeout = setTimeout(() => {
    console.log('💥 BOOM!');
}, 3000);

// Decidimos cortar el cable rojo a los 2 segundos
setTimeout(() => {
    clearTimeout(bomba);
    console.log('😅 Bomba desactivada');
}, 2000);

    setInterval() y clearInterval()

    Ejecuta una función repetidamente cada X milisegundos.

    Ejemplo 2: Polling simulado 

    let intentos: number = 0;

const intervalo: NodeJS.Timer = setInterval(() => {
    intentos++;
    console.log(`Verificando base de datos... Intento ${intentos}`);

    if (intentos === 5) {
        console.log('🛑 Parando verificación.');
        clearInterval(intervalo);
    }
}, 1000);

    setImmediate() vs clearImmediate()

    Este es exclusivo de Node.js (no estándar en navegadores). Se ejecuta después de la fase actual de I/O del Event Loop. A menudo se confunde con setTimeout(..., 0).

    Ejemplo 3: setImmediate 

    console.log('Inicio');

setImmediate(() => {
    console.log('Ejecutado en la fase "Check" del Event Loop');
});

console.log('Fin');
// Salida: Inicio -> Fin -> Ejecutado...

    Ejemplo 4: La carrera (Timeout vs Immediate)

    Este es un clásico de entrevista técnica. 

    import * as fs from 'fs';

// Caso A: Ejecución en el módulo principal (Resultado NO determinista)
setTimeout(() => console.log('Timeout'), 0);
setImmediate(() => console.log('Immediate'));

// Caso B: Ejecución dentro de un ciclo I/O (Resultado DETERMINISTA)
fs.readFile(__filename, () => {
    console.log('--- Dentro de I/O ---');
    setTimeout(() => console.log('Timeout (I/O)'), 0);
    setImmediate(() => console.log('Immediate (I/O)'));
});

// En el Caso B, 'setImmediate' SIEMPRE gana. ¿Por qué?
// Porque fs.readFile termina en la fase de Poll. 
// La siguiente fase del Event Loop es Check (donde vive setImmediate).
// Los Timers están al principio, así que tiene que dar toda la vuelta.

    Ejemplo 5: Pasando argumentos a los timers

    function saludar(nombre: string, rol: string): void {
  console.log(`Hola ${nombre}, eres ${rol}`);
}

// Los argumentos extra se pasan a la función callback
setTimeout(saludar, 1000, 'Ana', 'Admin');

    Comparativa: setTimeout vs setImmediate vs setInterval

    Característica setTimeout(fn, 0) setImmediate(fn) setInterval(fn, ms)
    Definición Ejecutar una vez "lo antes posible" (mínimo real 1ms). Ejecutar una vez en la siguiente fase de chequeo. Ejecutar repetidamente e infinitamente cada X ms.
    Fase del Event Loop Fase Timers. Fase Check. Fase Timers.
    Orden de Ejecución Impredecible al inicio del script (depende de CPU). Siempre después de los callbacks de I/O (Poll). Igual que setTimeout, pero se reagenda al terminar.
    Uso Ideal Posponer una tarea para que no bloquee el flujo actual. Ejecutar algo inmediatamente después de leer un archivo o red. Tareas periódicas: limpieza de caché, heartbeats, polling.


    Cuidado con setInterval(fn, 0)

    Técnicamente puedes hacer un setInterval con tiempo 0. Esto intentará ejecutar la función repetidamente "lo más rápido posible".

    A diferencia de un while(true), esto no bloquea el Event Loop completamente (deja respirar mínimamente entre ejecuciones), pero consumirá el 100% de un núcleo de tu CPU intentando ejecutar el callback miles de veces por segundo. ¡Úsalo con precaución!

    Reflexiona

    1. ¿Por qué es peligroso usar setInterval para tareas que tardan más que el propio intervalo? (Ej: intervalo de 1s, tarea de 3s).
    2. ¿Qué sucedería si ejecutas el Ejemplo 1 pero olvidas el clearInterval? ¿Tu programa de Node terminaría alguna vez?
    3. En el Ejemplo 2, intenta predecir la salida antes de ejecutarlo.


    4. Timers avanzados y control del Event Loop

    En Node.js, los timers devuelven un objeto, no un ID numérico. Este objeto nos da poder sobre el comportamiento del proceso de Node.js.

    Conceptos Clave

    Tip Profesional: ref() y unref()

    Por defecto, un timer activo mantiene vivo el proceso de Node.js. Si tienes un setInterval corriendo, el programa nunca termina. * unref(): Dice a Node "Si este timer es lo único que queda activo, no esperes por él, cierra el programa". * ref(): Vuelve a dar importancia al timer.

    Ejemplos Prácticos en TypeScript

    Ejemplo 1: El proceso que no termina (Comportamiento por defecto)

    // Este programa NUNCA terminará automáticamente
const keepAlive = setInterval(() => {
  console.log('Sigo vivo...');
}, 2000);

// Tienes que matarlo con Ctrl+C

    5. Introducción al Event Loop

    El Event Loop es el corazón de Node.js. Es lo que permite que Node realice operaciones no bloqueantes (como leer archivos o redes) a pesar de que JavaScript es single-threaded.

    Conceptos Clave

    Metáfora: El Tío Vivo (Carousel)

    Imagina un Tío Vivo que gira infinitamente. En cada vuelta, pasa por diferentes "estaciones".
    1. Estación de Timers.
    2. Estación de I/O (ficheros, red).
    3. Estación de Chequeo inmediato.
    4. Estación de Cierre.
    Si hay gente esperando en una estación, el Tío Vivo para, los sube (ejecuta sus callbacks) y sigue girando.

    Node descarga operaciones al kernel del sistema (multihilo) siempre que es posible. Cuando el sistema termina, "avisa" al Event Loop.

    Mito del Single-Thread

    Se dice que Node es single-thread.
    * Verdad: Tu código JS corre en un hilo.
    * Verdad: El Event Loop corre en ese mismo hilo.
    * Matiz: Las operaciones pesadas (leer disco, desencriptar) ocurren en hilos C++ de fondo (libuv Worker Pool).

    graph TD
    A[Tu Código JS] -->|Llama API Asíncrona| B(Node.js Bindings)
    B -->|Delega| C{Libuv / Event Loop}
    C -->|Tareas Ligeras| D[OS Kernel - Net/IO]
    C -->|Tareas Pesadas| E[Thread Pool - FS/Crypto]
    D -->|Callback| F[Cola de Eventos]
    E -->|Callback| F
    F -->|Event Loop ejecuta| A

    Definición: Event Loop

    Es el mecanismo que orquesta la ejecución de código síncrono y asíncrono. Monitorea la pila de llamadas (Call Stack) y la cola de tareas (Callback Queue). Si la pila está vacía, mueve tareas de la cola a la pila.

    Diagrama General

    flowchart TD
    Start((Inicio)) --> Sync[Código Síncrono]
    Sync --> Loop{¿Hay tareas pendientes?}
    Loop -- No --> End((Salir))
    Loop -- Sí --> Phases[Ejecutar Fases del Event Loop]
    Phases --> Loop

    Ejemplos Prácticos en TypeScript

    6. Event Loop en detalle y Libuv

    Aquí es donde separamos a los aficionados de los profesionales. Vamos a ver las fases reales. Node.js usa una librería C llamada libuv para gestionar esto.

    Fases del Event Loop

    1. Timers: Ejecuta callbacks de setTimeout y setInterval.
    2. Pending Callbacks: Ejecuta callbacks de I/O diferidos.
    3. Idle, Prepare: Uso interno.
    4. Poll (Encuesta): Recupera nuevos eventos I/O; ejecuta I/O callbacks. Aquí es donde Node suele "dormir" esperando peticiones.
    5. Check: Ejecuta setImmediate.
    6. Close Callbacks: Cierre de sockets, socket.on('close', ...).

    Libuv tiene un "Pool de Hilos" (por defecto 4) para tareas que el Kernel no puede hacer asíncronamente (como compresión o fs complejos).

        console.log(`Hash ${i+1}:`, Date.now() - start, 'ms');

}
// Si ejecutas esto, verás que terminan casi a la vez.
// Si pides 6 hashes, 4 terminan a la vez y 2 tardan el doble.

    7. Microtasks y prioridad de ejecución

    No todo es el Event Loop. Existe una "cola VIP" que se cuela constantemente.

    Conceptos Clave

    1. Macrotasks: Timers, I/O callbacks, setImmediate. Se ejecutan uno por fase.
    2. Microtasks: process.nextTick, Promise.then. Se ejecutan inmediatamente después de la operación actual y antes de pasar a la siguiente fase del Event Loop.

    Peligro: process.nextTick()

    Tiene el nombre más confuso de Node.js. No es "en el próximo tick". Es "AHORA MISMO, antes que nada". Si llenas recursivamente process.nextTick, el Event Loop nunca avanzará y bloquearás I/O.

    Ejemplos Prácticos en TypeScript

    Ejemplo 1: Jerarquía de Ejecución

    Este ejemplo es oro puro para entender Node.js. 

    console.log('1. Inicio');

setTimeout(() => console.log('5. Timeout (Macrotask)'), 0);
setImmediate(() => console.log('6. Immediate (Macrotask)'));

Promise.resolve().then(() => {
    console.log('3. Promise (Microtask)');
});

process.nextTick(() => {
    console.log('2. nextTick (Microtask Prioritaria)');
    // Incluso una microtask dentro de una microtask se cuela
    process.nextTick(() => console.log('2.5. nextTick interior'));
});

console.log('1.5. Fin Síncrono');

// ORDEN: 
// Síncronos (1, 1.5) -> nextTick (2, 2.5) -> Promises (3) -> Macrotasks (5 o 6)

    Ejemplo 2: Promise starvation (Bloqueo por microtasks)

    let count = 0;

function microtaskLoop() {
  count++;
  if(count < 1000) {
    // Esto se ejecutará 1000 veces ANTES de cualquier timer
    Promise.resolve().then(microtaskLoop);
  }
}

setTimeout(() => console.log('TIMER (por fin)'), 0);
microtaskLoop();
console.log('Fin sync');

    Ejemplo 3: Uso correcto de nextTick

    Se usa para emitir eventos antes de que el usuario pueda escucharlos, garantizando asincronía técnica. 

    import { EventEmitter } from 'events';

class MiEmisor extends EventEmitter {
  constructor() {
    super();
    // Si emitimos aquí directo, el usuario aún no ha hecho .on('init')
    // this.emit('init'); <--- Error, nadie escucha aún

    // Solución: Diferirlo mínimamente
    process.nextTick(() => {
      this.emit('init');
    });
  }
}

const emisor = new MiEmisor();
emisor.on('init', () => console.log('¡Inicializado!'));

    8. Bloqueo del Event Loop y paralelismo

    Node es rápido manejando 10,000 peticiones ligeras, pero terrible manejando 1 petición pesada de cálculo.

    Conceptos Clave

    • I/O Bound: Tareas limitadas por red/disco (Node es REY aquí).
    • CPU Bound: Tareas limitadas por procesador (Cálculo matemático, procesamiento de imagen).

    Si ejecutas una tarea CPU Bound en el hilo principal, bloqueas el Tío Vivo.

    Ejemplos Prácticos en TypeScript

    Ejemplo 1: El JSON de la muerte (Bloqueo)

    JSON.parse y JSON.stringify son síncronos. 

    import * as http from 'http';

const server = http.createServer((req, res) => {
  if (req.url === '/block') {
    // Simulamos objeto gigante
    const hugeObj = Array(1e6).fill({ data: 'test' });

    // ESTO BLOQUEA TODO EL SERVIDOR durante milisegundos o segundos
    const json = JSON.stringify(hugeObj); 
    res.end('Bloqueo terminado');
  } else {
    // Esta petición simple será lenta si alguien llama a /block
    res.end('Hola mundo');
  }
});

server.listen(3000);

    Ejemplo 2: Solución con setImmediate (Partitioning)

    Dividir una tarea grande en trozos pequeños. 

    function sumaGigante(n: number, acc: number = 0) {
  if (n === 0) {
    console.log('Total:', acc);
    return;
  }

  // Hacemos 1000 sumas y dejamos respirar al Event Loop
  // Si no hacemos esto, un n muy grande bloquearía
  if (n % 1000 === 0) {
    setImmediate(() => sumaGigante(n - 1, acc + n));
  } else {
    sumaGigante(n - 1, acc + n);
  }
}

sumaGigante(1000000); // No bloquea I/O

    Ejemplo 3: Solución real con Worker Threads

    Para CPU intensiva, usa hilos reales. 

    import { Worker, isMainThread, parentPort, workerData } from 'worker_threads';

if (isMainThread) {
  console.log('Soy el Hilo Principal. Delegando trabajo...');
  const worker = new Worker(__filename, { workerData: 10 });

  worker.on('message', (msg) => console.log('Resultado del Worker:', msg));

} else {
  // Esto corre en OTRO hilo real
  const n = workerData;
  const fib = (num: number): number => num <= 1 ? num : fib(num-1) + fib(num-2);

  parentPort?.postMessage(fib(40)); // Cálculo pesado
}

    Offloading (Workers) Mover a Worker Threads Criptografía custom, IA, compresión pesada.
    Offloading (Externo) Mover a otro servicio (Microservicio) Conversión de vídeo, generación PDF.

    Partitioning

    Otra estrategia para no bloquear es el "partitioning": dividir una tarea grande en trozos pequeños usando setImmediate, dejando respirar al Event Loop entre trozo y trozo.

    9. Manejo avanzado de asincronía

    Hemos pasado de los "Callback Hell" a un futuro brillante con Async/Await.

    Patrones de Evolución

    1. Callback Hell (El pasado oscuro)

    Anidación infinita, difícil manejo de errores.

    2. Promises (El presente estándar)

    Objetos que representan un valor futuro. Encadenables .then().

    3. Async/Await (Syntactic Sugar)

    Hace que el código asíncrono parezca síncrono. Es lo que debes usar por defecto.

    Diagrama de Estados de una Promesa

    stateDiagram-v2
    [*] --> Pending
    Pending --> Fulfilled: resolve(valor)
    Pending --> Rejected: reject(error)
    Fulfilled --> [*]
    Rejected --> [*]

    Ejemplos Prácticos en TypeScript

    Ejemplo 1: Promise.all (Paralelismo)

    Ejecutar tareas independientes a la vez. 

    async function cargarDashboard() {
  console.time('Carga');

  // Se lanzan las 3 a la vez
  const [users, posts, config] = await Promise.all([
    fetch('/api/users'), // Tarda 2s
    fetch('/api/posts'), // Tarda 1s
    fetch('/api/config') // Tarda 0.5s
  ]);

  // Tarda el máximo de las 3 (2s), no la suma (3.5s)
  console.timeEnd('Carga');
}

    Ejemplo 2: Promise.race (Timeout manual)

    Si una API tarda mucho, la cancelamos. 

    const tareaLenta = new Promise(r => setTimeout(r, 5000, 'Datos'));
const timeout = new Promise((_, reject) => setTimeout(reject, 1000, 'Tiempo agotado'));

async function pedirDatos() {
  try {
    const res = await Promise.race([tareaLenta, timeout]);
    console.log(res);
  } catch (e) {
    console.error('Error:', e); // Saltará esto al segundo
  }
}

    Ideal para procesar flujos de datos asíncronos en serie.

    console.log('Recibido trozo de:', chunk.length);

  }

    10. Flujos asíncronos reales y buenas prácticas

    Para terminar, ¿cómo se aplica esto en el mundo real?

    Conceptos Clave

    • Streams: Manejo de datos que fluyen (como agua en una tubería). No esperas a tener todo el archivo en RAM.
    • Backpressure: Si la tubería se llena (el disco escribe más lento de lo que la red descarga), el sistema debe pausar la lectura. Node lo hace automático con pipe.

    Ejemplos Prácticos en TypeScript

    Ejemplo 1: Tuberías (Piping)

    La forma más eficiente de servir un archivo en un servidor. 

    import * as http from 'http';
import * as fs from 'fs';

const server = http.createServer((req, res) => {
  // MAL: fs.readFileSync (Carga todo en RAM)
  // BIEN: Stream
  const stream = fs.createReadStream('video_hd.mp4');

  // Conecta el disco a la red. 
  // Gestiona backpressure automáticamente.
  res.writeHead(200, { 'Content-Type': 'video/mp4' });
  stream.pipe(res);
});

    Ejemplo 2: Event Emitters personalizados

    Node está basado en eventos. Crea los tuyos.

      this.emit('comprado', { usuario, fecha: new Date() });
    }, 500);
  }
}

    Reglas de Oro para Backend Escalable

    1. Nunca bloquees el Event Loop: Cuidado con JSON.parse de objetos gigantes o bucles sincrónicos largos.
    2. Gestiona siempre los errores: Una promesa rechazada no capturada puede tumbar el proceso Node.js.
    3. Usa Streams: Para todo lo que sea mover datos de un lado a otro.
