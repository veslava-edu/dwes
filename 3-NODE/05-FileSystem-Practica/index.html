    Práctica 5: Sentinel FS – Auditoría Forense de Archivos

    1. Introducción y Contexto del Cliente

    Cliente: SecurCorp Solutions, una consultora de ciberseguridad.

    El Problema: SecurCorp administra cientos de servidores Linux para bancos y aseguradoras. Han detectado que, ocasionalmente, archivos de configuración críticos (como .env o config.json) son modificados sin autorización durante la noche. Necesitan una herramienta ligera que no dependa de bases de datos complejas ni frameworks pesados para monitorizar estas carpetas "calientes".

    El Encargo: Debes desarrollar "Sentinel FS", una herramienta de línea de comandos y servidor web nativo (sin frameworks externos como Express) que vigile una carpeta específica. Cuando detecte un cambio, debe registrarlo inmutablemente en un log y exponer esa información en un panel web sencillo para que los administradores de sistemas puedan auditar qué pasó.

    2. 👤 User Scenes (Escenarios de Uso)

    Para entender cómo debe comportarse el sistema, hemos definido los siguientes escenarios:

    1. El inicio de la vigilancia El Administrador de Sistemas arranca la aplicación. En la consola, ve un mensaje confirmando que la carpeta /secure-data está siendo vigilada. Al entrar en el navegador a http://localhost:3000, ve un panel con un indicador verde ("Activo") y el contador de eventos a cero.

    2. La detección del incidente Un intruso (o un proceso automático) modifica el archivo passwords.txt dentro de la carpeta vigilada. Inmediatamente, la consola del servidor imprime una alerta. El sistema escribe una nueva línea en el archivo de registro audit.log con la fecha exacta y el tipo de evento.

    3. La auditoría forense vía Web El Administrador recarga la página web y navega a la sección /events. Allí ve una tabla HTML generada dinámicamente que lista la modificación reciente de passwords.txt. Posteriormente, va a /reports para ver si el sistema ha generado algún resumen diario automático de los archivos logueados.

    3. Requisitos Funcionales

    1. Vigilancia en Tiempo Real:

      • El sistema debe monitorizar una carpeta específica (ej: ./monitor) usando las capacidades nativas del sistema operativo.
      • Debe detectar eventos de cambio de contenido (change) y renombramiento/movimiento (rename).

    2. Persistencia de Logs (Audit Trail):

      • Cada evento detectado debe guardarse en un archivo físico (logs/audit.json o .log).
      • No se debe sobrescribir el historial; los nuevos eventos se añaden al final (append).
      • Formato del registro: Timestamp ISO, Tipo de Evento, Nombre del Archivo.

    3. Interfaz Web de Gestión (Dashboard):

      • Ruta / (Dashboard): Muestra el estado del servicio y métricas básicas (número de eventos registrados).
      • Ruta /events: Lee el archivo de logs y muestra los últimos eventos en una tabla HTML.
      • Ruta /reports: Lista los archivos de informes almacenados en disco y permite visualizarlos.

    4. Feedback en Consola:

      • La aplicación debe imprimir en la terminal cada vez que ocurra un evento relevante.

    4. Requisitos Técnicos

    • Lenguaje: TypeScript (ejecutado con ts-node o compilado).
    • Módulo Principal: node:fs y node:fs/promises (File System).
    • Servidor Web: Módulo nativo node:http. PROHIBIDO USAR EXPRESS, FASTIFY O SIMILARES.
    • Rutas y Paths: Uso obligatorio de node:path para gestionar rutas de forma segura y multiplataforma.
    • Sin Base de Datos: Toda la persistencia debe ser en archivos planos (JSON/TXT).
    • Validación: Uso de try/catch para gestionar errores de lectura/escritura (permisos, ficheros inexistentes).

    5. Estructura del Proyecto

    sentinel-fs/
├── src/
│   ├── index.ts          # Punto de entrada (inicia servidor y watcher)
│   ├── watcher.ts        # Lógica de fs.watch
│   ├── logger.ts         # Lógica de escritura en disco (logs)
│   ├── webServer.ts      # Servidor HTTP nativo (Manejo de rutas)
│   └── utils.ts          # Generadores de HTML simples
├── monitor/              # Carpeta "cebo" que vamos a vigilar
│   └── secret.txt        # Archivo de prueba
├── data/                 # Almacenamiento persistente
│   ├── audit.log         # Log acumulativo de eventos
│   └── status.json       # Estado actual (ej. última hora de inicio)
├── public/               # (Opcional) CSS básico
├── package.json
└── tsconfig.json

    6. Desarrollo Paso a Paso

    Fase 1: Configuración y Servidor HTTP Nativo

    Antes de vigilar nada, necesitamos que el servidor responda. Como no usamos Express, debemos analizar req.url manualmente.

    1. Crea el archivo src/webServer.ts.
    2. Importa createServer de node:http.
    3. Implementa un switch o if/else basado en la URL solicitada.
    4. Para cada ruta, devuelve un HTML básico construido con Template Strings.
    // Pista para src/webServer.ts
import { createServer } from 'node:http';

export const startServer = (port: number) => {
    const server = createServer(async (req, res) => {
        // Headers comunes
        res.setHeader('Content-Type', 'text/html; charset=utf-8');

        if (req.url === '/') {
            res.statusCode = 200;
            res.end('<h1>Sentinel FS: Dashboard</h1><p>Estado: 🟢 Activo</p>');
        } else if (req.url === '/events') {
            // Aquí leeremos el log más adelante
            res.statusCode = 200;
            res.end('<h1>Historial de Eventos</h1><p>Próximamente...</p>');
        } else {
            res.statusCode = 404;
            res.end('<h1>404 - Not Found</h1>');
        }
    });

    server.listen(port, () => {
        console.log(`🌐 Servidor web escuchando en http://localhost:${port}`);
    });
};

    Fase 2: El Ojo que Todo lo Ve (Watcher)

    Vamos a implementar la vigilancia usando fs.watch (la versión recomendada en los apuntes, preferiblemente iterando sobre el AsyncIterator si usas Node moderno, o con callbacks).

    1. Crea src/watcher.ts.
    2. Usa fs/promises o fs para iniciar el watcher sobre la carpeta ./monitor.
    3. Asegúrate de que la carpeta ./monitor existe antes de vigilarla (usa access o mkdir).
    4. Cada vez que detectes un evento, imprímelo por consola.

    Reto: Distingue entre rename (creación/borrado/renombrado) y change (modificación de contenido).

    Fase 3: Persistencia Forense (Logging)

    No sirve de nada ver el evento si se pierde al reiniciar.

    1. Crea src/logger.ts.
    2. Implementa una función logEvent(type: string, filename: string).
    3. Esta función debe:
      • Generar un timestamp.
      • Formatear una línea de texto o JSON (ej: {"date": "...", "type": "change", "file": "..."}).
      • Usar appendFile para añadirla a data/audit.log. Importante: Usa os.EOL para los saltos de línea.

    Fase 4: Conectando Web y Disco

    Ahora volveremos al webServer.ts para hacerlo dinámico.

    1. En la ruta /events:

      • Usa readFile para leer todo el contenido de data/audit.log.
      • Procesa el contenido (separa por saltos de línea \n).
      • Genera una tabla HTML iterando sobre esas líneas.
      • Si el archivo no existe (error ENOENT), muestra un mensaje "Sin eventos registrados".

    2. En la ruta /reports:

      • Usa readdir con la opción withFileTypes: true sobre la carpeta data/.
      • Muestra una lista <ul> con los archivos encontrados.
      • Mejora de seguridad: No permitas leer archivos fuera de esa carpeta.

    Fase 5: Dashboard Informativo

    En la ruta raíz (/), muestra información real: * Lee data/audit.log. * Cuenta cuántas líneas tiene. * Muestra ese número en el Dashboard: "Total de incidentes detectados: X".

    7. Consideraciones de Seguridad y Buenas Prácticas

    Seguridad: Path Traversal

    Aunque en esta práctica leemos archivos locales, en una aplicación real nunca debes pasar un parámetro de la URL directamente a fs.readFile. Mal: fs.readFile(req.url) Bien: Usar path.basename() o validar que la ruta resuelta empieza por la carpeta permitida.

    Gestión de Errores

    ¿Qué pasa si la carpeta logs no existe al intentar escribir? Asegúrate de usar mkdir con la opción { recursive: true } al iniciar la aplicación para garantizar que la estructura de directorios está lista.

    Módulo Path

    Recuerda usar siempre path.join(__dirname, '..', 'monitor') (o similar) para construir rutas. No concatenes strings manualmente (folder + '/' + file), ya que fallará en Windows.

    8. Retos Opcionales / Ampliaciones

    Si terminas rápido, intenta implementar estas mejoras para nota extra:

    1. Watcher Robusto: Usa AbortController para crear una función stopMonitoring() que detenga el watcher limpiamente desde el código.
    2. Detalle de Archivo: Haz que al hacer clic en un archivo en la vista /reports, el servidor lea ese archivo específico y muestre su contenido en el navegador (solo lectura).
    3. Filtrado de Eventos: Ignora los cambios en archivos ocultos (los que empiezan por .) o archivos temporales del sistema.
    4. Formato JSON Lines: Guarda el log en formato .jsonl (un JSON válido por línea) para facilitar el parsing línea a línea en lugar de usar manipulaciones de strings complejas.

    9. Checklist de Autoevaluación

    Antes de entregar, verifica los siguientes puntos:

    • [ ] El servidor arranca sin errores usando ts-node src/index.ts.
    • [ ] Al modificar un archivo en /monitor, aparece el mensaje en consola.
    • [ ] El evento se guarda persistentemente en data/audit.log.
    • [ ] La web muestra el número correcto de eventos en el Dashboard.
    • [ ] La ruta /events muestra la tabla con el historial histórico.
    • [ ] No has utilizado Express, Fastify ni librerías externas de servidor.
    • [ ] El código usa node:fs/promises y async/await.
    • [ ] Las rutas de archivos se construyen con node:path.
