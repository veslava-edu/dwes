    Módulos http y https en Node.js

    Introducción

    Construyendo el Servidor desde Cero. Imagina que Internet es una gigantesca red de carreteras y que tu aplicación es un restaurante de alta cocina que acaba de abrir. Para que los clientes (los navegadores web) puedan hacer sus pedidos (peticiones HTTP) y recibir sus platos (respuestas HTTP), necesitas una infraestructura de comunicación robusta.

    En el mundo de Node.js, los módulos nativos http y https son la centralita telefónica y el servicio de mensajería de tu restaurante. Son el corazón que permite a tu aplicación escuchar peticiones, procesarlas y enviar respuestas. Entender estos módulos a fondo es como conocer el plano de tu cocina: te da el control total para optimizar cada proceso, incluso antes de usar frameworks como Express o Fastify.

    Propósito fundamental

    Los módulos http y https permiten:
    - Crear servidores web sin dependencias externas como Apache o Nginx
    - Realizar peticiones HTTP/HTTPS a otros servidores
    - Trabajar directamente con el protocolo, sin abstracción
    - Integrar con componentes del sistema operativo mediante streams y eventos

    Conceptos Fundamentales

    Antes de sumergirnos en el código, es crucial establecer la terminología que usaremos.

    Definición: Protocolo HTTP (HyperText Transfer Protocol)

    Es el lenguaje estándar que utilizan los navegadores (clientes) y los servidores web para comunicarse. Es la base de cualquier intercambio de datos en la Web.

    Definición: Servidor Web (Web Server)

    Es un software que escucha peticiones a través de un puerto específico (como el 80 o 443) y responde a ellas, sirviendo contenido (HTML, JSON, imágenes, etc.) al cliente. En Node.js, nuestro código usando el módulo http se convierte en el servidor web.

    Definición: Event Loop (Bucle de Eventos)

    Es el mecanismo fundamental de Node.js que permite realizar operaciones de I/O (entrada/salida) no bloqueantes (como las peticiones de red). Es el "director de orquesta" que gestiona las tareas asíncronas de forma eficiente, asegurando que el servidor pueda atender a miles de clientes simultáneamente con un solo hilo de ejecución.

    Desarrollo y Ejemplos Prácticos

    1. Introducción a los módulos http y https

    Los módulos http y https son la columna vertebral de la capacidad de red de Node.js. Su propósito principal es permitir la creación de servidores web y clientes de red sin necesidad de dependencias externas. Esto significa que puedes construir una API o un microservicio completo utilizando solo las herramientas que vienen de serie con Node.js.

    El Corazón de la Comunicación: http vs https

    La diferencia fundamental entre ambos módulos radica en la seguridad y el cifrado de la comunicación:

    Característica Módulo http Módulo https
    Protocolo HTTP (HyperText Transfer Protocol) HTTPS (HTTP Secure)
    Cifrado No cifrado (datos viajan en texto plano) Cifrado mediante TLS/SSL
    Puerto por Defecto 80 443
    Uso Principal Desarrollo local, pruebas, microservicios internos (intranet) Producción, cualquier comunicación que maneje datos sensibles (credenciales, pagos)

    ¡Alerta de Seguridad!

    Nunca utilices el módulo http para desplegar un servidor en producción que maneje datos de usuarios o información sensible. La información viaja sin cifrar y es vulnerable a ataques de tipo Man-in-the-Middle.

    Importación Moderna y Tipado con TypeScript

    En un proyecto moderno de Node.js con TypeScript, la importación se realiza utilizando la sintaxis de módulos ES, y es una buena práctica usar el prefijo node: para indicar que es un módulo nativo, lo que mejora la claridad y el rendimiento en el bundling.

    Para que TypeScript entienda los tipos de estos módulos, es necesario tener instalado el paquete de definiciones de tipos:

    # Instalación de tipos para Node.js
pnpm install -D @types/node

    Ejemplo de Código 1.1: Importación y Tipado Básico

    // server.ts

// Importación moderna con prefijo 'node:'
import * as http from 'node:http';
import * as https from 'node:https';

// El tipo 'IncomingMessage' y 'ServerResponse' son proporcionados por @types/node
import { IncomingMessage, ServerResponse } from 'node:http';

// Definición de una función que maneja la lógica de la petición
// TypeScript nos obliga a tipar correctamente los parámetros
const requestListener = (req: IncomingMessage, res: ServerResponse) => {
    console.log(`Petición recibida: ${req.method} ${req.url}`);

    // El método 'writeHead' también está tipado
    res.writeHead(200, { 'Content-Type': 'text/plain' });
    res.end('¡Hola desde el servidor Node.js con TypeScript!');
};

// Creación del servidor HTTP
const httpServer = http.createServer(requestListener);

// El servidor está tipado como 'http.Server'
console.log(`Tipo del servidor: ${httpServer.constructor.name}`);

// El código es limpio y autocompletado gracias a TypeScript.

    Arquitectura: EventEmitter y el Event Loop

    Los módulos http y https están profundamente integrados con el modelo asíncrono de Node.js. El objeto http.Server es una subclase de EventEmitter, lo que significa que emite eventos cuando ocurren cosas importantes, como una nueva conexión (connection), una nueva petición (request) o un error (error).

    Esta arquitectura basada en eventos permite que el servidor sea altamente concurrente. Cuando llega una petición, el Event Loop la registra y la pasa a un callback (nuestra función requestListener). Mientras se procesa esa petición (que suele ser muy rápido), el Event Loop no se detiene, sino que sigue escuchando la siguiente petición.

    Los servidores HTTP en Node.js heredan de EventEmitter, lo que significa que todo funciona mediante eventos. El servidor no está bloqueado esperando peticiones; en su lugar, escucha eventos en el Event Loop y reacciona cuando llega una petición.

    Cada vez que un cliente se conecta, el servidor emite un evento ('request', 'connection', etc.), y tú proporcionas manejadores (listeners) que responden a esos eventos. Esto permite que miles de conexiones simultáneas se gestionen eficientemente.

    Tabla 1.2: Eventos Clave del Objeto http.Server

    Evento Descripción Uso Práctico
    request Emitido cada vez que llega una petición HTTP. Manejo de la lógica de la aplicación (routing, procesamiento).
    connection Emitido cuando se establece una nueva conexión TCP. Monitorización de conexiones activas o límites de conexión.
    listening Emitido cuando el servidor ha comenzado a escuchar en el puerto. Confirmación de que el servidor está listo para recibir tráfico.
    close Emitido cuando el servidor se detiene. Limpieza de recursos o notificaciones de apagado.

    Ejemplo de Código 1.2: Uso de EventEmitter

    // server_events.ts

import * as http from 'node:http';

const PORT = 3000;

const server = http.createServer((req, res) => {
    // Lógica de la petición
    res.end('Petición procesada.');
});

// Escuchando el evento 'listening'
server.on('listening', () => {
    console.log(`Servidor escuchando en http://localhost:${PORT}`);
});

// Escuchando el evento 'error'
server.on('error', (err: NodeJS.ErrnoException) => {
    if (err.code === 'EADDRINUSE') {
        console.error(`El puerto ${PORT} ya está en uso. ¿Hay otro servidor corriendo?`);
    } else {
        console.error('Ocurrió un error en el servidor:', err.message);
    }
});

// El servidor comienza a escuchar
server.listen(PORT);

    2. Modelo Cliente–Servidor y fundamentos HTTP

    El modelo Cliente-Servidor es el paradigma fundamental de la computación distribuida y la base de Internet. En el contexto de la web, un Cliente (típicamente un navegador o una aplicación móvil) solicita un recurso, y un Servidor (nuestro código Node.js) se encarga de procesar la solicitud y enviar una respuesta.

    El Ciclo Completo: Request → Processing → Response

    La comunicación HTTP sigue un ciclo de vida bien definido:

    1. Request (Solicitud): El cliente (ej. Chrome) envía un mensaje al servidor. Este mensaje incluye:
      • Método HTTP (GET, POST, PUT, DELETE, etc.).
      • URL del recurso solicitado.
      • Cabeceras (metadatos sobre la solicitud, como el tipo de navegador o la autenticación).
      • Cuerpo (Body) de la solicitud (para métodos como POST o PUT).
    2. Processing (Procesamiento): El servidor recibe la solicitud, la analiza, ejecuta la lógica de negocio (ej. consulta a una base de datos, cálculo) y prepara el resultado.
    3. Response (Respuesta): El servidor envía un mensaje de vuelta al cliente. Este mensaje incluye:
      • Código de Estado HTTP (ej. 200 OK, 404 Not Found, 500 Internal Server Error).
      • Cabeceras de Respuesta (metadatos sobre la respuesta, como el tipo de contenido).
      • Cuerpo (Body) de la respuesta (el contenido real: HTML, JSON, etc.).

    La Naturaleza Stateless de HTTP

    HTTP es un protocolo sin estado (stateless). Esto significa que cada par de Request-Response es independiente de cualquier otro par anterior o posterior. El servidor no "recuerda" nada sobre las peticiones previas de un cliente.

    Dato Curioso: ¿Cómo se mantiene la sesión?

    Para simular un "estado" (como mantener la sesión de un usuario logueado), se utilizan mecanismos externos al protocolo base, como las Cookies o los Tokens de Autenticación (ej. JWT), que se envían en las cabeceras de cada petición.

    Evolución del Protocolo: HTTP/1.1 vs HTTP/2

    La evolución del protocolo ha buscado principalmente mejorar la velocidad y la eficiencia de la transferencia de datos.

    Tabla 2.2: Comparativa de Versiones HTTP

    Característica HTTP/1.1 (Estándar Clásico) HTTP/2 (Estándar Moderno)
    Conexiones Una petición por conexión (bloqueo Head-of-Line) Multiplexación: Múltiples peticiones sobre una sola conexión.
    Cabeceras Texto plano, repetitivas. Comprimidas (HPACK), reduciendo el tamaño de la petición.
    Priorización Limitada. Priorización de streams: El servidor puede enviar recursos más importantes primero.
    Server Push No soportado. Soportado: El servidor puede enviar recursos al cliente antes de que este los pida.

    Rendimiento Crítico

    El principal problema de HTTP/1.1 es el bloqueo Head-of-Line, donde una petición lenta puede detener el procesamiento de todas las peticiones subsiguientes en la misma conexión. HTTP/2 resuelve esto con la multiplexación.

    3. Creación de un servidor HTTP básico

    El corazón de cualquier aplicación backend en Node.js es el servidor HTTP. El módulo http nos proporciona la función http.createServer(), que es la encargada de instanciar nuestro servidor.

    http.createServer(requestListener)

    Esta función toma como argumento una función callback que se ejecutará cada vez que el servidor reciba una nueva petición. Esta función es nuestro requestListener y recibe dos objetos fundamentales:

    1. req: IncomingMessage: Representa la solicitud entrante del cliente. Contiene toda la información sobre la petición (URL, método, cabeceras, cuerpo).
    2. res: ServerResponse: Representa la respuesta que vamos a enviar de vuelta al cliente. Contiene métodos para escribir cabeceras, el cuerpo y finalizar la comunicación.

    Ejemplo de Código 3.1: Servidor "Hola Mundo" en TypeScript

    // basic_server.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';

const HOSTNAME = '127.0.0.1'; // localhost
const PORT = 3000;

// 1. Definición del Request Listener
const serverListener = (req: IncomingMessage, res: ServerResponse) => {
    // 2. Análisis de la petición
    console.log(`Petición recibida en: ${req.url}`);

    // 3. Preparación de la respuesta
    // Escribimos la cabecera de respuesta: 200 OK y tipo de contenido
    res.writeHead(200, { 'Content-Type': 'text/html' });

    // Escribimos el cuerpo de la respuesta
    res.write('<h1>Servidor Node.js Activo</h1>');
    res.write(`<p>Ruta solicitada: <strong>${req.url}</strong></p>`);

    // 4. Finalización de la respuesta (obligatorio)
    res.end(); 
};

// 5. Creación del servidor
const server = http.createServer(serverListener);

// 6. El servidor comienza a escuchar
server.listen(PORT, HOSTNAME, () => {
    console.log(`Servidor corriendo en http://${HOSTNAME}:${PORT}/`);
});

    server.listen() y el Ciclo de Vida

    El método server.listen() es el que activa el servidor, haciendo que comience a escuchar las conexiones entrantes en un puerto y dirección IP específicos.

    Parámetro Descripción Valor por Defecto
    port El puerto TCP donde el servidor escuchará. Aleatorio si no se especifica.
    hostname La dirección IP o nombre de host a la que se enlaza. 0.0.0.0 (escucha en todas las interfaces)
    backlog El número máximo de conexiones pendientes en cola. 511
    callback Función que se ejecuta una vez que el servidor está escuchando. N/A

    Buenas Prácticas: Hostname

    Para desarrollo local, usa 127.0.0.1 o localhost. Para producción, si quieres que el servidor sea accesible desde cualquier IP, usa 0.0.0.0 (o simplemente omite el parámetro hostname).

    Manejo Básico de Errores y Eventos

    Como vimos en el punto 1, el servidor es un EventEmitter. Es crucial manejar el evento error para evitar que una excepción no controlada detenga todo el proceso de Node.js.

    Ejemplo de Código 3.2: Manejo de Errores y Routing Básico

    // server_routing.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';

const PORT = 8080;

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {
    // 1. Routing manual basado en la URL
    if (req.url === '/') {
        res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
        res.end('<h1>Página de Inicio</h1><p>Bienvenido a la ruta principal.</p>');
    } else if (req.url === '/api/status') {
        res.writeHead(200, { 'Content-Type': 'application/json' });
        // Enviamos un JSON como respuesta
        res.end(JSON.stringify({ status: 'ok', uptime: process.uptime() }));
    } else {
        // 2. Manejo de error 404 (Not Found)
        res.writeHead(404, { 'Content-Type': 'text/plain' });
        res.end('Error 404: Recurso no encontrado.');
    }
});

// Manejo del evento 'error'
server.on('error', (err: NodeJS.ErrnoException) => {
    console.error('Error fatal del servidor:', err.message);
    // Si el error es por puerto en uso, intentamos notificar al usuario
    if (err.code === 'EADDRINUSE') {
        console.error(`El puerto ${PORT} está ocupado. Por favor, libera el puerto.`);
        // En un entorno profesional, aquí se podría intentar otro puerto o salir del proceso.
        process.exit(1); 
    }
});

server.listen(PORT, () => {
    console.log(`Servidor HTTP básico escuchando en el puerto ${PORT}`);
});

    4. Creación de un servidor HTTPS

    Si el módulo http es la comunicación por radio, el módulo https es la comunicación por radio cifrada y segura. Para crear un servidor HTTPS, utilizamos el módulo https, que es casi idéntico a http, pero requiere un paso adicional: la configuración de certificados TLS/SSL.

    El Módulo https y Diferencias con http

    El módulo https utiliza internamente el módulo tls (Transport Layer Security) de Node.js para gestionar el cifrado. La función para crear el servidor es https.createServer(), que acepta un objeto de opciones como primer argumento, además del requestListener.

    Tabla 4.1: Opciones Mínimas para https.createServer()

    Opción Tipo Descripción
    key string | Buffer La clave privada del certificado (Private Key).
    cert string | Buffer El certificado público (Certificate).
    ca string | Buffer | Array Certificados de la Autoridad de Certificación (CA) intermedios.

    Certificados TLS/SSL: La Identidad del Servidor

    Para que un navegador confíe en tu servidor HTTPS, este debe presentar un certificado digital emitido por una Autoridad de Certificación (CA) reconocida (como Let's Encrypt).

    1. Clave Privada (key): Se mantiene secreta en el servidor. Se usa para descifrar los datos que llegan.
    2. Certificado Público (cert): Se envía al cliente. Contiene la clave pública y la identidad del servidor. Se usa para cifrar los datos que salen del cliente.

    Certificados Autofirmados para Desarrollo

    En producción, siempre debes usar certificados de una CA. Para desarrollo local, puedes generar un certificado autofirmado (self-signed certificate). Los navegadores mostrarán una advertencia de seguridad, pero es funcional para pruebas.

    Configuración Segura y Consideraciones de Entorno

    Una buena práctica profesional es redirigir automáticamente el tráfico HTTP (puerto 80) a HTTPS (puerto 443). Esto se hace creando un servidor HTTP simple que solo se encarga de la redirección.

    Ejemplo de Código 4.2: Redirección de HTTP a HTTPS

    // redirect_server.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';

const HTTP_PORT = 8080;
const HTTPS_PORT = 8443;

// Servidor HTTP para la redirección
const redirectServer = http.createServer((req: IncomingMessage, res: ServerResponse) => {
    // 1. Construimos la nueva URL segura
    const secureUrl = `https://${req.headers.host}:${HTTPS_PORT}${req.url}`;

    // 2. Enviamos el código de estado 301 (Moved Permanently) o 307 (Temporary Redirect)
    res.writeHead(307, { 
        'Location': secureUrl,
        'Content-Type': 'text/plain'
    });

    res.end(`Redirigiendo a ${secureUrl}`);
});

redirectServer.listen(HTTP_PORT, () => {
    console.log(`Servidor HTTP de redirección escuchando en el puerto ${HTTP_PORT}`);
});

    Parsing de URL y Query Parameters

    El objeto req.url contiene la ruta y los parámetros de consulta (query parameters). Para analizarlos de forma segura y sencilla, Node.js proporciona el módulo nativo url.

    Ejemplo de Código 5.2: Uso del Módulo url para Query Parameters

    // url_parsing.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';
import { URL } from 'node:url'; // Importación del módulo URL

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {

    // 1. Creamos un objeto URL. Es necesario un 'base' para URLs relativas.
    // Usamos 'http://localhost' como base temporal para que el constructor funcione.
    const fullUrl = new URL(req.url || '/', `http://${req.headers.host}`);

    const pathName = fullUrl.pathname; // La ruta sin query string
    const userId = fullUrl.searchParams.get('userId'); // Obtener un parámetro específico

    res.writeHead(200, { 'Content-Type': 'text/plain' });

    if (pathName === '/api/user' && userId) {
        res.end(`Buscando usuario con ID: ${userId}`);
    } else {
        res.end(`Ruta: ${pathName}. No se encontró ID de usuario.`);
    }
});

server.listen(3000);

    Lectura del Body mediante Streams (data, end)

    Para peticiones que contienen un cuerpo (ej. POST, PUT), como el envío de un formulario o un JSON, el objeto req actúa como un Stream legible (Readable Stream). Esto es clave para la eficiencia: Node.js no espera a que el cuerpo completo se cargue en memoria, sino que lo procesa en trozos (chunks) a medida que llega.

    El proceso de lectura es asíncrono y se maneja con los eventos data y end:

    1. data: Se emite cuando un trozo de datos está disponible.
    2. end: Se emite cuando se ha recibido todo el cuerpo de la petición.

    Ejemplo de Código 5.3: Lectura de un Body JSON (Asíncrono)

    // body_parsing.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {

    if (req.method === 'POST' && req.url === '/api/data') {
        let body = '';

        // 1. Escuchamos el evento 'data' para acumular los trozos
        req.on('data', (chunk) => {
            body += chunk.toString(); // Convertimos el Buffer a string
        });

        // 2. Escuchamos el evento 'end' para procesar el cuerpo completo
        req.on('end', () => {
            try {
                const data = JSON.parse(body);
                console.log('Datos recibidos:', data);

                res.writeHead(200, { 'Content-Type': 'application/json' });
                res.end(JSON.stringify({ message: 'Datos procesados con éxito', received: data }));

            } catch (error) {
                // 3. Manejo de error de JSON inválido
                res.writeHead(400, { 'Content-Type': 'text/plain' });
                res.end('Error: JSON inválido en el cuerpo de la petición.');
            }
        });

    } else {
        res.writeHead(405, { 'Content-Type': 'text/plain' });
        res.end('Método no permitido o ruta incorrecta.');
    }
});

server.listen(3000);

    Seguridad y Límites de Tamaño (Backpressure)

    El uso de streams es eficiente, pero requiere control. Si un cliente envía un cuerpo de petición gigantesco, y nuestro servidor lo acumula en una variable (let body = ''), podemos agotar la memoria del servidor.

    Riesgo de DoS

    No limitar el tamaño del cuerpo de la petición es un vector de ataque de Denegación de Servicio (DoS). Un atacante podría enviar un archivo de varios GB para colapsar tu servidor.

    El concepto de Backpressure se refiere a la capacidad de un stream de decirle a su fuente que envíe datos más lentamente. Aunque el módulo http lo maneja internamente, en Node.js es una buena práctica limitar el tamaño del cuerpo de la petición antes de acumularlo.

    Tipo de Contenido Cabecera Content-Type Método de Lectura
    JSON application/json Acumular chunks y usar JSON.parse().
    Formulario application/x-www-form-urlencoded Acumular chunks y usar querystring.parse() (módulo nativo).
    Archivos multipart/form-data Requiere librerías externas (ej. formidable, multer) para parsear el formato complejo.

    6. Manejo de respuestas (Response – ServerResponse)

    El objeto res (de tipo ServerResponse) es nuestra herramienta para comunicarnos de vuelta con el cliente. Es un Stream escribible (Writable Stream), lo que nos permite enviar datos en trozos, aunque en la mayoría de los casos de API se usa para enviar la respuesta final de una sola vez.

    Envío de Respuestas y Flujo (write, end)

    El flujo de respuesta sigue estos pasos:

    1. res.writeHead(statusCode, headers): (Opcional, pero recomendado) Escribe las cabeceras de la respuesta y el código de estado. Si no se llama, Node.js lo hace automáticamente con 200 OK cuando se llama a res.end() o res.write() por primera vez.
    2. res.write(chunk): Envía un trozo del cuerpo de la respuesta. Se puede llamar múltiples veces.
    3. res.end(data): Finaliza la respuesta. Es obligatorio llamarlo. Si se le pasa un argumento, ese dato se envía como el último trozo del cuerpo.

    Error Común

    Si olvidas llamar a res.end(), el cliente se quedará esperando la respuesta indefinidamente, lo que resultará en un timeout (tiempo de espera agotado) y una mala experiencia de usuario.

    Estados HTTP (statusCode, statusMessage)

    El código de estado HTTP es crucial, ya que indica el resultado de la operación al cliente.

    Tabla 6.1: Códigos de Estado HTTP Esenciales

    Rango Significado Ejemplos Clave Uso en Node.js (res.writeHead)
    1xx Informativo 100 Continue Raro en el servidor, más para proxies.
    2xx Éxito 200 OK, 201 Created, 204 No Content Operación exitosa.
    3xx Redirección 301 Moved Permanently, 307 Temporary Redirect Mover al cliente a otra URL.
    4xx Error del Cliente 400 Bad Request, 401 Unauthorized, 404 Not Found El cliente cometió un error (ej. URL incorrecta, datos inválidos).
    5xx Error del Servidor 500 Internal Server Error, 503 Service Unavailable El servidor falló al procesar la petición.

    Ejemplo de Código 6.1: Envío de Respuestas Comunes

    // response_types.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {

    if (req.url === '/success') {
        // Respuesta de éxito (JSON)
        res.writeHead(200, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify({ message: 'Operación completada' }));

    } else if (req.url === '/not-found') {
        // Respuesta de error del cliente
        res.writeHead(404, { 'Content-Type': 'text/plain' });
        res.end('El recurso solicitado no existe.');

    } else if (req.url === '/redirect') {
        // Respuesta de redirección
        res.writeHead(302, { 'Location': '/success' });
        res.end(); // El cuerpo es opcional en redirecciones

    } else {
        // Respuesta por defecto (HTML)
        res.writeHead(200, { 'Content-Type': 'text/html' });
        res.end('<h1>Ruta por Defecto</h1>');
    }
});

server.listen(3000);

    Streaming de Respuestas (Archivos, Datos Grandes)

    Para enviar archivos grandes (ej. un video o un archivo ZIP), es fundamental usar el streaming de respuesta. Esto evita cargar todo el archivo en la memoria del servidor antes de enviarlo.

    Podemos "conectar" un Readable Stream (el archivo) directamente a nuestro Writable Stream (res) usando el método pipe().

    Ejemplo de Código 6.2: Streaming de un Archivo con pipe()

    // file_stream.ts

import * as http from 'node:http';
import * as fs from 'node:fs';
import * as path from 'node:path';
import { IncomingMessage, ServerResponse } from 'node:http';

const FILE_PATH = path.join(__dirname, 'large_file.txt'); // Asumimos que existe

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {

    if (req.url === '/download') {

        // 1. Comprobamos si el archivo existe
        if (!fs.existsSync(FILE_PATH)) {
            res.writeHead(404);
            return res.end('Archivo no encontrado.');
        }

        // 2. Obtenemos el tamaño del archivo para la cabecera Content-Length
        const stat = fs.statSync(FILE_PATH);

        // 3. Escribimos las cabeceras para la descarga
        res.writeHead(200, {
            'Content-Type': 'text/plain',
            'Content-Length': stat.size,
            // Cabecera para forzar la descarga con un nombre de archivo
            'Content-Disposition': 'attachment; filename="reporte.txt"' 
        });

        // 4. Creamos un stream de lectura y lo conectamos al stream de respuesta
        const readStream = fs.createReadStream(FILE_PATH);
        readStream.pipe(res); // Conecta el archivo al socket de respuesta

        // Manejo de errores del stream de lectura
        readStream.on('error', (err) => {
            console.error('Error al leer el archivo:', err);
            // Si el error ocurre antes de enviar las cabeceras, podemos enviar un 500
            if (!res.headersSent) {
                res.writeHead(500);
                res.end('Error interno del servidor al enviar el archivo.');
            }
        });

    } else {
        res.writeHead(200);
        res.end('Ruta de prueba.');
    }
});

server.listen(3000);

    7. Cabeceras HTTP y control del protocolo

    Las cabeceras HTTP son metadatos que acompañan tanto a la solicitud como a la respuesta. Son esenciales para el funcionamiento del protocolo, ya que controlan el caching, la seguridad, el tipo de contenido y la autenticación.

    Cabeceras Esenciales

    • Content-Type: Qué te envío.
    • Content-Length: Cuánto ocupa.
    • Cache-Control: Cuánto tiempo puedes guardarlo en memoria.

    Uso de setHeader() y Control de Envío

    El objeto ServerResponse (res) nos permite manipular las cabeceras antes de que se envíe el cuerpo de la respuesta.

    • res.setHeader(name, value): Establece una cabecera.
    • res.getHeader(name): Obtiene el valor de una cabecera.
    • res.removeHeader(name): Elimina una cabecera.
    • res.headersSent: Propiedad booleana que indica si las cabeceras ya han sido enviadas al cliente (después de res.writeHead() o la primera res.write()/res.end()).

    Buenas Prácticas: res.writeHead() vs res.setHeader()

    res.writeHead() es más eficiente para establecer todas las cabeceras de una vez. res.setHeader() es útil para establecer cabeceras de forma condicional antes de la llamada a res.writeHead(). No se puede llamar a res.setHeader() después de que las cabeceras han sido enviadas.

    Cabeceras Esenciales

    Cabecera Tipo (Req/Res) Descripción Uso Práctico
    Content-Type Respuesta Indica el formato del cuerpo de la respuesta (ej. application/json, text/html). Obligatoria para que el cliente sepa cómo interpretar el cuerpo.
    Content-Length Respuesta El tamaño del cuerpo en bytes. Permite al cliente saber cuándo esperar que termine la respuesta.
    User-Agent Solicitud Identifica el software del cliente (navegador, bot, etc.). Routing o lógica específica para ciertos clientes.
    Cache-Control Respuesta Define cómo y por cuánto tiempo el cliente puede almacenar la respuesta en caché. Optimización de rendimiento.
    Authorization Solicitud Contiene credenciales para autenticar al cliente (ej. Bearer Token). Seguridad y acceso a recursos protegidos.

    Ejemplo de Código 7.1: Control de Caching

    // cache_control.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {

    if (req.url === '/static/image.jpg') {
        // 1. Cabeceras para contenido estático (cacheable)
        res.setHeader('Content-Type', 'image/jpeg');
        // Cache-Control: max-age=3600 (1 hora), public (puede ser cacheado por proxies)
        res.setHeader('Cache-Control', 'public, max-age=3600'); 
        res.writeHead(200);
        // Aquí iría el streaming de la imagen...
        res.end('Contenido de la imagen (simulado)');

    } else if (req.url === '/api/data') {
        // 2. Cabeceras para contenido dinámico (no cacheable)
        res.setHeader('Content-Type', 'application/json');
        // Cache-Control: no-store (no guardar en caché), must-revalidate
        res.setHeader('Cache-Control', 'no-store, must-revalidate');
        res.writeHead(200);
        res.end(JSON.stringify({ timestamp: new Date().toISOString() }));

    } else {
        res.writeHead(200);
        res.end('Ruta de prueba.');
    }
});

server.listen(3000);

    CORS y Cabeceras de Seguridad

    El CORS (Cross-Origin Resource Sharing) es un mecanismo de seguridad que permite a un navegador web solicitar recursos a un servidor en un dominio diferente al que sirvió la página original. Por defecto, los navegadores lo prohíben.

    Para habilitar CORS, el servidor debe enviar cabeceras específicas:

    Cabecera CORS Descripción
    Access-Control-Allow-Origin Indica qué orígenes (dominios) tienen permiso para acceder al recurso. Usa * para permitir todos (solo para desarrollo o APIs públicas).
    Access-Control-Allow-Methods Indica qué métodos HTTP están permitidos (GET, POST, etc.).
    Access-Control-Allow-Headers Indica qué cabeceras personalizadas puede enviar el cliente.

    Ejemplo de Código 7.2: Implementación Básica de CORS

    // cors_server.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {

    // 1. Permitir acceso desde cualquier origen (solo para ejemplo)
    res.setHeader('Access-Control-Allow-Origin', '*');
    res.setHeader('Access-Control-Allow-Methods', 'GET, POST, OPTIONS');
    res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization');

    // 2. Manejo de peticiones OPTIONS (preflight request)
    if (req.method === 'OPTIONS') {
        res.writeHead(204); // No Content
        return res.end();
    }

    if (req.url === '/api/data' && req.method === 'GET') {
        res.writeHead(200, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify({ data: 'Datos accesibles desde cualquier dominio' }));
    } else {
        res.writeHead(404);
        res.end('Not Found');
    }
});

server.listen(3000);

    8. Cliente HTTP/HTTPS en Node.js

    Hasta ahora hemos actuado como el servidor. Pero Node.js también es excelente para actuar como cliente, es decir, para hacer peticiones a APIs externas. Para esto, tradicionalmente se usaban http.get() y http.request(), pero el panorama ha cambiado con la llegada de fetch() nativo.

    Realizar Peticiones con http.get() y http.request()

    Ambos métodos son para realizar peticiones salientes.

    • http.get(url, callback): Es un atajo para peticiones GET. Automáticamente llama a req.end().
    • http.request(options, callback): Es el método base. Permite configurar el método (POST, PUT, etc.), cabeceras y requiere que se llame a req.end() manualmente para enviar la petición.

    Ejemplo de Código 8.1: Cliente HTTP Básico con http.get() (Legacy)

    // http_client_legacy.ts

import * as http from 'node:http';

const options = {
    hostname: 'jsonplaceholder.typicode.com',
    port: 80, // Puerto por defecto para HTTP
    path: '/posts/1',
    method: 'GET'
};

// 1. La función de callback recibe la respuesta (res)
const req = http.get(options, (res) => {
    console.log(`Status Code: ${res.statusCode}`);
    console.log(`Content-Type: ${res.headers['content-type']}`);

    let data = '';

    // 2. Acumulamos los datos de la respuesta (stream)
    res.on('data', (chunk) => {
        data += chunk;
    });

    // 3. Procesamos la respuesta completa
    res.on('end', () => {
        try {
            const post = JSON.parse(data);
            console.log('Título del Post:', post.title);
        } catch (e) {
            console.error('Error al parsear JSON:', e);
        }
    });
});

// 4. Manejo de errores de la petición (ej. DNS no resuelto)
req.on('error', (e) => {
    console.error(`Problema con la petición: ${e.message}`);
});

// En http.get() no es necesario llamar a req.end()

    Comparación con fetch() Nativo (Node.js Moderno)

    A partir de Node.js v18, la API global fetch() (estándar de navegadores) está disponible de forma nativa. Es la forma moderna y recomendada de hacer peticiones cliente, ya que es más limpia, basada en Promise y más fácil de usar.

    Ejemplo de Código 8.2: Cliente HTTP con fetch() (Moderno)

    // http_client_fetch.ts

// No se necesita importar nada, fetch es global en Node.js >= 18

async function getPostData(postId: number) {
    const url = `https://jsonplaceholder.typicode.com/posts/${postId}`;

    try {
        // 1. Petición asíncrona
        const response = await fetch(url);

        // 2. Comprobación de estado (fetch no lanza error en 4xx/5xx)
        if (!response.ok) {
            throw new Error(`Error HTTP: ${response.status} ${response.statusText}`);
        }

        // 3. Parseo directo del cuerpo (JSON, text, blob, etc.)
        const data = await response.json();

        console.log(`Título del Post (Fetch): ${data.title}`);

    } catch (error) {
        console.error('Fallo al obtener los datos:', error);
    }
}

    9. Operaciones avanzadas y buenas prácticas

    Una vez que se dominan los fundamentos, es hora de aplicar técnicas que hacen que un servidor Node.js sea robusto, eficiente y profesional.

    Routing Manual Básico

    Aunque los frameworks como Express automatizan el routing, entender cómo funciona a bajo nivel es crucial. El routing manual implica analizar el req.method y el req.url para dirigir la petición a la función de manejo adecuada.

    Sin un framework, debemos construir nuestro propio sistema de rutas. Es como ser un guardia de tráfico.

    Diagrama de Flujo de Routing

    graph TD
    A[Petición Entrante] --> B{¿Método GET?}
    B -- Sí --> C{¿URL /api?}
    B -- No --> D{¿Método POST?}
    C -- Sí --> E[Ejecutar lógica API]
    C -- No --> F[404 Not Found]
    D -- Sí --> G[Leer Body y procesar]
    D -- No --> H[405 Method Not Allowed]

    Ejemplo de Código 9.1: Routing Manual con switch y if

    // advanced_routing.ts

import * as http from 'node:http';
import { IncomingMessage, ServerResponse } from 'node:http';
import { URL } from 'node:url';

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {

    const fullUrl = new URL(req.url || '/', `http://${req.headers.host}`);
    const pathName = fullUrl.pathname;

    switch (req.method) {
        case 'GET':
            if (pathName === '/users') {
                // Lógica para obtener todos los usuarios
                res.writeHead(200, { 'Content-Type': 'application/json' });
                res.end(JSON.stringify([{ id: 1, name: 'Alice' }]));
            } else if (pathName.startsWith('/users/')) {
                // Lógica para obtener un usuario específico (ej. /users/1)
                const id = pathName.split('/')[2];
                res.writeHead(200);
                res.end(`Obteniendo usuario con ID: ${id}`);
            } else {
                res.writeHead(404);
                res.end('Ruta GET no encontrada.');
            }
            break;

        case 'POST':
            if (pathName === '/users') {
                // Lógica para crear un nuevo usuario (requiere lectura del body)
                res.writeHead(201); // Created
                res.end('Usuario creado (simulado).');
            }
            break;

        default:
            res.writeHead(405); // Method Not Allowed
            res.end('Método no soportado.');
    }
});

server.listen(3000);

    Conexiones Persistentes y Keep-Alive

    HTTP/1.1 introdujo las conexiones persistentes, controladas por la cabecera Connection: keep-alive. Esto permite que múltiples peticiones se envíen a través de la misma conexión TCP, reduciendo la latencia de establecer una nueva conexión para cada recurso.

    El módulo http de Node.js maneja keep-alive por defecto, pero es importante saber cómo controlarlo.

    Optimización de Rendimiento

    Mantener la conexión abierta (keep-alive) es una optimización clave, especialmente para servir muchos archivos pequeños (imágenes, CSS, JS) en una sola página web.

    Cierre Graceful del Servidor

    Un cierre graceful (elegante) significa que el servidor deja de aceptar nuevas conexiones, pero permite que las conexiones ya existentes terminen su trabajo antes de apagarse. Esto es vital para evitar que las peticiones de los usuarios se corten a mitad.

    Ejemplo de Código 9.2: Cierre Graceful

    // graceful_shutdown.ts

import * as http from 'node:http';

const server = http.createServer((req, res) => {
    // Simulación de una tarea larga
    setTimeout(() => {
        res.end('Petición completada.');
    }, 500); 
});

server.listen(3000, () => {
    console.log('Servidor activo en puerto 3000.');
});

// Función de cierre elegante
function gracefulShutdown() {
    console.log('\nRecibida señal de apagado. Iniciando cierre elegante...');

    // 1. Detener la aceptación de nuevas conexiones
    server.close((err) => {
        if (err) {
            console.error('Error al cerrar el servidor:', err);
            process.exit(1);
        }
        console.log('Servidor HTTP cerrado. Terminando proceso.');
        // 2. Salir del proceso solo cuando el servidor esté cerrado
        process.exit(0); 
    });

    // 3. Forzar la salida si el cierre tarda demasiado
    setTimeout(() => {
        console.error('El cierre elegante tardó demasiado. Forzando salida.');
        process.exit(1);
    }, 5000); // 5 segundos de gracia
}

// Escuchar señales de terminación comunes
process.on('SIGTERM', gracefulShutdown); // Señal enviada por la mayoría de los gestores de procesos
process.on('SIGINT', gracefulShutdown);  // Ctrl+C

    10. Visión profesional y camino a frameworks

    Entender los módulos http y https es la base para cualquier desarrollador backend de Node.js. Es la diferencia entre ser un "usuario" de un framework y ser un "arquitecto" que entiende cómo funciona la casa por dentro.

    http/https como Base de Express, Fastify y NestJS

    Los frameworks web más populares de Node.js no son más que capas de abstracción construidas sobre los módulos nativos http y https.

    Framework Abstracción Principal Beneficio Clave
    Express Middleware y Routing Simplicidad, gran ecosistema.
    Fastify Routing y Rendimiento Velocidad extrema, validación de esquemas.
    NestJS Arquitectura (MVC/Módulos) Estructura de aplicación empresarial, basado en TypeScript.

    Analogía Laboral:

    Usar http nativo es como construir una casa con ladrillos y cemento (control total, pero lento). Usar Express es como usar un kit prefabricado (rápido, pero con menos control sobre los cimientos).

    Cuándo usar el módulo nativo y cuándo un framework

    Usar Módulo Nativo (http/https) Usar un Framework (Express, Fastify, NestJS)
    Microservicios extremadamente ligeros y de alto rendimiento. APIs REST/GraphQL complejas con muchos endpoints.
    Proxies o Load Balancers personalizados. Aplicaciones con lógica de negocio compleja y necesidad de modularidad.
    Aprender y entender el protocolo HTTP a fondo. Necesidad de seguridad, validación y middleware preconstruido.
    Aplicaciones que solo necesitan un único endpoint muy específico. Proyectos grandes que requieren estándares de codificación y estructura.

    Importancia de Entender HTTP “a bajo nivel”

    Un desarrollador que entiende el IncomingMessage y el ServerResponse puede:

    1. Depurar problemas de red complejos que los frameworks ocultan.
    2. Optimizar el rendimiento al evitar abstracciones innecesarias.
    3. Escribir middleware personalizado para cualquier framework.
    4. Elegir el framework adecuado o incluso crear uno propio.
