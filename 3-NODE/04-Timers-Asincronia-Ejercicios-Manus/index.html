    Ejercicios Prácticos: Timers, Event Loop y Asincronía en Node.js

    Narrativa del Proyecto: Nexus Server Monitor (NSM)

    El equipo de DevOps de Innovatech está desarrollando Nexus Server Monitor (NSM), una herramienta crítica que debe ser extremadamente eficiente y nunca bloquearse, ya que monitoriza la salud de los servidores en tiempo real. Para lograr esto, es fundamental dominar el modelo asíncrono de Node.js, asegurando que las operaciones de I/O (lectura de logs, peticiones de red) no detengan el hilo principal.

    Ejercicios de Consolidación

    1) Diagnóstico de Bloqueo: Síncrono vs Asíncrono | Nivel: Fácil

    1) Diagnóstico de Bloqueo: Síncrono vs Asíncrono | Nivel: Fácil

    Objetivo:

    Comprender la diferencia entre las operaciones síncronas y asíncronas del módulo fs y su impacto en el Event Loop.

    Setup Inicial:

    Crea un archivo llamado io-test.ts.

    Tarea a realizar:

    Analiza el siguiente código y predice el orden de la salida. Luego, crea el archivo y verifica tu predicción.

    import * as fs from 'fs';

console.log('1. Inicio de la solicitud');

// Tarea A: Asíncrona (Non-blocking)
fs.readFile('package.json', 'utf-8', (err, data) => {
  console.log('3. Tarea A (Lectura de archivo asíncrona)');
});

// Tarea B: Síncrona (Blocking)
const data = fs.readFileSync('package.json', 'utf-8');
console.log('2. Tarea B (Lectura de archivo síncrona)');

console.log('4. Fin del script principal');
    1. ¿Cuál es el orden de la salida si package.json es un archivo pequeño?
    2. ¿Qué pasaría si la lectura síncrona (fs.readFileSync) tardara 5 segundos? ¿Qué mensaje se vería afectado?
    Aplicación en el Mundo Real:

    En NSM, usar fs.readFileSync para leer un log gigante bloquearía el monitor, impidiendo que procese otras alertas. Por ello, todas las operaciones de I/O deben ser asíncronas.

    VER Solución.

    1. Orden de Salida (Archivo pequeño): 

      1. Inicio de la solicitud
2. Tarea B (Lectura de archivo síncrona)
4. Fin del script principal
3. Tarea A (Lectura de archivo asíncrona)
      Explicación: El código síncrono (1, 2, 4) se ejecuta primero. La Tarea A es delegada a Libuv y su callback se ejecuta solo cuando el Event Loop se vacía. La Tarea B, aunque es I/O, es síncrona y bloquea el hilo principal hasta que termina.

    2. Si fs.readFileSync tardara 5 segundos: El mensaje 4. Fin del script principal se retrasaría 5 segundos, ya que el hilo principal estaría bloqueado por la Tarea B.

    2) Uso Básico de Timers: setTimeout y setInterval | Nivel: Fácil

    2) Uso Básico de Timers: setTimeout y setInterval | Nivel: Fácil

    Objetivo:

    Implementar tareas temporizadas para simular el polling (verificación periódica) y la ejecución diferida de comandos.

    Setup Inicial:

    Crea un archivo llamado timers-monitor.ts.

    Tarea a realizar:

    El NSM necesita dos funcionalidades:

    1. Alerta de Inicio: Usa setTimeout para imprimir un mensaje de "Sistema de Monitoreo Iniciado" exactamente 2 segundos después de que el script comience.
    2. Verificación Periódica: Usa setInterval para simular una verificación de estado cada 500 milisegundos. Esta verificación debe detenerse automáticamente después de 5 intentos usando clearInterval.
    Aplicación en el Mundo Real:

    Los timers son la base para el polling de APIs, la re-conexión automática a bases de datos y la ejecución de tareas programadas dentro de un servidor.

    VER Solución. 
    // timers-monitor.ts
console.log('Iniciando script...');

// 1. Alerta de Inicio (Ejecución diferida)
setTimeout(() => {
    console.log('✅ Sistema de Monitoreo Iniciado (2 segundos después)');
}, 2000);

// 2. Verificación Periódica (Polling)
let intentos: number = 0;
const MAX_INTENTOS: number = 5;

const intervalo: NodeJS.Timer = setInterval(() => {
    intentos++;
    console.log(`[Polling] Verificando estado del servidor... Intento ${intentos}`);

    if (intentos >= MAX_INTENTOS) {
        clearInterval(intervalo);
        console.log('🛑 Verificación periódica finalizada.');
    }
}, 500);

console.log('El script principal continúa ejecutándose...');

    3) El Orden de Ejecución: setTimeout(0) vs setImmediate | Nivel: Fácil

    3) El Orden de Ejecución: setTimeout(0) vs setImmediate | Nivel: Fácil

    Objetivo:

    Entender la diferencia de prioridad entre setTimeout (Fase Timers) y setImmediate (Fase Check) en el Event Loop.

    Setup Inicial:

    Crea un archivo llamado event-order.ts.

    Tarea a realizar:

    Escribe el siguiente código y predice el orden de la salida.

    console.log('1. Síncrono');

setTimeout(() => {
    console.log('3. setTimeout(0) - Fase Timers');
}, 0);

setImmediate(() => {
    console.log('4. setImmediate - Fase Check');
});

console.log('2. Fin Síncrono');
    1. ¿Por qué el resultado es a menudo no determinista (a veces setTimeout primero, a veces setImmediate primero)?
    2. ¿Qué se ejecuta siempre antes que ambos?
    Aplicación en el Mundo Real:

    La precisión en el orden es vital. setImmediate se usa a menudo para tareas que deben ejecutarse inmediatamente después de la I/O, mientras que setTimeout es para un retraso mínimo.

    VER Solución.

    Orden de Salida (Típico, pero no garantizado): 

    1. Síncrono
2. Fin Síncrono
3. setTimeout(0) - Fase Timers (o 4)
4. setImmediate - Fase Check (o 3)

    1. No Determinista: Al inicio del script, el tiempo que tarda el sistema en preparar el Event Loop puede ser mayor o menor que el delay mínimo de setTimeout(0). Si el tiempo de preparación es mayor que 1ms, el timer puede estar listo antes de que el Event Loop llegue a la fase Check. Si no, setImmediate puede ejecutarse primero.
    2. Siempre antes: El código síncrono (1. Síncrono y 2. Fin Síncrono) se ejecuta siempre antes de que el Event Loop comience a procesar Macrotasks.

    4) Paralelismo Asíncrono con Promise.all | Nivel: Fácil

    4) Paralelismo Asíncrono con Promise.all | Nivel: Fácil

    Objetivo:

    Utilizar Promise.all para ejecutar múltiples tareas asíncronas de forma concurrente y esperar a que todas finalicen.

    Setup Inicial:

    Crea un archivo llamado concurrent-tasks.ts.

    Tarea a realizar:

    El NSM necesita consultar el estado de tres microservicios a la vez.

    1. Crea una función asíncrona simularPeticion(nombre: string, tiempo: number) que use setTimeout (o la versión con promesas de node:timers/promises) para simular una latencia. Debe imprimir "Iniciando [nombre]" y "Finalizando [nombre]" y devolver el nombre.
    2. Llama a Promise.all con tres peticiones con diferentes tiempos (ej: 3s, 1s, 2s).
    3. Mide el tiempo total de ejecución usando console.time y console.timeEnd.
    Aplicación en el Mundo Real:

    Promise.all es la herramienta fundamental para reducir la latencia en APIs, ya que permite que el tiempo de respuesta sea igual al de la tarea más lenta, no a la suma de todas.

    VER Solución. 
    // concurrent-tasks.ts
import { setTimeout } from 'node:timers/promises';

async function simularPeticion(nombre: string, tiempo: number): Promise<string> {
    console.log(`[${nombre}] Iniciando... (Tardará ${tiempo}ms)`);
    await setTimeout(tiempo);
    console.log(`[${nombre}] Finalizando.`);
    return nombre;
}

async function ejecutarConcurrente(): Promise<void> {
    console.time('Tiempo Total de Carga');

    try {
        const resultados = await Promise.all([
            simularPeticion('Microservicio A', 3000),
            simularPeticion('Microservicio B', 1000),
            simularPeticion('Microservicio C', 2000),
        ]);

        console.log('\n✅ Todas las tareas completadas. Resultados:', resultados);
    } catch (error) {
        console.error('❌ Una de las peticiones falló.');
    }

    console.timeEnd('Tiempo Total de Carga');
}

ejecutarConcurrente();

    5) Control de Vida del Proceso con unref() | Nivel: Fácil

    Objetivo:

    Aprender a usar timer.unref() para permitir que el proceso de Node.js termine incluso si un timer secundario sigue activo.

    Setup Inicial:

    Crea un archivo llamado unref-logger.ts.

    Tarea a realizar:

    El NSM tiene una tarea principal y un logger de métricas en segundo plano.

    1. Crea un setInterval llamado logger que se ejecute cada 100ms e imprima "Logueando métricas...".
    2. Aplica logger.unref() al intervalo.
    3. Usa un setTimeout de 2 segundos para simular la finalización de la "Tarea Principal".
    4. Observa y explica por qué el proceso termina después de 2 segundos, a pesar de que el setInterval sigue teóricamente activo.
    Aplicación en el Mundo Real:

    unref() es crucial para tareas de limpieza, métricas o heartbeats que no deben impedir que el servidor se apague o reinicie limpiamente.

    VER Solución. 
    // unref-logger.ts
console.log('Iniciando Tarea Principal...');

// Tarea secundaria (Logger)
const logger: NodeJS.Timer = setInterval(() => {
    console.log('[Logger] Enviando métricas en segundo plano...');
}, 100);

// 1. Desreferenciar el timer. Si es lo único que queda, Node puede salir.
logger.unref();

// Tarea principal que termina después de 2 segundos
setTimeout(() => {
    console.log('✅ Tarea Principal Finalizada.');
    // Node.js saldrá aquí porque el 'logger' ya no mantiene el Event Loop vivo.
}, 2000);

console.log('El Event Loop está activo, pero el logger es secundario.');

    6) Microtasks: Prioridad de process.nextTick | Nivel: Fácil

    6) Microtasks: Prioridad de process.nextTick | Nivel: Fácil

    Objetivo:

    Demostrar la alta prioridad de process.nextTick sobre todas las Macrotasks (Timers y Immediate).

    Setup Inicial:

    Crea un archivo llamado microtask-priority.ts.

    Tarea a realizar:

    Escribe el siguiente código y predice el orden de la salida.

    console.log('1. Inicio Síncrono');

setTimeout(() => console.log('4. setTimeout(0)'), 0);
setImmediate(() => console.log('5. setImmediate'));

Promise.resolve().then(() => {
    console.log('3. Promise.then()');
});

process.nextTick(() => {
    console.log('2. process.nextTick()');
});

console.log('1.5. Fin Síncrono');
    Aplicación en el Mundo Real:

    process.nextTick se usa para garantizar que una función se ejecute de forma asíncrona, pero antes de que el Event Loop pase a la siguiente fase, lo que es útil para inicialización de eventos.

    VER Solución.

    Orden de Salida (Garantizado): 

    1. Inicio Síncrono
1.5. Fin Síncrono
2. process.nextTick()
3. Promise.then()
4. setTimeout(0) (o 5)
5. setImmediate (o 4)
    Explicación: El código síncrono se ejecuta primero. Luego, el Event Loop vacía la cola de Microtasks: process.nextTick tiene la máxima prioridad, seguido por las Promesas. Finalmente, se pasa a las Macrotasks (Timers y Check), cuyo orden es no determinista en este caso.

    7) Depuración de Código: El Bug del Orden Determinista | Nivel: Medio

    7) Depuración de Código: El Bug del Orden Determinista | Nivel: Medio

    Objetivo:

    Encuentra y corrige el bug en el orden de ejecución entre setTimeout(0) y setImmediate cuando se ejecuta dentro de un callback de I/O.

    Setup Inicial:

    El siguiente código simula una lectura de archivo y tiene un problema de orden.

    // bug-order.ts
import * as fs from 'fs';

// Simulamos una lectura de archivo (I/O)
fs.readFile('package.json', () => {
    console.log('--- Dentro del Callback de I/O (Fase Poll) ---');

    // El desarrollador quiere que el timer se ejecute primero
    setTimeout(() => console.log('1. Tarea de Timer'), 0);
    setImmediate(() => console.log('2. Tarea Inmediata'));
});

console.log('Inicio del script');
    Tarea a realizar:
    1. Ejecuta el código y observa la salida. ¿Qué se ejecuta primero (setTimeout o setImmediate)?
    2. Corrige el código para que la Tarea de Timer se ejecute siempre antes que la Tarea Inmediata, sin cambiar los tiempos de los timers.
    3. Pista: El material didáctico indica que dentro de un callback de I/O, el orden es determinista. ¿Qué Microtask tiene la máxima prioridad y podría usarse para "colarse" antes de la fase Check?
    Aplicación en el Mundo Real:

    Garantizar el orden de ejecución es vital para la integridad de los datos. Si una tarea de limpieza (setImmediate) se ejecuta antes de que se complete una tarea crítica (setTimeout), puede haber errores.

    VER Solución.
    1. Observación: Al ejecutar el código, setImmediate se ejecuta primero (2. Tarea Inmediata), porque el callback de fs.readFile termina en la fase Poll, y la siguiente fase es Check (donde vive setImmediate).
    2. Corrección: Para que el setTimeout se ejecute primero, debemos elevar su prioridad a Microtask, o usar una Microtask para forzar la ejecución del setTimeout antes de que el Event Loop llegue a la fase Check. La solución más simple es usar process.nextTick para envolver el setTimeout, aunque esto no garantiza que el setTimeout se ejecute en la misma vuelta. Una solución más directa para forzar el orden es usar process.nextTick para envolver el setTimeout y que se ejecute antes de que el Event Loop pase a la fase Check.
    // bug-order.ts (CORREGIDO)
import * as fs from 'fs';

// Simulamos una lectura de archivo (I/O)
fs.readFile('package.json', () => {
    console.log('--- Dentro del Callback de I/O (Fase Poll) ---');

    // CORRECCIÓN: Usamos process.nextTick para forzar la ejecución
    // de la Tarea de Timer en la cola de Microtasks, que se vacía
    // ANTES de pasar a la fase Check (setImmediate).
    process.nextTick(() => {
        setTimeout(() => console.log('1. Tarea de Timer'), 0);
    });

    setImmediate(() => console.log('2. Tarea Inmediata'));
});

console.log('Inicio del script');

// NOTA: La solución más simple es usar process.nextTick para envolver el setTimeout.
// Sin embargo, la solución más limpia es simplemente usar process.nextTick para la tarea
// que debe ejecutarse primero, ya que tiene la máxima prioridad.

    8) Análisis de Microtasks: nextTick vs Promise | Nivel: Medio

    Objetivo:

    Demostrar la diferencia de prioridad dentro de la cola de Microtasks entre process.nextTick y Promise.resolve().then().

    Setup Inicial:

    Crea un archivo llamado microtask-race.ts.

    Tarea a realizar:

    Escribe el siguiente código, que anida una Microtask dentro de otra.

    console.log('1. Inicio');

Promise.resolve().then(() => {
    console.log('3. Promise Externa');
    process.nextTick(() => console.log('3.5. nextTick Anidado'));
});

process.nextTick(() => {
    console.log('2. nextTick Externo');
    Promise.resolve().then(() => console.log('2.5. Promise Anidada'));
});

console.log('4. Fin');
    1. Predice el orden de la salida, prestando especial atención a los elementos anidados (3.5 y 2.5).
    2. Explica por qué process.nextTick siempre se ejecuta antes que las Promesas, incluso si la Promesa fue declarada antes.
    Aplicación en el Mundo Real:

    Esta jerarquía es importante al diseñar librerías que necesitan garantizar que su código se ejecute antes que el código de terceros que usa Promesas.

    VER Solución.

    Orden de Salida (Garantizado): 

    1. Inicio
4. Fin
2. nextTick Externo
3.5. nextTick Anidado
3. Promise Externa
2.5. Promise Anidada

    Explicación: 1. Síncrono (1, 4): Se ejecuta primero. 2. process.nextTick (2): Tiene la máxima prioridad en la cola de Microtasks. Se ejecuta. 3. nextTick Anidado (3.5): Al ejecutarse 2, se añade 3.5 a la cola de nextTick. Como la cola de nextTick se vacía completamente antes de pasar a las Promesas, 3.5 se ejecuta inmediatamente después de 2. 4. Promise Externa (3): Se ejecuta la primera Promesa. 5. Promise Anidada (2.5): Al ejecutarse 2, se añade 2.5 a la cola de Promesas. Se ejecuta después de 3.

    9) Investigación: Estrategias de Concurrencia y Fallos | Nivel: Alto

    9) Investigación: Estrategias de Concurrencia y Fallos | Nivel: Alto

    Objetivo:

    Investigar y comparar dos estrategias avanzadas de manejo de concurrencia en Promesas, cruciales para el desarrollo de microservicios robustos.

    Setup Inicial:

    No se requiere código inicial.

    Tarea a realizar:

    El NSM necesita consultar el estado de 100 servidores. Si uno falla, el reporte no debe detenerse.

    1. Investiga la diferencia clave entre Promise.all() y Promise.allSettled().
    2. Documenta con ejemplos de código (conceptuales) cómo usarías cada uno en el contexto de NSM:
      • Promise.all: Para tareas donde el fallo de una implica el fallo de todo el sistema (ej: iniciar 3 servicios críticos).
      • Promise.allSettled: Para tareas independientes donde necesitas el resultado de todas, incluso si algunas fallan (ej: consultar el estado de 100 servidores).
    3. Peer Review: Incluye una sección de Peer Review donde se pida a un compañero que evalúe si el uso de Promise.allSettled introduce un riesgo de seguridad al ignorar errores. ¿Cómo debería el desarrollador manejar los rejections después de usar allSettled?
    Aplicación en el Mundo Real:

    En producción, Promise.allSettled es la herramienta preferida para tareas de batch (procesamiento por lotes) donde la resiliencia es más importante que la velocidad.

    VER Solución.

    Comparativa: Promise.all vs Promise.allSettled

    Característica Promise.all(promises) Promise.allSettled(promises)
    Comportamiento ante Fallo Fail-Fast: Si una sola promesa es rechazada (reject), Promise.all se rechaza inmediatamente con el error de la primera promesa. Resiliente: Espera a que todas las promesas se resuelvan o se rechacen.
    Valor de Retorno Un array de valores de las promesas resueltas. Un array de objetos de estado, cada uno con { status: 'fulfilled' | 'rejected', value | reason }.
    Caso de Uso Principal Tareas interdependientes donde el éxito de todas es necesario. Tareas independientes (batch) donde se necesita un reporte completo de todos los resultados.

    Uso en Nexus Server Monitor (NSM)

    1. Uso de Promise.all (Fallo Crítico): Se usa para el inicio de los componentes principales. Si el servidor de logs o la base de datos no están listos, el monitor no puede arrancar.

    async function iniciarServiciosCriticos(): Promise<void> {
    try {
        const [logServer, dbConnection] = await Promise.all([
            iniciarLogServer(), // Si falla, el catch se activa inmediatamente
            conectarBaseDeDatos(),
            cargarConfiguracion()
        ]);
        console.log('Servicios críticos iniciados con éxito.');
    } catch (error) {
        console.error('FATAL: No se pudo iniciar un servicio crítico. Abortando.', error);
        process.exit(1);
    }
}

    2. Uso de Promise.allSettled (Reporte de Estado): Se usa para consultar el estado de 100 servidores. Si 5 fallan, queremos saber cuáles fallaron, pero seguir con el reporte de los 95 restantes.

    async function obtenerReporteCompleto(servidores: string[]): Promise<void> {
    const promesas = servidores.map(servidor => verificarEstado(servidor));

    const resultados = await Promise.allSettled(promesas);

    const fallos = resultados.filter(r => r.status === 'rejected');
    const exitos = resultados.filter(r => r.status === 'fulfilled');

    console.log(`Reporte: ${exitos.length} OK, ${fallos.length} Fallos.`);

    fallos.forEach((f, index) => {
        // Es crucial manejar el error aquí para que no sea ignorado
        console.error(`❌ Servidor ${index + 1} falló. Razón:`, (f as PromiseRejectedResult).reason);
    });
}
    Peer Review (Instrucciones para el compañero):
    • Riesgo de Seguridad/Ignorar Errores: El uso de Promise.allSettled no ignora errores, sino que los encapsula como objetos de estado. El riesgo es que el desarrollador no revise la propiedad reason de los objetos rejected.
    • Manejo de Rejections: El desarrollador debe iterar sobre el array de resultados y buscar explícitamente los objetos con status: 'rejected'. Si no se hace, el error pasa silenciosamente, lo cual es una mala práctica. El código de ejemplo maneja correctamente los rejections al filtrarlos y loguear la razón.

    10) Reto de Codificación: Evitando el Bloqueo de CPU | Nivel: Alto

    10) Reto de Codificación: Evitando el Bloqueo de CPU | Nivel: Alto

    Objetivo:

    Identificar una tarea CPU-Bound y proponer una solución para evitar que bloquee el Event Loop, usando el concepto de Worker Threads o Partitioning.

    Setup Inicial:

    Crea un archivo llamado cpu-blocker.ts.

    Tarea a realizar:

    El NSM necesita calcular un hash de seguridad muy complejo para validar la integridad de un archivo. Este cálculo es CPU-Bound.

    1. Crea una función síncrona fibonacci(n: number) que calcule el número de Fibonacci para un n grande (ej: 40).
    2. Simula un servidor HTTP simple (usando http.createServer) con dos rutas:
      • /fib: Ejecuta fibonacci(40) de forma síncrona.
      • /status: Simplemente responde "OK" inmediatamente.
    3. Prueba de Bloqueo: Lanza una petición a /fib y, mientras espera, lanza una petición a /status. Observa que /status se retrasa.
    4. Propuesta de Solución (Conceptual): Describe cómo se modificaría el código de /fib para delegar el cálculo a un Worker Thread (módulo worker_threads), liberando el hilo principal. No es necesario implementar el Worker Thread completo, solo el código conceptual de cómo se lanzaría.
    Aplicación en el Mundo Real:

    Cualquier tarea que consuma más de 10ms de CPU (cifrado, compresión, cálculo intensivo) debe ser movida fuera del Event Loop para evitar un Denial of Service (DoS) accidental.

    VER Solución.

    Código de Bloqueo (Demostración del Problema)

    // cpu-blocker.ts
import * as http from 'http';

// Tarea CPU-Bound (Síncrona)
function fibonacci(n: number): number {
    if (n <= 1) return n;
    return fibonacci(n - 1) + fibonacci(n - 2);
}

const server = http.createServer((req, res) => {
    if (req.url === '/fib') {
        console.time('Fibonacci');
        // ESTO BLOQUEA EL EVENT LOOP
        const result = fibonacci(40); 
        console.timeEnd('Fibonacci');
        res.writeHead(200, { 'Content-Type': 'text/plain' });
        res.end(`Resultado de Fib(40): ${result}`);
    } else if (req.url === '/status') {
        // Esta ruta se retrasa porque el Event Loop está bloqueado por /fib
        res.writeHead(200, { 'Content-Type': 'text/plain' });
        res.end('OK - Servidor Respondiendo (Lentamente)');
    } else {
        res.writeHead(404);
        res.end('Not Found');
    }
});

server.listen(3000, () => {
    console.log('Servidor escuchando en puerto 3000. Prueba /fib y /status.');
});

    Propuesta de Solución (Worker Threads)

    La solución es mover la función fibonacci(40) fuera del hilo principal de Node.js, delegándola a un hilo de trabajo real (Worker Thread).

    // Solución Conceptual con Worker Threads
import * as http from 'http';
import { Worker } from 'worker_threads'; // Se importaría el módulo

const server = http.createServer((req, res) => {
    if (req.url === '/fib') {
        // 1. En lugar de ejecutar fibonacci(40) aquí, creamos un Worker
        const worker = new Worker('./worker.js', {
            workerData: 40 // Pasamos el argumento
        });

        // 2. El hilo principal sigue libre para atender otras peticiones (como /status)

        worker.on('message', (result) => {
            // 3. Cuando el Worker termina, nos envía el resultado
            res.writeHead(200, { 'Content-Type': 'text/plain' });
            res.end(`Resultado de Fib(40) (Worker): ${result}`);
        });

        worker.on('error', (err) => {
            res.writeHead(500);
            res.end('Error en el Worker');
        });

    } else if (req.url === '/status') {
        // Esta ruta responde inmediatamente, sin esperar a Fibonacci
        res.writeHead(200, { 'Content-Type': 'text/plain' });
        res.end('OK - Servidor Respondiendo (Rápidamente)');
    }
    // ...
});

    • Evaluación: ¿La solución con Worker Threads resuelve el problema de bloqueo del Event Loop?
    • Pregunta: ¿Qué desventaja introduce el uso de Worker Threads en términos de consumo de memoria y latencia inicial (overhead)? (Pista: Crear un hilo es costoso).
    • Alternativa: ¿Podría haberse usado setImmediate para resolver este problema? (Respuesta: No, porque setImmediate solo divide la tarea en Macrotasks, pero sigue usando el mismo hilo principal, lo que no resuelve el problema de CPU-Bound). ```
