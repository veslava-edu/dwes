    Ejercicios Prácticos: Fundamentos de Node.js y Módulos Core

    Contexto del Proyecto: "ServerSentry CLI"

    Eres el nuevo Ingeniero Backend en CloudNet Solutions, una empresa que gestiona servidores para pymes. Tu primera misión es desarrollar "ServerSentry", una herramienta de línea de comandos (CLI) interna. Esta herramienta se ejecutará en los servidores Linux y Windows de los clientes para: 1. Diagnosticar el entorno de ejecución. 2. Reportar el estado del hardware (RAM, CPU). 3. Gestionar logs y archivos de configuración de forma segura.

    El equipo antiguo usaba scripts desordenados. Tu objetivo es profesionalizar esto usando TypeScript y Node.js moderno.

    Ejercicios de Consolidación

    1) Auditoría de Entorno: ¿Dónde estoy corriendo? | Nivel: Fácil

    Objetivo

    Distinguir programáticamente el entorno de ejecución (Node.js vs Navegador) y evitar el uso de APIs no disponibles.

    Setup Inicial

    Imagina que estás auditando un código compartido que falló en producción. Tienes el siguiente fragmento en check-env.ts:

    // check-env.ts
function auditarSistema() {
    console.log("Iniciando auditoría...");

    // Intento de leer la URL actual
    try {
        console.log(`URL actual: ${window.location.href}`);
    } catch (e) {
        console.log("Acceso a window falló.");
    }

    // Intento de leer variables de entorno
    if (process.env.USER) {
        console.log(`Usuario: ${process.env.USER}`);
    }
}

auditarSistema();
    Tarea a realizar
    1. Ejecuta este código con ts-node y observa el resultado.
    2. Modifica el código para que detecte robustamente si está en Node.js antes de intentar acceder a process o window.
    3. Haz que el script imprima: "✅ Entorno Servidor Detectado" o "💻 Entorno Navegador Detectado".
    Aplicación en el Mundo Real

    En librerías "Isomorphic" (que funcionan en Frontend y Backend), detectar el entorno es vital para no romper la aplicación al intentar acceder al DOM en el servidor o al sistema de archivos en el navegador.

    2) El Reportero de Hardware: Uso de os | Nivel: Fácil

    Objetivo

    Utilizar el módulo nativo os para extraer información vital del servidor.

    Tarea a realizar

    Crea un script llamado server-status.ts. Este script debe:
    1. Importar el módulo os.
    2. Obtener la memoria libre y la memoria total del sistema.
    3. Calcular el porcentaje de memoria libre.
    4. Utilizar console.table para mostrar un resumen estructurado con:
        - Arquitectura del SO.
        - Plataforma (win32, linux, etc.).
        - Memoria Total (en GB, con 2 decimales).
        - % Memoria Libre.

    Aplicación en el Mundo Real

    Los agentes de monitoreo (como Datadog o Prometheus) usan estos mismos módulos nativos para alertar a los administradores de sistemas si un servidor se queda sin RAM.

    3) Rutas a Prueba de Balas: Uso de path | Nivel: Fácil

    Objetivo

    Manipular rutas de archivos de forma segura y multiplataforma, evitando errores comunes de concatenación de strings.

    Tarea a realizar

    Estás desarrollando una función que debe guardar un log en la carpeta de documentos del usuario, en una subcarpeta llamada "ServerSentry_Logs".
    1. Crea un archivo path-fixer.ts.
    2. Usa os.homedir() para obtener la carpeta base del usuario.
    3. Usa path.join() para construir la ruta completa al archivo error.log dentro de la estructura mencionada.
    4. Usa path.parse() para descomponer esa ruta resultante y mostrar en consola solo el nombre del directorio (dir) y la extensión (ext).

    Restricción: Está prohibido usar el signo + para unir carpetas (ej: dir + '/' + file).

    Aplicación en el Mundo Real

    Si desarrollas en Windows (donde separan con \) y despliegas en Linux (donde separan con /), tu código fallará si usas strings manuales. path resuelve esto automáticamente.

    4) Refactorización Legacy: De CommonJS a ESM | Nivel: Medio

    Objetivo

    Transformar código "legacy" (CommonJS) a estándares modernos (ES Modules) usando TypeScript.

    Setup Inicial

    Tienes un archivo antiguo math-utils.js (CommonJS): 

    // math-utils.js
const FACTOR = 1.5;
function calcularCarga(cpu) { return cpu * FACTOR; }
module.exports = { calcularCarga };
    Y un app.js que lo usa: 
    // app.js
const { calcularCarga } = require('./math-utils');
console.log(calcularCarga(50));

    Tarea a realizar
    1. Convierte ambos archivos a TypeScript (.ts).
    2. Refactoriza el código para usar ES Modules (export, import).
    3. Utiliza Named Exports (no default).
    4. Asegúrate de que tu package.json tenga "type": "module" (simulado o real).
    5. Recuerda la regla de las extensiones .js en los imports de ESM.
    Aplicación en el Mundo Real

    La industria está migrando activamente a ESM para aprovechar el Tree Shaking (eliminar código no usado) y la compatibilidad nativa con navegadores modernos. Saber migrar código antiguo es una habilidad muy demandada.

    5) Debugging: El misterio del __dirname perdido | Nivel: Medio

    Objetivo

    Identificar y corregir errores causados por el cambio de paradigma entre CJS y ESM.

    Setup Inicial

    Un compañero ha intentado pasar su script a ES Modules pero obtiene un error: ReferenceError: __dirname is not defined.

    // file-locator.ts
// Config: "type": "module" en package.json
import path from 'path';

console.log("Buscando configuración en:");
// ❌ Esto falla en ESM
const configPath = path.join(__dirname, 'config.json'); 
console.log(configPath);
    Tarea a realizar
    1. Explica por qué falla el código (mira la teoría sobre variables globales en ESM).
    2. Reescribe el código para obtener __dirname usando import.meta.url y las utilidades fileURLToPath del módulo url.
    Aplicación en el Mundo Real

    Este es el error número 1 que encuentran los desarrolladores al configurar proyectos modernos de Node.js o al intentar usar herramientas de bundling modernas.

    6) Interfaz CLI: Argumentos y Salida | Nivel: Fácil

    Objetivo

    Interactuar con el usuario a través de la consola usando process.

    Tarea a realizar

    Crea un script cli.ts que actúe como punto de entrada de "ServerSentry".
    1. Debe leer los argumentos pasados por consola (process.argv).
    2. Si el usuario pasa el flag --help, imprime una lista de comandos disponibles.
    3. Si el usuario pasa el flag --version, imprime "v1.0.0".
    4. Si no pasa nada o pasa un comando desconocido, imprime un error usando console.error y termina el proceso con código de error 1 (process.exit(1)).

    Aplicación en el Mundo Real

    Todas las herramientas que usas (git, npm, docker) funcionan analizando argv y gestionando los códigos de salida (exit codes) para que otros scripts sepan si fallaron o no.

    Ejercicios de Refuerzo

    7) El Cargador de Configuración Seguro | Nivel: Medio

    Objetivo

    Usar process.env y path para cargar configuraciones sensibles sin exponerlas en el código.

    Setup

    Necesitas simular que tienes variables de entorno cargadas. 2 opciones:
    * Pasarlas: Puedes pasarlas al ejecutar: PORT=3000 DB_PASS=secret npx ts-node src/config.ts.
    * Módulo dotenv: Puedes usar el módulo dotenv para leer el fichero .env de configuración de variables de entorno:
         1º) npm install dotenv
         2º) En el código:
             - Importarlo al inicio del programa: import dotenv from 'dotenv';
             - Antes de usarlo, lanzar el configurador: dotenv.config();

    Tarea a realizar

    Crea un módulo config.ts que exporte un objeto de configuración.
    1. Debe leer process.env.PORT. Si no existe, usar 8080 por defecto.
    2. Debe leer process.env.DB_PASS. Si no existe, lanzar un error fatal y cerrar el proceso (no podemos arrancar sin base de datos).
    3. Debe definir una ruta base para los archivos temporales usando os.tmpdir() y path.join haciendo path.join(os.tmpdir(), 'server-sentry-tmp')

    Aplicación en el Mundo Real

    La "12-Factor App methodology" establece que la configuración debe guardarse en el entorno, nunca hardcodeada en el repositorio (especialmente contraseñas).

    8) Investigación: require vs import en profundidad | Nivel: Medio

    Objetivo

    Consolidar la diferencia técnica en el momento de carga entre CJS y ESM.

    Tarea a realizar

    Responde a las siguientes preguntas en un fichero de texto investigacion.md:
    1. Si tengo un archivo bloqueante.js que tarda 5 segundos en ejecutarse (bucle while):
    * ¿Qué pasa con el resto del programa si lo cargo con require('./bloqueante')?
    * ¿Permite ESM (import) cargar módulos de forma condicional (dentro de un if)? Investiga sobre "Dynamic Imports".

    • Pista: Busca "Node.js dynamic import syntax".
    Aplicación en el Mundo Real

    Entender esto permite optimizar el tiempo de arranque de aplicaciones grandes (Lazy Loading), cargando módulos pesados solo cuando realmente se necesitan.

    9) Modularización de Utilidades | Nivel: Medio

    Objetivo

    Practicar la exportación nombrada y la organización de código.

    Tarea a realizar

    Crea una estructura de proyecto pequeña:
    * src/utils/formatters.ts: Debe exportar funciones para formatear fechas (ISO string) y formatear bytes a MB (número).
    * src/utils/logger.ts: Debe exportar una clase Logger con un método log(msg) que use el formateador de fechas.
    * src/main.ts: Importa Logger, instancia uno y manda un mensaje.

    • Pista: Usa export const en formatters y export class en logger. Evita export default.
    Aplicación en el Mundo Real

    Mantener funciones "puras" (como los formateadores) separadas de la lógica de negocio (como el Logger) facilita los tests unitarios.

    Ejercicios de Ampliación

    10) El Reto del Monitor de Procesos (Peer Review) | Nivel: Alto

    Objetivo

    Manipular process y os para crear una herramienta de diagnóstico real.

    Tarea a realizar

    Crea una herramienta CLI llamada proc-mon.ts.
    1. Debe mostrar el PID (Process ID) actual del propio script.
    2. Debe mostrar el uso de memoria actual del proceso (process.memoryUsage()).
    3. Debe mostrar el tiempo que lleva encendido el sistema operativo (os.uptime()) convertido a horas/minutos legibles.
    4. Reto: Implementa un setInterval que actualice esta información en consola cada 2 segundos.
    5. Peer Review: Intercambia tu código con un compañero. El revisor debe comprobar:
    * ¿Se limpian los intervalos al salir (Ctrl+C)? (Investiga process.on('SIGINT')).
    * ¿Es el código TypeScript estricto?
    * ¿La conversión de tiempo es correcta?

    Aplicación en el Mundo Real

    Este es el principio básico de cómo funcionan herramientas como top o htop en Linux.

    11) Diagrama de Arquitectura: ¿Por qué es asíncrono? | Nivel: Alto

    Objetivo

    Comprender el "Event Loop" y la arquitectura interna de Node.js.

    Tarea a realizar

    Investiga por qué Node.js puede manejar miles de peticiones con un solo hilo (Single Threaded), pero operaciones como fs.readFile (acceso a disco) no bloquean ese hilo.

    1. Crea un diagrama en Mermaid que explique el flujo:

      • Script JS llama a fs.readFile.
      • La llamada pasa a Node API / Libuv.
      • Libuv usa el Thread Pool del Sistema Operativo (Worker Threads).
      • El Event Loop recoge el callback cuando termina la lectura.

    2. Explica en 3 líneas qué pasaría si Node leyera archivos de forma síncrona en un servidor web.

    Aplicación en el Mundo Real

    Entender esto es la diferencia entre un Junior y un Senior. Es la base para entender por qué no debemos hacer operaciones pesadas de CPU (cálculos matemáticos complejos) en el hilo principal de Node.

    12) ServerSentry Pro: Persistencia de Logs | Nivel: Alto

    Objetivo

    Integrar todos los conocimientos (fs, path, os, modules) en un script funcional.

    Tarea a realizar

    Desarrolla el módulo final snapshot.ts.
    1. Debe ejecutarse una sola vez y generar un archivo .json.
    2. El nombre del archivo debe ser snapshot-YYYY-MM-DD.json (usa la fecha actual).
    3. El contenido del JSON debe incluir:
    * Usuario del sistema.
    * CPUs (modelo y velocidad).
    * Interfaces de red (IPs).
    * Memoria libre actual.
    4. El archivo debe guardarse en una carpeta logs relativa al script. Si la carpeta no existe, el script debe crearla (investiga fs.mkdirSync o la versión asíncrona).

    Aplicación en el Mundo Real

    Esto simula un "cron job" (tarea programada) que recolecta métricas diarias para análisis forense o histórico.
