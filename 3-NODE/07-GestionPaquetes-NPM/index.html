    Gestión de Paquetes con npm

    Introducción a npm

    npm es el corazón del ecosistema Node.js. Si JavaScript es el lenguaje, npm es la biblioteca donde vive toda la comunidad. Imagina npm como un enorme almacén de LEGO: millones de bloques (paquetes) que otros desarrolladores han construido, probado y compartido. En lugar de reinventar la rueda cada vez que quieres hacer algo, entras al almacén, tomas los bloques que necesitas y los ensamblas en tu proyecto.

    ¿Por qué usar un gestor de paquetes?

    Problema sin npm Solución con npm
    Tienes que descargar archivos .js manualmente y meterlos en carpetas. Un solo comando (npm install) descarga y organiza todo.
    Es difícil saber qué versión de una librería estás usando. El archivo package.json registra versiones exactas.
    Actualizar una librería implica borrar archivos y volver a descargar. npm update se encarga de todo el proceso de forma segura.
    Las librerías que usas pueden necesitar otras librerías (dependencias de dependencias). npm resuelve automáticamente todo el árbol de dependencias.

    Dato Curioso: El Registro de npm

    El registro de npm alberga más de 2 millones de paquetes. Es el registro de software más grande del mundo, superando a los de Java (Maven), Python (PyPI) o PHP (Composer). Es la infraestructura central de prácticamente todas las aplicaciones web modernas.

    Conceptos Fundamentales

    Para movernos con soltura en el ecosistema de Node.js, debemos entender los pilares de su gestión de dependencias.

    Definición: npm (Node Package Manager)

    Es el gestor de paquetes por defecto para Node.js. Se compone de tres partes: un sitio web para buscar paquetes, un registro (una base de datos gigante) y una interfaz de línea de comandos (CLI) que usamos para instalar y gestionar librerías en nuestros proyectos.

    Definición: Paquete (Package)

    Es una carpeta que contiene código (normalmente una librería de JavaScript/TypeScript) y un archivo package.json que lo describe. Es la unidad básica de software que compartimos y reutilizamos en la comunidad.

    Definición: Dependencia (Dependency)

    Es un paquete externo que tu proyecto necesita para funcionar. Por ejemplo, si usas una librería para conectar con una base de datos, esa librería es una dependencia de tu proyecto.

    1. ¿Qué es npm exactamente?

    npm consta de tres componentes esenciales:

    Los tres pilares de npm

    • Sitio web (npmjs.com): descubres paquetes, creas tu perfil, gestionas organizaciones
    • CLI (Command Line Interface): herramienta que ejecutas en terminal, cómo interactúas con npm
    • Registry (Registro): base de datos pública con millones de paquetes y sus metadatos

    Propósito fundamental

    npm permite:
    - Reutilizar código: no escribes fetch desde cero, usas un paquete
    - Gestionar versiones: controla qué versión de cada paquete usas
    - Compartir tu código: publica tus propios paquetes para que otros los usen
    - Automatizar tareas: desde compilar código hasta ejecutar tests
    - Trabajar en equipo: asegura que todos usan las mismas versiones (lock files)

    npm vs Otros Gestores

    Característica npm Yarn pnpm
    Origen El original, viene con Node. Creado por Facebook para mejorar velocidad. Enfocado en eficiencia de espacio en disco.
    Instalación Automática con Node.js. Requiere instalación extra. Requiere instalación extra.
    Estructura node_modules plano (versiones modernas). node_modules plano. node_modules con enlaces simbólicos (ahorra espacio).
    Uso en FP Estándar educativo. Muy común en empresas React. Tendencia actual por rapidez.

    Instalación y verificación

    Node.js incluye npm de forma automática. Para verificar que lo tienes:

    # Ver versión de npm
npm --version
# Salida típica: 10.5.0 (en 2025)

# Ver versión de Node.js
node --version
# Salida típica: v20.11.0

# Obtener información del usuario npm (si estás logueado)
npm whoami

    2. Ecosistema: ¿Qué ventajas e inconvenientes crees que tiene el hecho de que cualquier persona pueda subir un paquete al registro de npm?
    3. Seguridad: ¿Cómo crees que npm ayuda a mantener la seguridad de las aplicaciones si una librería que usamos tiene una vulnerabilidad conocida?
    4. Práctica: Ejecuta npm -v en tu terminal. Si tu versión es inferior a la 10, investiga cómo podrías actualizar npm a la última versión estable.


    2. Crear un paquete con npm

    La forma más simple de crear un proyecto npm es inicializarlo. npm te hará preguntas y creará un archivo package.json con tus respuestas.

    npm init: creando desde cero

    Cuando ejecutamos npm init, se nos preguntará por:
    - package name: El nombre de tu proyecto (debe ser en minúsculas y sin espacios).
    - version: Siguiendo el estándar de Semantic Versioning (ej. 1.0.0).
    - description: Una breve explicación de qué hace tu app.
    - entry point: El archivo principal (ej. index.js o dist/main.js en TS).
    - test command: El comando para ejecutar tus tests.
    - git repository: La URL de tu repositorio.
    - keywords: Etiquetas para encontrar tu paquete.
    - author: Tu nombre o empresa.
    - license: Normalmente MIT o ISC para código abierto.

    La inicialización guiada es perfecta cuando comienzas un proyecto nuevo:

    # Crear carpeta del proyecto
mkdir mi-proyecto-ts
cd mi-proyecto-ts

# Inicializar npm (modo interactivo)
npm init
# Te hará preguntas sobre:
# - package name: (mi-proyecto-ts)
# - version: (1.0.0)
# - description: Mi primer proyecto con TypeScript
# - entry point: (index.js)
# - test command:
# - git repository:
# - keywords:
# - author: Tu nombre
# - license: (ISC)

# O versión rápida (acepta todos los defaults)
npm init -y
# Crea package.json con valores por defecto

    Ejemplo 1: Inicialización interactiva paso a paso

    # Terminal output:
# Press ^C at any time to quit.
# package name: (my-app) mi-app-node
# version: (1.0.0) 1.0.0
# description: Una aplicación increíble en Node.js
# entry point: (index.js) src/index.ts
# test command: npm run test
# git repository: https://github.com/usuario/mi-app
# keywords: node,typescript,webapp
# author: Juan Pérez
# license: (ISC) MIT

    Ejemplo 2: Inicialización rápida

    npm init -y
# Crea automáticamente con valores por defecto
# {
#   "name": "mi-carpeta",
#   "version": "1.0.0",
#   "main": "index.js",
#   ...
# }

    Ejemplo 3: Inicialización con prefijo de scope

    # Para paquetes que publicarás con tu organización
npm init --scope=@miempresa

# Genera:
# "name": "@miempresa/mi-paquete"
# Lo que lo hace único y diferente de otros

    Consideraciones al crear paquetes

    • El nombre debe ser único si lo vas a publicar
    • Evita nombres en MAYÚSCULAS
    • Evita caracteres especiales excepto - y _
    • Si es privado, no importa tanto, pero sigue buenas prácticas
    • Usa nombres descriptivos y cortos

    ¡Cuidado con el nombre!

    Si planeas subir tu paquete a npm algún día, asegúrate de que el nombre no esté ya cogido. Puedes comprobarlo en npmjs.com.

    npm init vs npm init -y

    Comando npm init npm init -y
    Interacción Pregunta campo por campo. No pregunta nada, asume defaults.
    Personalización Alta desde el principio. Baja (tienes que editar el fichero luego).
    Velocidad Lento (1-2 minutos). Instantáneo.
    Uso recomendado Proyectos serios / Producción. Pruebas / Demos / Ejercicios de clase.

    Campos clave al iniciar

    Campo Significado Recomendación TypeScript
    entry point El archivo principal de ejecución. Apuntar al JS compilado (ej: ./dist/index.js).
    test command Comando para pasar tests. Usar Jest o Vitest (jest).
    author Creador del paquete. Tu nombre + email.

    3. Introducción al formato JSON

    JSON (JavaScript Object Notation) es el formato que npm usa para guardar configuración. Es simple, legible y estructurado.

    Estructura básica de JSON

    // JSON válido: pares clave-valor
{
  "nombre": "valor",
  "numero": 42,
  "booleano": true,
  "array": [1, 2, 3],
  "objeto": { "anidado": "valor" }
}

    Reglas importantes de JSON:

    Regla Válido Inválido
    Las claves siempre van entre comillas "nombre": "Juan" nombre: "Juan"
    Los strings van entre comillas dobles "hola" 'hola' o hola
    Sin comas al final "a": 1, "b": 2 "a": 1, "b": 2,
    Solo estos tipos de datos string, number, boolean, null, array, object functions, undefined, NaN

    Ejemplo 1: Validación de JSON

    // ✅ JSON VÁLIDO
{
  "name": "mi-app",
  "version": "1.0.0",
  "author": "Juan",
  "active": true,
  "dependencies": {}
}

// ❌ JSON INVÁLIDO (clave sin comillas)
{
  name: "mi-app",  // Error: clave debe ir entre comillas
  "version": "1.0.0"
}

// ❌ JSON INVÁLIDO (comillas simples)
{
  "name": 'mi-app',  // Error: debe ser comillas dobles
  "version": "1.0.0"
}

    Ejemplo 2: Estructura anidada correcta

    {
  "name": "proyecto-complejo",
  "config": {
    "puerto": 3000,
    "host": "localhost",
    "ssl": false
  },
  "scripts": {
    "start": "node index.js",
    "test": "jest"
  },
  "dependencies": {
    "express": "^4.18.0",
    "typescript": "^5.0.0"
  }
}

    Tablas Comparativas

    JSON vs Objeto JavaScript/TypeScript

    Característica JSON Objeto JS/TS
    Comillas en claves Obligatorias ("key"). Opcionales (key o "key").
    Comillas en strings Solo dobles ("valor"). Dobles, simples o backticks (', ", `).
    Comentarios No permitidos. Permitidos (//, /**/).
    Tipos de datos Texto, número, booleano, null, array, objeto. Todo lo anterior + Funciones, Undefined, Dates, etc.

    Usos de JSON

    Uso Descripción Ejemplo
    Configuración Guardar preferencias de herramientas. package.json, tsconfig.json, .eslintrc.
    APIs Enviar y recibir datos servidor-cliente. Respuestas REST API.
    Almacenamiento Bases de datos NoSQL. MongoDB (usa BSON, binario de JSON).

    Ejemplo 3: Validar JSON desde línea de comandos

    # Verificar si un archivo JSON es válido
npm ls  # Si hay error, mostrará problema en package.json

# Con herramientas externas
node -e "console.log(JSON.parse(require('fs').readFileSync('package.json', 'utf8')))"
# Si no hay error, JSON es válido

# Con jq (si lo tienes instalado)
jq . package.json

    Herramientas para trabajar con JSON

    • VS Code: valida JSON automáticamente (rojo si hay error)
    • JSONLint.com: pega tu JSON y verifica online
    • npm ls: muestra si package.json tiene problemas
    • npx json-lint: comando directo desde npm

    Versionado Semántico (SemVer)

    El versionado sigue el formato MAYOR.MENOR.PARCHE (por ejemplo, 1.2.3):

    Componente Cambio Ejemplo
    MAYOR Breaking changes (incompatible) 1.0.0 → 2.0.0
    MENOR Nuevas features (compatible) 1.2.0 → 1.3.0
    PARCHE Bug fixes (compatible) 1.2.0 → 1.2.1

    Símbolos de Versión (SemVer)

    Símbolo Significado Ejemplo con 1.2.3 Se actualizará a...
    ^ (Caret) Compatible con la versión Mayor. ^1.2.3 1.9.9 (No sube a 2.0.0).
    ~ (Tilde) Compatible con la versión Menor. ~1.2.3 1.2.9 (No sube a 1.3.0).
    Nada Versión exacta. 1.2.3 1.2.3 (Fijo).
    * Cualquier versión. * La última absoluta (Peligroso). 
    // Comparación de versiones
"1.2.3"  // Exacto: solo esta versión
"^1.2.3" // Compatible: 1.2.3, 1.2.4, 1.3.0, pero NO 2.0.0
"~1.2.3" // Aproximado: 1.2.3, 1.2.4, pero NO 1.3.0
"*" o "" // Cualquier versión
">1.0.0" // Mayor que 1.0.0

    5. package-lock.json: El guardián de la consistencia

    Mientras que package.json es flexible (permite rangos como ^1.2.3), package-lock.json es absolutamente específico. Guarda exactamente qué versiones se instalaron.

    ¿Por qué necesitas package-lock.json?

    Imagina que especificas "express": "^4.18.0" en package.json. Esto significa: - Hoy: npm instala 4.18.2 - Mañana: se lanza 4.19.0 que cumple ^4.18.0 - Si instalas de nuevo, podrías obtener 4.19.0 (¡comportamiento diferente!)

    package-lock.json previene esto asegurando que todos usen exactamente las mismas versiones. El package-lock.json soluciona esto:
    1. Fija las versiones exactas de todas las dependencias y sus sub-dependencias.
    2. Garantiza la reproducibilidad: El proyecto se instalará exactamente igual en cualquier ordenador.
    3. Mejora la velocidad: npm no tiene que calcular qué versiones descargar, ya están escritas en el lock.

    Estructura de package-lock.json

    {
  "name": "mi-proyecto",
  "version": "1.0.0",
  "lockfileVersion": 3,
  "requires": true,
  "packages": {
    "": {
      "name": "mi-proyecto",
      "version": "1.0.0",
      "dependencies": {
        "express": "4.18.2"  // Versión EXACTA instalada
      }
    },
    "node_modules/express": {
      "version": "4.18.2",
      "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
      "integrity": "sha512-...",  // Hash para verificar integridad
      "dependencies": {
        "body-parser": "1.20.1",  // Sus dependencias también especificadas
        "content-disposition": "0.5.4"
      }
    }
  }
}

    Ejemplo 1: Reproducibilidad con lock files

    # Día 1: Desarrollador A instala
npm install
# Crea package-lock.json con versiones exactas
# Versiones instaladas: express@4.18.2, jest@29.7.0

# Día 7: Desarrollador B clona repo
npm install
# Lee package-lock.json
# Instala EXACTAMENTE: express@4.18.2, jest@29.7.0
# (aunque 4.19.0 y 29.8.0 estén disponibles)

# ¡Ambos trabajar con idéntico comportamiento!

    Ejemplo 2: Actualización controlada

    # Para actualizar pero mantener consistency:

# Opción 1: Actualizar solo parches (bug fixes)
npm update
# Actualiza 4.18.2 → 4.18.3 si hay parches
# Actualiza package-lock.json automáticamente

# Opción 2: Actualizar a versión más nueva manualmente
npm install express@^4.19.0
# Actualiza package.json Y package-lock.json
# Ahora todos instalarán 4.19.x

# Opción 3: Ver qué está desactualizado
npm outdated
# Muestra qué paquetes tienen versiones más nuevas

    Ejemplo 3: Detectar problemas con lock files

    # Si alguien modifica manualmente package.json sin npm:
# (por ejemplo, cambia version de express)

npm ci  # "clean install" - usa package-lock.json
# ✅ Instala exactamente lo que dice package-lock.json
# Si hay conflicto, npm ci falla (buena para CI/CD)

npm install
# ⚠️ Intenta reconciliar package.json con package-lock.json
# Más flexible pero menos seguro

    Mejores prácticas con lock files

    • SIEMPRE commitea package-lock.json a Git
    • Usa npm ci en CI/CD (no npm install)
    • Nunca elimines package-lock.json manualmente
    • Revisa cambios en package-lock.json en PRs

    package.json vs package-lock.json

    Característica package.json package-lock.json
    Generado por Usuario (npm init) o npm. Automáticamente por npm.
    Edición Manual (frecuente). Prohibida (manual).
    Versiones Rangos (^, ~). Exactas y URLs de descarga.
    Propósito Definir requisitos del proyecto. Garantizar consistencia e integridad.

    Regla de Oro del Desarrollador

    NUNCA edites el package-lock.json a mano. Y SIEMPRE súbelo a tu repositorio Git. Es vital para el trabajo en equipo.

    6. Instalar y desinstalar paquetes con npm

    La razón principal de usar npm es instalar paquetes de otros desarrolladores. Es simple pero tiene muchos matices.

    Comandos de Instalación

    • npm install <paquete>: Instala y añade a dependencies.
    • npm install -D <paquete>: Instala y añade a devDependencies (la -D es de Development).
    • npm install -g <paquete>: Instala de forma global en tu sistema (ej. para herramientas CLI como nodemon o typescript).

    Instalación de paquetes

    # Instalar y añadir a dependencies
npm install express
# o forma corta:
npm i express

# Instalar como devDependency (solo desarrollo)
npm install --save-dev typescript
# o forma corta:
npm i -D typescript

# Instalar múltiples paquetes a la vez
npm install express axios dotenv
npm install -D jest @types/node typescript

# Instalar versión específica
npm install express@4.18.2

# Instalar versión compatible más nueva
npm install express@^4.18.0

# Instalar globalmente (comando disponible en todo el sistema)
npm install -g @angular/cli
# Ahora puedes usar: ng new my-app (desde cualquier carpeta)

# Solo para producción (sin devDependencies)
npm install --production
# Útil para despliegues donde no necesitas testing, etc.

    Diagrama: Flujo de Instalación

    graph TD
    A[npm install react] --> B{¿Está en caché local?}
    B -- Sí --> C[Copiar desde caché]
    B -- No --> D[Descargar desde Registry npm]
    D --> E[Guardar en caché]
    E --> C
    C --> F[Descomprimir en node_modules]
    F --> G[Actualizar package.json]
    G --> H[Generar/Actualizar package-lock.json]

    Desinstalación de paquetes

    # Desinstalar y quitar de package.json
npm uninstall express
# o forma corta:
npm rm express

# Desinstalar del devDependencies
npm uninstall --save-dev typescript
npm rm -D typescript

# Desinstalar globalmente
npm uninstall -g @angular/cli

# Limpiar paquetes no usados
npm prune
# Elimina paquetes que están en node_modules pero no en package.json

    Ejemplo 1: Setup inicial de un proyecto

    # 1. Crear proyecto
mkdir mi-api
cd mi-api
npm init -y

# 2. Instalar dependencias de producción
npm install express axios pg dotenv

# 3. Instalar dependencias de desarrollo
npm install -D typescript @types/express @types/node
npm install -D ts-node nodemon  # Para desarrollo más cómodo
npm install -D jest @types/jest # Para testing

# Resultado en package.json:
# "dependencies": { "express": "^4.18.2", ... }
# "devDependencies": { "typescript": "^5.3.3", ... }

    Ejemplo 2: Migrando proyecto existente

    # Si clonas un repo que ya tiene package.json y package-lock.json

# Simplemente ejecuta (instala todo lo que falta):
npm install
# Descarga todos los paquetes especificados

# Verifica lo instalado:
npm list
# Muestra árbol de dependencias (puede ser largo)

# Ver solo dependencias directas:
npm list --depth=0

    Ejemplo 3: Limpiar y reinstalar

    # A veces npm se corrompe y necesitas limpiar:

# 1. Elimina node_modules (pasta con todos los paquetes)
rm -rf node_modules  # Unix/Mac
rmdir /s node_modules  # Windows

# 2. Limpia caché (opcional pero recomendado)
npm cache clean --force

# 3. Reinstala limpiamente
npm install

# Alternativa más segura (npm 6.13+):
npm ci  # clean install, usa package-lock.json exactamente

    npm install vs npm ci

    • npm install: Flexible, ajusta versions si es necesario
    • npm ci (clean install): Estricto, instala exactamente package-lock.json
    • Usa npm ci en CI/CD, producción y equipos
    • Usa npm install durante desarrollo local

    node_modules: El Agujero Negro

    Cuando instalas paquetes, se guardan en la carpeta node_modules. Esta carpeta puede llegar a ser enorme. Nunca la subas a Git. Para eso está el archivo .gitignore.

    Instalación Local vs Global

    Tipo Comando Ubicación Uso
    Local npm i paquete ./node_modules Librerías que tu código importa (import x from 'x').
    Global npm i -g paquete /usr/local/lib o %AppData% Herramientas de sistema (ej: npm, vercel).

    Flags útiles de instalación

    Flag Alias Acción
    --save (Ya no es necesario) Antes de npm 5, era obligatorio para guardar en package.json. Ahora es default.
    --save-dev -D Guarda en devDependencies.
    --global -g Instala en el sistema, no en el proyecto.
    --force - Fuerza la instalación ignorando conflictos (Peligroso).

    7. Uso avanzado de npm

    npm tiene capacidades avanzadas para proyectos profesionales y monorepos. Una vez dominas lo básico, npm ofrece herramientas para optimizar y asegurar tu proyecto.

    Auditoría de Seguridad

    npm comprueba automáticamente si las librerías que usas tienen fallos de seguridad conocidos.

    Ejemplo de Código 7.1: Auditoría y reparación

    # Ver informe de vulnerabilidades
npm audit

# Intentar arreglar automáticamente las vulnerabilidades
npm audit fix

# Forzar arreglos (¡Cuidado! Puede actualizar versiones Major y romper cosas)
npm audit fix --force

    Gestión de Versiones y Actualizaciones

    Ejemplo de Código 7.2: Comprobar paquetes desactualizados

    # Muestra qué paquetes tienen versiones nuevas disponibles
npm outdated

    Ejemplo de Código 7.3: Ejecutar binarios sin instalar (npx)

    npx es una herramienta que viene con npm y permite ejecutar paquetes sin tener que instalarlos globalmente. Es ideal para herramientas que solo vas a usar una vez.

    # Ejecutar el compilador de TypeScript sin tenerlo instalado globalmente
npx tsc --init

# Crear una app de React (ejecuta el creador y luego se borra)
npx create-react-app my-app

    Truco de Profesional: npm scripts y npx

    Dentro de la sección "scripts" de tu package.json, no necesitas usar npx. npm ya busca automáticamente los binarios dentro de node_modules/.bin.

    npm vs npx

    Herramienta npm npx
    Nombre Node Package Manager. Node Package Execute.
    Función Gestionar (instalar/borrar). Ejecutar.
    Caso de uso "Quiero tener esta librería". "Quiero usar esta herramienta ahora".
    Persistencia Guarda archivos en disco. Temporal (o usa los locales de node_modules).

    Comandos de Mantenimiento

    Comando Descripción ¿Cuándo usarlo?
    npm audit Busca vulnerabilidades. Regularmente o antes de desplegar.
    npm outdated Muestra paquetes con versiones nuevas. Cuando quieras actualizar dependencias.
    npm update Actualiza paquetes respetando SemVer (^). Para mantener el proyecto al día.
    npm ci Clean Install. En servidores de despliegue (borra node_modules e instala desde lockfile).

    8. Dependencias de desarrollo VS dependencias de producción

    Esta es una diferencia crítica que confunde a muchos desarrolladores nuevos.

    ¿Cuál es la diferencia real?

    • Dependencias de Producción (dependencies):Tu aplicación se ejecuta en el servidor de clientes. Son el código que tu aplicación ejecuta mientras el usuario la usa. Sin ellas, la app falla. Ejemplos: Express, axios, dotenv, bases de datos, utilidades de lógica. NO necesita: jest, eslint, typescript (ya compilado)
    • Dependencias de Desarrollo (devDependencies): Tu computadora mientras escribes código. Son herramientas que tú, como programador, usas para escribir, probar o compilar el código. Necesita AMBAS: dependencias + devDependencies. No se necesitan para que la app funcione una vez terminada. Ejemplos: TypeScript, Jest, ESLint, Prettier.

    La regla del compilado

    TypeScript se compila a JavaScript. El servidor ejecuta JavaScript. Por tanto, el compilador typescript NO hace falta en el servidor de producción, solo en tu máquina para generar el JS. Por eso es una devDependency.

    peerDependencies y optionalDependencies

    Para casos especiales:

    {
  "peerDependencies": {
    // Para plugins que requieren que el host tenga cierta versión

    // Ejemplo: plugin que solo funciona con React 18+
  },

  "optionalDependencies": {
    // Para paquetes que IF no se instalan, no falla todo

  },

  "bundledDependencies": [
    // Para empaquetar (npm pack) junto a tu paquete

    "moment"
  ]
}
