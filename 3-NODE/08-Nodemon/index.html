    Automatización del Desarrollo con Nodemon

    Introducción

    Imagina que eres un escritor de novelas que trabaja en una máquina de escribir antigua. Cada vez que quieres corregir una sola palabra en una página, tienes que sacar el papel, tirarlo a la papelera, poner uno nuevo y volver a escribir toda la página desde el principio. Frustrante, ¿verdad? Pues así es exactamente como se siente desarrollar en Node.js sin herramientas de automatización: haces un cambio en tu código, detienes el servidor manualmente (Ctrl+C), y lo vuelves a arrancar (node app.js).

    En el mundo del desarrollo moderno, Nodemon es como tener un procesador de textos inteligente. Él se queda vigilando tu "papel" (tu código) y, en el preciso instante en que detecta que has cambiado una coma o una función, él mismo se encarga de "reescribir" y "publicar" (reiniciar el servidor) por ti. Como vimos en el tema anterior sobre npm, Nodemon es una de esas piezas fundamentales que instalamos para que nuestra vida como desarrolladores sea mucho más fluida y productiva.

    Conceptos Fundamentales

    Antes de ensuciarnos las manos con la terminal, definamos qué es esta herramienta y por qué es el estándar en la industria.

    Definición: Nodemon

    Es una utilidad que monitoriza los cambios en el código fuente de tu aplicación y reinicia automáticamente el servidor. No requiere cambios en tu código original ni en la forma en que programas; simplemente envuelve el comando node original.

    Definición: Hot Reloading (Recarga en Caliente)

    Es la capacidad de una herramienta de desarrollo para aplicar cambios en el código sin necesidad de reiniciar manualmente todo el proceso. Aunque Nodemon técnicamente hace un reinicio completo, el efecto para el desarrollador es una experiencia de recarga casi instantánea.

    Definición: Watcher (Observador)

    Es un proceso en segundo plano que utiliza eventos del sistema operativo para detectar cuándo un archivo ha sido guardado, modificado o eliminado dentro de un directorio específico.

    Desarrollo y Ejemplos Prácticos

    1. ¿Qué es Nodemon y para qué se utiliza?

    Nodemon (abreviatura de Node Monitor) es una herramienta de línea de comandos diseñada para mejorar la experiencia de desarrollo (Developer Experience o DX). Su propósito es eliminar la tarea repetitiva de reiniciar el proceso de Node.js cada vez que editamos un archivo.

    Problemas que resuelve

    Sin Nodemon (Manual) Con Nodemon (Automático)
    Tienes que recordar parar el proceso con Ctrl+C. Nodemon detecta el guardado y para el proceso por ti.
    Tienes que volver a escribir el comando de ejecución. Nodemon arranca el proceso inmediatamente.
    Pierdes entre 5 y 10 segundos en cada cambio. El reinicio ocurre en milisegundos tras guardar.
    Riesgo de estar probando código antiguo por olvidar reiniciar. Garantiza que siempre estás ejecutando la última versión guardada.

    Diferencia Clave

    A diferencia de ejecutar node app.js, que es un proceso de "disparar y olvidar", nodemon app.js es un proceso persistente que se mantiene vivo mientras tú trabajas.

    Ejemplo de Código 1.1: Ejecución tradicional (Node) 

    # Ejecución única. Si cambias el código, no pasa nada hasta que reinicies.
node src/index.js

    Ejemplo de Código 1.2: Ejecución con Nodemon 

    # Nodemon envuelve a node. Se queda "escuchando" cambios.
nodemon src/index.js

    Ejemplo de Código 1.3: Forzar reinicio manual 

    # Si por alguna razón Nodemon no detecta un cambio, 
# puedes escribir 'rs' en la terminal donde corre Nodemon y pulsar Enter.
rs

    Diagrama de Flujo del Proceso

    flowchart LR
    A[Desarrollador guarda archivo] -->|Evento FS| B(Nodemon Watcher)
    B -->|Detecta cambio| C{¿Es extensión válida?}
    C -- No --> D[Ignorar]
    C -- Sí --> E[Matar proceso actual]
    E --> F[Arrancar nuevo proceso]
    F --> G[Servidor actualizado]

    🧠 Reflexión

    1. Productividad: Si haces 50 cambios al día y cada reinicio manual te toma 10 segundos, ¿cuánto tiempo total estarías perdiendo a la semana sin Nodemon?
    2. Flujo de Trabajo: ¿Por qué crees que Nodemon es una herramienta exclusiva de desarrollo y nunca debería usarse en un servidor de producción?
    3. Detección: ¿Cómo crees que Nodemon sabe qué archivos debe vigilar y cuáles debe ignorar (como la carpeta node_modules)?
    4. Práctica: Intenta arrancar un script simple con node y haz un cambio. Luego haz lo mismo con nodemon. ¿Qué diferencias notas en la terminal?


    2. Instalación y primeros pasos

    Como aprendimos en el tema de npm, tenemos dos formas principales de instalar herramientas: global o localmente. Con Nodemon, la tendencia moderna es la instalación local.

    Instalación Local vs Global

    Tipo de Instalación Comando Uso Recomendado
    Global npm install -g nodemon Para herramientas que usas en muchos proyectos pequeños sin package.json.
    Local (Dev) npm install -D nodemon Estándar profesional. Asegura que todos los desarrolladores del proyecto usen la misma versión.

    ¡Alerta de devDependencies!

    Nodemon debe instalarse siempre con el flag -D (o --save-dev). Esto indica que es una herramienta de desarrollo y no se incluirá cuando subas tu app a producción (donde usarás algo más robusto como PM2 o Docker).

    Ejemplo de Código 2.1: Instalación profesional (Local) 

    # Instalamos nodemon como dependencia de desarrollo
npm install -D nodemon

    Ejemplo de Código 2.2: Verificación de instalación 

    # Si es global:
nodemon -v

# Si es local (usando npx):
npx nodemon -v

    Ejemplo de Código 2.3: Actualización 

    # Para actualizar a la última versión en tu proyecto
npm update nodemon

    Diagrama de Decisión de Instalación

    graph TD
    A[¿Cómo instalo Nodemon?] --> B{¿Es un proyecto compartido?}
    B -- Sí (Equipo/Git) --> C[Instalación Local]
    C --> D[npm install --save-dev nodemon]
    B -- No (Script rápido/Prueba) --> E{¿Lo usarás mucho?}
    E -- Sí --> F[Instalación Global]
    F --> G[npm install -g nodemon]
    E -- No --> H[Uso temporal con npx]
    H --> I[npx nodemon script.js]

    🧠 Reflexión

    1. Versiones: ¿Qué problema podría surgir si un compañero de equipo tiene instalada la versión 2.0 de Nodemon globalmente y tú tienes la 3.0?
    2. Espacio en disco: ¿Por qué crees que algunos desarrolladores prefieren la instalación global a pesar de no ser la recomendada para proyectos serios?
    3. Seguridad: ¿Cómo ayuda el archivo package-lock.json (que vimos en el tema anterior) a que Nodemon funcione igual en todos los ordenadores del equipo?
    4. Práctica: Instala Nodemon localmente en un proyecto nuevo y comprueba que aparece en la sección devDependencies de tu package.json.


    3. Uso básico de Nodemon

    Nodemon es extremadamente sencillo de usar. En su forma más básica, solo necesita saber qué archivo quieres ejecutar.

    Ejecución y Comportamiento

    Por defecto, Nodemon vigila todos los archivos con extensiones .js, .mjs, .coffee, .litcoffee y .json en el directorio actual y sus subdirectorios.

    Ejemplo de Código 3.1: Ejecución de un archivo específico 

    # Vigila cambios y ejecuta server.js
nodemon server.js

    Ejemplo de Código 3.2: Pasar argumentos a tu aplicación 

    # Nodemon pasará los argumentos '--port 3000' al proceso de node
nodemon app.js --port 3000

    Ejemplo de Código 3.3: Ejecutar scripts que no son Node 

    # Nodemon también puede vigilar y ejecutar otros lenguajes usando '--exec'
nodemon --exec "python3" script.py

    Reinicio Inteligente

    Nodemon espera un pequeño lapso de tiempo (un segundo por defecto) después de un cambio antes de reiniciar. Esto evita reinicios múltiples si guardas varios archivos a la vez.

    Diagrama de Secuencia: Ciclo de vida básico

    sequenceDiagram
    participant Dev as Desarrollador
    participant NM as Nodemon
    participant App as Tu Aplicación (Node)

    Dev->>NM: npx nodemon index.js
    NM->>App: Inicia proceso (PID 1234)
    App-->>Dev: "Servidor escuchando en puerto 3000"

    Note over Dev, App: Pasa el tiempo...

    Dev->>Dev: Modifica archivo.js
    Dev->>NM: Guardar cambios (Evento OS)
    NM->>NM: Detecta cambio
    NM->>App: SIGUSR2 / Kill PID 1234
    App-->>NM: Proceso termina
    NM->>App: Inicia nuevo proceso (PID 1235)
    App-->>Dev: "Servidor escuchando en puerto 3000"

    Tabla: Comandos CLI útiles

    Flag / Comando Descripción Ejemplo
    --watch Vigila solo carpetas/archivos específicos. nodemon --watch src/ app.js
    --ext Define qué extensiones disparan el reinicio. nodemon --ext ts,json,html
    --delay Espera X segundos tras un cambio antes de reiniciar. nodemon --delay 2.5
    --exec Ejecuta un binario que no sea 'node'. nodemon --exec "python3"

    🧠 Reflexión

    1. Extensiones: Si estás trabajando en un proyecto de Frontend y cambias un archivo .css, ¿crees que Nodemon reiniciará el servidor por defecto? ¿Por qué?
    2. Argumentos: ¿Cuál es la diferencia entre nodemon --help y nodemon app.js --help?
    3. Interrupción: ¿Qué sucede con las conexiones activas de los usuarios cuando Nodemon reinicia el servidor? ¿Es un proceso "invisible" para el usuario final?
    4. Práctica: Crea un archivo test.js que imprima un mensaje cada 2 segundos usando setInterval. Arráncalo con Nodemon y cambia el mensaje mientras corre.


    4. Integración con NPM y package.json

    En un entorno profesional, nunca ejecutamos nodemon directamente desde la terminal. En su lugar, creamos un script de npm.

    Ventajas de usar Scripts de NPM

    1. Abstracción: No necesitas recordar flags complejos; solo ejecutas npm run dev.
    2. Portabilidad: No importa si Nodemon está instalado globalmente o no; npm lo encontrará en node_modules.
    3. Estandarización: Todos los desarrolladores del mundo saben que npm start o npm run dev son los comandos para empezar.

    Creando Scripts Profesionales

    El archivo package.json es el centro de mando.

    Ejemplo 4.1: Configuración Estándar para JS

    {
  "name": "mi-api-daw",
  "scripts": {
    "start": "node dist/index.js",       // Producción
    "dev": "nodemon src/index.js"        // Desarrollo
  },
  "devDependencies": {
    "nodemon": "^3.0.1"
  }
}

    Ejemplo 4.2: Configuración para TypeScript (con ts-node)

    {
  "scripts": {
    "build": "tsc",
    "start": "node dist/index.js",
    // Nodemon llamará a ts-node para ejecutar el TS directamente
    "dev": "nodemon src/index.ts" 
  }
}
    Nota: Para que esto funcione fluido, a veces requerimos configurar el nodemon.json que veremos luego.

    Ejemplo 4.3: Scripts con parámetros

    A veces queremos pasar variables de entorno. 

    {
  "scripts": {
    "dev": "PORT=8080 nodemon src/index.ts"
  }
}

    Ventajas de no instalarlo globalmente

    Al usar npm run dev, NPM busca automáticamente en la carpeta ./node_modules/.bin/. Esto significa que no necesitas tener nodemon instalado en tu sistema, solo en el proyecto. Esto garantiza que todos los desarrolladores usen la misma versión de Nodemon definida en el package.json.

    1. Nomenclatura: ¿Por qué solemos llamar al script dev para Nodemon y start para Node directo?

    3. Entorno: ¿Qué pasaría si intentas ejecutar npm run dev en un ordenador que no tiene instaladas las dependencias (node_modules)?
    4. Práctica: Configura un script dev en tu proyecto que use Nodemon para arrancar tu archivo principal.


    5. Configuración de Nodemon

    A medida que los proyectos crecen, la configuración por defecto se queda corta. Para proyectos serios, usamos un archivo llamado nodemon.json.

    Opciones clave de configuración

    Opción Propósito Ejemplo
    watch Directorios específicos a vigilar. ["src", "config"]
    ignore Archivos o carpetas que NO deben provocar reinicio. ["test/*", "docs/*"]
    ext Extensiones de archivo adicionales. "ts,json,graphql"
    exec El comando exacto para ejecutar el archivo. "ts-node src/index.ts"
    delay Tiempo de espera antes de reiniciar (ms). 2500

    Ejemplo de Código 5.1: Archivo nodemon.json profesional 

    {
  "watch": ["src"],
  "ext": "ts,json",
  "ignore": ["src/**/*.spec.ts"],
  "exec": "ts-node ./src/index.ts"
}

    Ejemplo de Código 5.2: Configuración dentro de package.json 

    // Si no quieres crear un archivo extra, puedes usar la clave 'nodemonConfig'
"nodemonConfig": {
  "watch": ["src"],
  "delay": 2000
}

    Ejemplo de Código 5.3: Configuración por línea de comandos (CLI) 

    # Útil para pruebas rápidas sin tocar archivos de config
nodemon --watch lib --extension js,xml server.js

    ¡Cuidado con los bucles infinitos!

    Si tu aplicación escribe archivos (logs, bases de datos SQLite) en una carpeta que Nodemon está vigilando, entrarás en un bucle infinito de reinicios. Usa siempre ignore para estas carpetas.

    Diagrama de Clases (Configuración)

    classDiagram
    class NodemonConfig {
        +Array~String~ watch
        +String ext
        +Array~String~ ignore
        +String exec
        +Object env
        +Boolean legacyWatch
    }

    class ProyectoTS {
        +watch = ["src"]
        +ext = "ts,json"
        +exec = "ts-node src/app.ts"
    }

    class ProyectoJS {
        +watch = ["lib"]
        +ext = "js"
        +exec = "node lib/server.js"
    }

    NodemonConfig <|-- ProyectoTS
    NodemonConfig <|-- ProyectoJS

    Tabla: Propiedades vs Flags CLI

    Propiedad JSON Flag equivalente Descripción
    watch --watch Directorios a vigilar.
    ignore --ignore Archivos que NO deben reiniciar la app.
    ext --ext Lista de extensiones separadas por coma.
    env N/A (inline vars) Variables de entorno inyectadas.

    🧠 Reflexión

    1. Rendimiento: ¿Por qué es mejor vigilar solo la carpeta src en lugar de todo el proyecto?
    2. Extensiones: Si estás usando una base de datos en un archivo .json, ¿por qué deberías añadir ese archivo a la lista de ignore?
    3. Delay: ¿En qué tipo de proyectos crees que sería útil aumentar el delay a 5 o 10 segundos?
    4. Práctica: Crea un archivo nodemon.json que ignore una carpeta llamada temp y comprueba que al crear archivos dentro de ella, el servidor no se reinicia.


    6. Uso de Nodemon en proyectos reales (TypeScript)

    En el mundo de TypeScript, Nodemon no puede ejecutar los archivos .ts directamente porque Node solo entiende JavaScript. Aquí es donde entra en juego la integración con otras herramientas.

    Escenario A: Express + TypeScript

    Este es el estándar moderno en Node.js. Usamos ts-node para ejecución en memoria durante el desarrollo (es lento en producción, pero genial en dev).

    Ejemplo 6.1: Estructura de carpetas

    /mi-proyecto
  /src
    - app.ts (Express)
    - routes.ts
  - package.json
  - nodemon.json
  - tsconfig.json
    Nodemon vigila src. Cuando guardas routes.ts, ts-node recompila al vuelo en memoria y Express reinicia.

    Escenario B: Entornos con Docker

    Aquí viene un problema clásico. Docker corre en un contenedor (Linux virtualizado). Nodemon dentro de Docker a veces no recibe el evento de archivo guardado desde Windows/Mac.

    El problema del Polling en Docker

    Los sistemas de archivos virtuales a veces no propagan los eventos de cambio. Si usas Docker y Nodemon no reinicia, necesitas activar el modo Legacy Watch (Polling).

    Ejemplo 6.2: Configuración para Docker (Legacy Watch)

    Esto fuerza a Nodemon a "preguntar" cada X milisegundos si el archivo cambió, en lugar de esperar a que le avisen. Consume más CPU, pero es infalible en Docker.

    // nodemon.json para Docker
{
  "legacyWatch": true,
  "pollingInterval": 1000 
}
    O vía comando: nodemon -L

    Escenario C: Depuración (Debugging)

    Si quieres usar el debugger de VS Code o Chrome DevTools, necesitas pasarle el flag de inspección a Node, no a Nodemon.

    Ejemplo 6.3: Debugging

    nodemon --inspect src/index.js
    Esto abre el puerto 9229 para que puedas poner puntos de ruptura (breakpoints).

    Diagrama: Nodemon + Docker

    graph TD
    subgraph Host[Tu Ordenador]
        Code[Código Fuente]
    end

    subgraph Container[Contenedor Docker]
        Volume[Volumen Montado]
        NM[Nodemon -L]
        Node[Proceso Node]
    end

    Code -- Sincronización de Volumen --> Volume
    NM -- Polling (Pregunta cte.) --> Volume
    Volume -- Cambio detectado --> NM
    NM -- Reinicio --> Node

    Tabla: Tecnologías complementarias

    Tecnología Rol Interacción con Nodemon
    Express Framework Web Nodemon reinicia el servidor HTTP.
    TypeScript Lenguaje Requiere ts-node o paso de compilación previo.
    Docker Contenedor Requiere -L (legacy watch) a menudo.
    Dotenv Variables Env Conviene añadir .env a la lista de ext.

    🧠 Reflexión

    1. En un proyecto con Docker, ¿por qué preferimos montar un volumen con el código en lugar de copiarlo al construir la imagen durante la fase de desarrollo?

    7. Opciones avanzadas y rendimiento

    Cuando el proyecto se vuelve gigante (miles de archivos), Nodemon puede empezar a consumir mucha CPU o volverse lento.

    Control de reinicios y depuración

    • --quiet: Reduce la cantidad de mensajes en la terminal.
    • --verbose: Muestra exactamente qué archivo provocó el reinicio (ideal para depurar bucles infinitos).
    • --signal SIGTERM: Cambia la señal que Nodemon envía para parar el proceso (útil para cierres elegantes o graceful shutdowns).

    Ejemplo de Código 7.1: Depuración de reinicios 

    # Si el servidor se reinicia y no sabes por qué:
nodemon --verbose src/index.js

    Ejemplo de Código 7.2: Limitar el reinicio a una sola vez 

    # Si quieres que se detenga tras el primer error fatal
nodemon --exitcrash server.js

    Ejemplo de Código 7.3: Eventos de Nodemon Nodemon puede ejecutar comandos cuando ocurren eventos específicos (reinicio, error, etc.). 

    "nodemonConfig": {
  "events": {
    "restart": "echo '¡Servidor reiniciado con éxito!'",
    "crash": "notify-send '¡La app ha petado!'"
  }
}

    8. Buenas prácticas y alternativas

    Para cerrar este tema, veamos cómo encaja Nodemon en el ecosistema actual y qué otras opciones tenemos.

    Comparativa con Alternativas

    Herramienta Propósito Ventaja Desventaja
    Nodemon Desarrollo Universal, muy configurable. Requiere instalación extra.
    node --watch Desarrollo Nativo (sin instalar nada). Menos opciones de configuración (por ahora).
    PM2 Producción Gestión de clusters, auto-reinicio tras fallos. Demasiado pesado para desarrollo.
    tsx / ts-node-dev Desarrollo TS Mucho más rápidos que Nodemon+ts-node. Específicos para TypeScript.

    Error de Novato: Nodemon en Producción

    Nunca, jamás, uses Nodemon en producción. Nodemon no está diseñado para la estabilidad, sino para la comodidad. Si tu app falla por un error de memoria, Nodemon podría entrar en un bucle de reinicios infinito que consuma todos los recursos del servidor. Usa PM2 o Docker para producción.

    Resumen de Buenas Prácticas

    1. Instalación Local: Siempre como devDependency.
    2. Usa nodemon.json: Mantén tu package.json limpio y la configuración centralizada.
    3. Ignora lo innecesario: Sé estricto con la carpeta ignore para evitar reinicios accidentales.
    4. Scripts Semánticos: Usa npm run dev para que cualquier desarrollador sepa qué hacer.

    🎓 Visión profesional y camino a frameworks

    Nodemon es la puerta de entrada a la automatización. Una vez que te acostumbras a que el servidor se reinicie solo, empezarás a buscar automatizar los tests, el estilo del código (Prettier) y el despliegue. En frameworks como NestJS, Nodemon ya viene configurado de serie porque es imposible entender el desarrollo moderno sin él.
