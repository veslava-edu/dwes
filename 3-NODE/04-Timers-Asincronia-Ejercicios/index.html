    Actividades: Dominando el Tiempo en Node.js (Proyecto "CitySense")

    Bienvenido al equipo de UrbanaTech. Acabas de ser asignado al proyecto CitySense, la plataforma que gestiona en tiempo real los sensores de tráfico, contaminación y transporte público de una "Smart City".

    A diferencia de una web normal, aquí manejamos miles de eventos por segundo. Si tu código bloquea el Event Loop un solo segundo, 50 semáforos podrían desincronizarse. Tu misión es optimizar el "latido" de la ciudad utilizando Timers, Asincronía y el Event Loop de Node.js.

    ¡Manos a la obra, Dev!

    Ejercicios de Consolidación

    1) Concepto: El Semáforo Bloqueado | Nivel: Fácil

    Objetivo:

    Diferenciar claramente entre operaciones bloqueantes (síncronas) y no bloqueantes (asíncronas) en el contexto de un servidor.

    Tarea a realizar:

    Analiza las siguientes dos situaciones hipotéticas en el servidor de control de semáforos y responde:

    1. Situación A: Al arrancar el servidor a las 03:00 AM, el sistema lee un archivo config.json de 5KB para saber la IP de las cámaras. Se usa fs.readFileSync.
    2. Situación B: A las 08:00 AM (hora punta), llega una petición HTTP para cambiar el estado de un semáforo. El servidor necesita registrar este evento en un archivo de log de 2GB. Se usa fs.appendFileSync.

    Preguntas: * ¿En cuál de las dos situaciones es "aceptable" usar la versión síncrona (Blocking)? ¿Por qué? * Explica qué sucedería con el resto de semáforos de la ciudad en la Situación B mientras se escribe el log.

    Aplicación en el Mundo Real:

    Saber cuándo se puede "pecar" de síncrono (startup) y cuándo es un crimen (runtime) es vital para la estabilidad del servicio.

    2) Código: El Latido del Sensor (Interval vs Timeout) | Nivel: Fácil

    Objetivo:

    Implementar y diferenciar el uso de setInterval y setTimeout para tareas repetitivas, manejando correctamente los tipos en TypeScript.

    Tarea a realizar:

    Escribe un script en TypeScript que simule un sensor de contaminación enviando datos. 1. Crea una función enviarDatos() que imprima "📡 Enviando nivel de CO2..." y la hora actual. 2. Usa setInterval para que se ejecute cada 2 segundos. 3. Programa un setTimeout que, tras 7 segundos de ejecución, detenga el intervalo usando clearInterval e imprima "🛑 Sensor desactivado por mantenimiento". 4. Importante: Asegúrate de tipar correctamente las variables que almacenan los timers (Pista: NodeJS.Timeout).

    Aplicación en el Mundo Real:

    El Polling (preguntar periódicamente) es la base de la monitorización de sistemas IoT. Saber detenerlo limpiamente evita fugas de memoria.

    3) Debugging: El Bucle de la Muerte (While true) | Nivel: Fácil

    Objetivo:

    Identificar y corregir patrones de bloqueo de CPU que detienen el Event Loop.

    Setup Inicial:

    Un desarrollador junior intentó crear una función para esperar 3 segundos antes de abrir una barrera de peaje, pero el servidor dejó de responder a otras peticiones mientras esperaba.

    Tarea a realizar:

    Analiza el siguiente código erróneo ("El Bug"). 1. Explica por qué este código bloquea todo el programa (incluyendo el mensaje del timer). 2. Reescribe el código ("El Fix") usando la forma correcta asíncrona para esperar sin bloquear.

    Código con Bug: 

    console.log('1. Solicitud de apertura recibida');

// Timer simulando otra tarea concurrente
setTimeout(() => console.log('⚡ Tarea concurrente (Health Check)'), 500);

// Intento de "espera" de 3 segundos
const fin = Date.now() + 3000;
while (Date.now() < fin) {
    // Esperando activamente...
}

console.log('2. Barrera abierta');

    Aplicación en el Mundo Real:

    En Node.js, nunca debes usar bucles while o for para "hacer tiempo". Eso secuestra la CPU e impide que el Event Loop procese cualquier otra cosa (como el Health Check).

    4) Teoría Visual: Diagrama de Fases | Nivel: Fácil

    Objetivo:

    Visualizar dónde se ejecutan setTimeout y setImmediate dentro del Event Loop.

    Tarea a realizar:

    Basándote en el material proporcionado, dibuja un diagrama simple con Mermaid (graph TD) que muestre el orden de las siguientes fases y callbacks. * Fase Timers (setTimeout) * Fase Poll (Entrada/Salida - I/O) * Fase Check (setImmediate)

    Supón que estamos dentro de un callback de lectura de archivo (fs.readFile). ¿Cuál se ejecutará primero al terminar la lectura: un setImmediate o un setTimeout(..., 0)? Refléjalo en el diagrama o en una nota adjunta.

    Aplicación en el Mundo Real:

    Entender esto es clave para predecir el orden de ejecución cuando necesitas alta precisión en el manejo de respuestas HTTP.

    5) Código: El Dead Man's Switch (Cancelación) | Nivel: Fácil

    Objetivo:

    Aprender a "rearmar" timers para implementar patrones de inactividad (timeout de sesión).

    Tarea a realizar:

    Simula un sistema de seguridad para un guardia nocturno. 1. Crea una variable alarma (tipo NodeJS.Timeout). 2. Crea una función activarAlarma() que imprima "🚨 ¡ALERTA! Guardia no reportado." tras 2 segundos. 3. Crea una función reportarGuardia() que: * Cancele la alarma actual (clearTimeout). * Imprima "👮 Guardia reportado. Reiniciando contador...". * Vuelva a programar la alarma para dentro de 2 segundos. 4. Simula llamadas a reportarGuardia() al segundo 0.5 y al 1.5. Deja que el tiempo corra para ver si la alarma salta finalmente.

    Aplicación en el Mundo Real:

    Este patrón se usa en servidores web para cerrar sesiones de usuarios inactivos (Session Timeout) o detectar microservicios caídos (Heartbeat/Watchdog).

    6) Investigación: El Misterio del Intervalo Acumulado | Nivel: Fácil

    Objetivo:

    Comprender los riesgos de usar setInterval cuando la tarea tarda más que el intervalo.

    Tarea a realizar:

    Imagina que configuras un setInterval cada 1 segundo para procesar imágenes de cámaras de tráfico. Sin embargo, el procesamiento de cada imagen tarda 3 segundos debido a la alta carga de CPU.

    Responde brevemente: 1. ¿Esperará setInterval a que termine el procesamiento anterior para lanzar el siguiente? 2. ¿Qué pasará con la cola de callbacks pendientes tras 1 minuto de funcionamiento? 3. ¿Qué método alternativo (visto en los apuntes) se recomienda para evitar este "atasco"?

    Aplicación en el Mundo Real:

    Este es un error clásico que tumba servidores por "Memory Leak" o saturación de pila cuando la base de datos se ralentiza.

    Ejercicios de Refuerzo

    7) Gestión de Procesos: El Logger Fantasma (unref) | Nivel: Medio

    Objetivo:

    Utilizar unref() para evitar que tareas secundarias impidan el cierre del proceso Node.js.

    Setup Inicial:

    Tienes un script que realiza una migración de base de datos (tarea principal) y luego debería terminar. Sin embargo, has añadido un sistema de métricas que envía el estado de la CPU cada 500ms.

    Tarea a realizar:
    1. Simula la "Migración de DB" con un setTimeout de 2 segundos que imprima "✅ Migración terminada".
    2. Simula el "Reportero de Métricas" con un setInterval de 500ms que imprima "📊 Enviando métricas...".
    3. El Problema: Si ejecutas esto tal cual, el script nunca termina porque el setInterval mantiene el Event Loop vivo.
    4. La Solución: Aplica .unref() al intervalo de métricas para que, en cuanto termine la migración (y no quede nada más pendiente), Node.js cierre el proceso automáticamente, ignorando al reportero de métricas.
    Aplicación en el Mundo Real:

    Esencial para scripts de mantenimiento (CRON jobs), tests automatizados o herramientas CLI que no deben quedarse "colgadas" por culpa de un logger secundario.

    8) Lógica de Prioridad: La Carrera de Eventos | Nivel: Medio

    Objetivo:

    Predecir el orden de ejecución combinando Síncrono, Microtasks (nextTick, Promise) y Macrotasks (setTimeout, setImmediate).

    Tarea a realizar:

    Sin ejecutar el código, analiza el siguiente fragmento y escribe en un papel el orden exacto de los logs (1 al 6). Luego ejecútalo para verificar.

    console.log('A. Inicio');

setImmediate(() => console.log('B. Immediate'));

setTimeout(() => console.log('C. Timeout 0s'), 0);

process.nextTick(() => console.log('D. NextTick'));

Promise.resolve().then(() => console.log('E. Promesa'));

console.log('F. Fin');
    Nota: Supón que estamos en el contexto global (no dentro de I/O), por lo que el orden entre B y C puede variar, pero céntrate en la posición de D y E respecto a A y F.

    Pista: Recuerda: Síncrono > Microtasks (NextTick > Promise) > Macrotasks.

    Aplicación en el Mundo Real:

    Entender esto es vital para depurar condiciones de carrera (Race Conditions) donde los datos no están listos cuando crees que lo están.

    9) Patrones Asíncronos: De Callback a Promesa | Nivel: Medio

    Objetivo:

    Envolver una función antigua basada en callbacks (simulada con setTimeout) en una Promesa moderna.

    Tarea a realizar:

    Tienes una función legacy de un driver de semáforo antiguo: function driverAntiguo(id: number, callback: (error: string|null, estado?: string) => void) Simula esta función usando un setTimeout que tarde 1s y devuelva aleatoriamente un error o "VERDE".

    Tu misión es crear una función moderna async function obtenerEstadoSemaforo(id: number): Promise<string>. * Debe devolver una Promesa. * Si el callback devuelve error, la promesa hace reject. * Si devuelve estado, la promesa hace resolve. * Consúmela con await y un bloque try/catch.

    Aplicación en el Mundo Real:

    En el mundo real, te encontrarás muchas librerías viejas de Node que usan callbacks. Convertirlas a Promesas (Promisify) es el primer paso para escribir código limpio en TypeScript.

    Ejercicios de Ampliación

    10) Arquitectura: Partitioning con setImmediate | Nivel: Alto

    Objetivo:

    Implementar la técnica de Partitioning (troceado) para procesar un array gigante sin bloquear el Event Loop.

    Tarea a realizar:

    UrbanaTech recibe un array con 10 millones de lecturas de sensores (const datos = Array(1e7).fill(1)). Queremos sumar todos esos números. 1. Si haces un for normal, bloquearás el hilo durante varios segundos. Compruébalo midiendo el tiempo antes y después. 2. Crea una función recursiva sumaNoBloqueante(indice, acumulado) que procese los datos en bloques (chunks) de 100.000 elementos. 3. Al terminar un bloque, usa setImmediate para programar el procesamiento del siguiente bloque. Esto permitirá que el Event Loop "respire" y atienda otras peticiones entre bloque y bloque. 4. Muestra el resultado final al terminar.

    Aplicación en el Mundo Real:

    Esencial cuando necesitas hacer cálculos pesados en Node.js (ej: procesar un CSV gigante) sin obligar a usar Worker Threads, manteniendo el servidor "vivo" para otras peticiones HTTP.

    11) Investigación: Event Loop Starvation | Nivel: Alto

    Objetivo:

    Investigar un fenómeno avanzado de seguridad y rendimiento.

    Tarea a realizar:

    Busca información sobre el término "Event Loop Starvation" (inanición del bucle de eventos). Prepara un breve informe (o explicación oral) respondiendo: 1. ¿Qué diferencia hay entre "Bloquear" el loop (con un while) y matarlo de hambre ("Starvation")? 2. ¿Cómo puede un uso abusivo de process.nextTick() causar Starvation, pero setImmediate() no? (Pista: mira el diagrama de microtasks vs macrotasks). 3. Encuentra una métrica o herramienta en Node.js para detectar si el Loop tiene demasiado lag (Pista: módulo perf_hooks o librerías como loopbench).

    Aplicación en el Mundo Real:

    Proteger tu API contra ataques DoS (Denegación de Servicio) involuntarios causados por código recursivo mal diseñado.

    12) Reto Final: Mecanismo de Reintento con Exponential Backoff | Nivel: Alto (Peer Review)

    Objetivo:

    Sintetizar todo lo aprendido (Timers, Promesas, Recursividad) en un algoritmo profesional de tolerancia a fallos.

    Tarea a realizar:

    Diseña una función conectarSensorConReintento() que simule conectar con un sensor inestable. 1. La conexión falla el 70% de las veces (simulado con Math.random). 2. Si falla, debe reintentar automáticamente. 3. El Truco: No debe reintentar inmediatamente. Debe usar Exponential Backoff: * Intento 1: Espera 1s * Intento 2: Espera 2s * Intento 3: Espera 4s * ...hasta un máximo de 5 intentos. 4. Si tras 5 intentos falla, lanza un error definitivo. 5. Usa setTimeout envuelto en promesa para las esperas (wait(ms)).

    Peer Review: Intercambia tu código con un compañero. Revisad: * ¿Usa async/await limpio? * ¿Calcula bien la potencia de 2 para el tiempo? (Math.pow(2, intento)). * ¿Maneja correctamente el error final?

    Aplicación en el Mundo Real:

    Este es el estándar de oro para conectar microservicios (ej: conectar a AWS S3 o una base de datos). Si reintentas "a lo loco" (bucle infinito rápido), tumbarás el servicio destino (DDoS). Esperar exponencialmente permite que el sistema se recupere.
