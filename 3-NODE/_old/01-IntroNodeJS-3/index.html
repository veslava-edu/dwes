    Introducción a Node.js: JavaScript conquista el Servidor

    Introducción

    Bienvenidos al Backend. Hasta ahora, seguramente habéis visto a JavaScript como un león enjaulado, atrapado dentro de las paredes del navegador (Chrome, Firefox, Edge), capaz de hacer cosas increíbles, pero solo dentro de esa "jaula".

    Node.js es la llave que abrió esa jaula.

    Imagina que JavaScript era un piloto de Fórmula 1 (el motor V8) que solo podía conducir en un circuito específico (el navegador). Node.js sacó ese coche a la calle, permitiéndole ir al supermercado, viajar por autopista o transportar mercancías. Técnicamente, sacamos el motor V8 del navegador y le dimos acceso al sistema de archivos, a la red y al sistema operativo.

    Como vimos en módulos anteriores de ASIR o en la introducción a la programación, el servidor es donde ocurre la "magia" que el usuario no ve: bases de datos, autenticación y lógica de negocio. Hoy, JavaScript es el rey de ese castillo.

    1. ¿Qué es Node.js?

    Definición: Node.js

    Node.js no es un lenguaje de programación, ni un framework. Es un entorno de ejecución (runtime) para JavaScript construido sobre el motor V8 de Chrome, diseñado para crear aplicaciones de red escalables y rápidas.

    Historia y Evolución

    En 2009, Ryan Dahl presentó Node.js. Su frustración nació de algo simple: ver una barra de progreso de subida de archivos en Flickr. El servidor tenía que consultar constantemente "¿ya terminaste?", bloqueando recursos. Dahl quería un sistema que dijera: "Avísame cuando termines y mientras tanto haré otra cosa".

    Características Principales

    1. Motor V8: El mismo motor que usa Google Chrome. Compila JS a código máquina nativo a una velocidad endiablada.
    2. Single-Threaded (Monohilo): A diferencia de Java o PHP clásicos, Node.js usa un solo hilo principal.
    3. Non-blocking I/O (Entrada/Salida no bloqueante): No espera a que una base de datos responda para atender al siguiente usuario.
    4. Basado en Eventos: Todo funciona mediante "avisos" (callbacks, promesas, eventos).

    ¿Por qué usarlo en el desarrollo moderno?

    Característica Servidor Clásico (Ej. Apache/PHP antiguo) Node.js
    Concurrencia Crea un hilo (thread) por cada petición. Consume mucha RAM. Un solo hilo gestiona miles de conexiones concurrentes.
    Bloqueo Si la DB tarda, el hilo se duerme y espera. Si la DB tarda, Node atiende a otro cliente mientras espera.
    Lenguaje PHP/Java/Python en back, JS en front. (Context Switching). TypeScript/JS en todo el stack. (Full Stack real).

    Casos de uso Reales

    Gigantes como Netflix (redujo el tiempo de inicio en un 70%), Uber (gestión masiva de datos en tiempo real), LinkedIn y NASA utilizan Node.js para sistemas críticos.

    Ejemplo de Código: Tu primer servidor

    Aunque profundizaremos más adelante, mirad lo sencillo que es levantar un servidor HTTP nativo.

    // holamundo.ts
import http, { IncomingMessage, ServerResponse } from 'http';

const HOSTNAME: string = '127.0.0.1';
const PORT: number = 3000;

const server = http.createServer((req: IncomingMessage, res: ServerResponse) => {
  res.statusCode = 200;
  res.setHeader('Content-Type', 'text/plain');
  res.end('¡Hola desde Node.js con TypeScript!');
});

server.listen(PORT, HOSTNAME, () => {
  console.log(`🚀 Servidor corriendo en http://${HOSTNAME}:${PORT}/`);
});

    TypeScript y Node

    Node.js no entiende TypeScript nativamente (aún). Siempre necesitaremos un paso de "transpilación" a JavaScript o usar ejecutores como ts-node o las nuevas flags de Node 22+.

    🧠 Reflexión

    1. Si Node.js es "Single Threaded", ¿cómo crees que puede atender a 10,000 usuarios a la vez sin colapsar si uno de ellos pide un cálculo matemático muy pesado?
    2. ¿Qué ventaja tiene para una empresa contratar a un desarrollador que sepa TypeScript para el Frontend y el Backend?

    2. Arquitectura Interna de Node.js

    Aquí es donde separamos a los aficionados de los ingenieros. Entender esto es vital para no bloquear vuestro servidor.

    El Corazón: El Event Loop (Bucle de Eventos)

    Imagina un camarero (Node.js) en un restaurante muy concurrido.

    • Modelo Clásico (Apache): Contratas un camarero por cada mesa. Si el cliente tarda en decidir, el camarero espera de pie sin hacer nada. Es caro y consume recursos.
    • Modelo Node.js: Hay un solo camarero para todo el restaurante. Toma nota en la mesa 1, pasa el pedido a cocina (Sistema Operativo/Libuv), va a la mesa 2, sirve una bebida, vuelve a cocina a por el plato de la mesa 1... Nunca se para.

    EL -->|Ejecuta Callback| JS

    Componentes Clave

    1. Call Stack (Pila de llamadas): Donde se ejecuta tu código TypeScript síncrono. LIFO (Last In, First Out).
    2. Libuv: Es el "ayudante de cocina". Una librería en C++ que le da a Node.js acceso al sistema operativo y gestiona el Thread Pool para operaciones pesadas (ficheros, criptografía).
    3. Colas (Queues):
    4. Macrotasks: setTimeout, setInterval, I/O.
    5. Microtasks: Promise.then, process.nextTick. Tienen prioridad VIP.

    ¿Cómo se ejecuta el código? (El orden importa)

    console.log('1. Inicio del script'); // Síncrono -> Call Stack

setTimeout(() => {
  console.log('4. Timeout (Macrotask)'); // Asíncrono -> Macrotask Queue
}, 0);

Promise.resolve().then(() => {
  console.log('3. Promesa (Microtask)'); // Asíncrono -> Microtask Queue (VIP)
});

console.log('2. Fin del script'); // Síncrono -> Call Stack

    Salida Real: 1, 2, 3, 4. Aunque el timeout sea 0ms, las promesas (Microtasks) siempre se cuelan antes que los timers (Macrotasks) una vez que el Call Stack está vacío.

    El peligro del bloqueo

    Node.js es rapidísimo gestionando I/O (bases de datos, red), pero es terrible con cálculos CPU intensivos en el hilo principal. Si pones un bucle while(true) o calculas Fibonacci de 1000 en el hilo principal, bloqueas al "camarero" y nadie más recibe su comida.

    🧠 Reflexión

    1. ¿Por qué setTimeout(() => {}, 0) no se ejecuta inmediatamente?
    2. Investiga: ¿Qué son los "Worker Threads" en Node.js y cómo solucionan el problema de las tareas intensivas de CPU?

    3. Instalación y configuración inicial

    Como profesionales, no descargamos el instalador .msi o .pkg y le damos a "Siguiente, Siguiente". Eso genera problemas de permisos y versiones en el futuro.

    La regla de oro: Usa un Gestor de Versiones (NVM)

    Usaremos NVM (Node Version Manager). Te permite tener varias versiones de Node instaladas (ej. la 18 para un proyecto legacy y la 22 para uno nuevo) y cambiar entre ellas con un comando.

    Pasos para la instalación profesional:

    1. Instalar NVM:
    2. Windows: Descarga nvm-windows desde GitHub.

    3. Linux/Mac: curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash

    4. Instalar Node.js: 

      nvm install --lts    # Instala la última versión Long Term Support (Estable)
nvm use --lts        # Activa esa versión

    5. Verificación: 

      node -v   # Ejemplo: v20.11.0
npm -v    # Ejemplo: 10.2.4

    Tu primer proyecto ("Hola Mundo" profesional)

    En este ciclo usaremos Visual Studio Code.

    1. Crea una carpeta curso-node.
    2. Abre la terminal en esa carpeta.
    3. Inicializa el proyecto: 
      npm init -y

    Esto crea el DNI de tu proyecto: el package.json.

    Ejecución de Scripts: REPL vs Archivos

    • REPL (Read-Eval-Print Loop): Si escribes node en la terminal, entras en modo interactivo. Útil para probar cosas rápidas.
    • Archivos: Lo normal es crear un fichero y ejecutarlo.
    // index.ts
const saludo: string = "Bienvenido al Backend";
console.log(saludo.toUpperCase());

    Para ejecutar TypeScript directamente sin compilar manualmente cada vez, usaremos ts-node (solo en desarrollo):

    npx ts-node index.ts

    Tipos de Dependencias (¡Crucial!)

    • dependencies (npm install paq): Librerías que tu código necesita para funcionar en producción (ej. Express, React, Mysql).
    • devDependencies (npm install -D paq): Herramientas que solo usas tú mientras programas (ej. TypeScript, ESLint, Tests). No se suben al servidor de producción.

    El peso de node_modules

    La carpeta node_modules es donde se guardan las librerías. NUNCA se sube a GitHub/GitLab. Es el objeto más pesado del universo conocido. Asegúrate de tener un fichero .gitignore que incluya node_modules.

    npx: El ejecutor de paquetes

    A veces quieres usar una herramienta sin instalarla globalmente en tu PC.

    • Antes: npm install -g create-react-app (llena tu disco de basura).
    • Ahora: npx create-react-app mi-app (baja, ejecuta y borra).

    🧠 Reflexión

    1. Si borras la carpeta node_modules por error, ¿cómo recuperas tu proyecto? (Pista: package.json y package-lock.json).
    2. ¿Qué pasa si instalamos typescript en dependencies en lugar de devDependencies?

    5. Otras utilidades recomendadas

    Para programar como un profesional, necesitamos herramientas que mantengan nuestro código limpio y estandarizado. "Si el código huele mal, refactoriza".

    ESLint (El policía del código)

    Analiza tu código estáticamente para encontrar errores y patrones no deseados antes de que ejecutes nada.

    • Instalación: 

      npm init @eslint/config

    • Te hará preguntas: ¿Usas TS? Sí. ¿Estilo? Airbnb/Standard.

    • Resultado: Te avisa si dejas variables sin usar, si usas var en lugar de let/const, etc.

    Prettier (El maquillador)

    Olvídate de debatir si poner espacios o tabulaciones, o si las llaves van en la misma línea. Prettier formatea el código automáticamente al guardar.

    • Instalación: 

      npm install -D prettier

    • Integración: Se suele usar junto a ESLint para que no se peleen entre ellos.
