    Tema 3: Automatización en el Desarrollo con Nodemon

    Introducción: El Asistente Incansable

    Imagina que estás rodando una película. Eres el director. Cada vez que un actor se equivoca en una línea o decides cambiar un diálogo del guion, tienes que despedir a todo el equipo, apagar las cámaras, desmontar el set, volver a montarlo todo, recontratar a la gente y gritar "¡Acción!" de nuevo.

    Suena ridículo y agotador, ¿verdad? Pues eso es exactamente lo que ocurre cuando desarrollas en Node.js "a pelo". Cada vez que guardas un cambio en tu código (Ctrl+S), tienes que ir a la terminal, matar el proceso (Ctrl+C) y volver a arrancarlo. Cientos de veces al día.

    Nodemon es tu asistente de dirección incansable. Es ese miembro del equipo que vigila el guion con ojos de halcón. En el nanosegundo en que detecta un cambio en el texto, chasquea los dedos y reinicia la escena automáticamente sin que tú tengas que levantar la vista del monitor.

    En este tema, vamos a aprender a dejar de pelear con la terminal y dejar que las herramientas trabajen por nosotros.

    1. ¿Qué es Nodemon y para qué se utiliza?

    Concepto y Propósito

    Nodemon es una utilidad de línea de comandos que monitorea los archivos de tu proyecto. Su única misión en la vida es detectar cambios en tus ficheros de código fuente y reiniciar automáticamente el servidor o el proceso de Node.js.

    Definición: Hot Reloading vs Live Reloading

    Aunque a veces se confunden, Nodemon hace un reinicio de proceso (Process Restart). Cierra la aplicación vieja y arranca una nueva. No es Hot Module Replacement (HMR) como en React o Vue, donde se cambia el módulo sin perder el estado de la memoria, pero el efecto práctico para el backend es tener tu código fresco al instante.

    El problema que resuelve

    Node.js, por diseño, carga todos los archivos en memoria al arrancar. Si cambias el archivo en el disco duro, Node.js no se entera porque sigue usando la versión que leyó y guardó en la memoria RAM al inicio.

    Sin Nodemon: 1. Escribes código. 2. Guardas. 3. Vas a la terminal -> Ctrl+C (Detener). 4. Flecha Arriba -> Enter (Arrancar). 5. Pruebas.

    Con Nodemon: 1. Escribes código. 2. Guardas. 3. Magia (Nodemon reinicia solo). 4. Pruebas.

    Ejemplos Prácticos

    Ejemplo 1.1: El flujo de trabajo clásico (Problemático)

    Imagina un servidor HTTP básico. Si cambias el mensaje de "Hola Mundo" a "Hola FP", sin Nodemon, el navegador seguirá mostrando "Hola Mundo" hasta que reinicies manualmente.

    // server.ts
import http from 'http';

const server = http.createServer((req, res) => {
    // Si cambio esto a 'Hola FP', Node no se entera
    res.end('Hola Mundo'); 
});

server.listen(3000);

    Ejemplo 2.1: Diferencia en la terminal

    Visualmente, Nodemon te informa de lo que hace.

    Ejecución estándar: 

    $ node dist/index.js
# (El cursor se queda esperando, si cambias algo, no pasa nada)

    Ejecución con Nodemon: 

    $ nodemon dist/index.js
[nodemon] 2.0.22
[nodemon] to restart at any time, enter `rs`
[nodemon] watching path(s): *.*
[nodemon] watching extensions: js,mjs,json
[nodemon] starting `node dist/index.js`
# (Si guardas un archivo...)
[nodemon] restarting due to changes...
[nodemon] starting `node dist/index.js`

    Comparativa: Node vs Nodemon

    Característica Node.js (Nativo) Nodemon
    Persistencia Carga una vez y mantiene en memoria. Vigila y recarga ante cambios.
    Uso ideal Producción (estable, sin cambios). Desarrollo (cambios constantes).
    Consumo recursos Bajo (solo la app). Ligeramente superior (app + watcher).
    Feedback Solo logs de la app. Logs de la app + Estado del sistema.

    Diagrama de Flujo del Proceso

    flowchart LR
    A[Desarrollador guarda archivo] -->|Evento FS| B(Nodemon Watcher)
    B -->|Detecta cambio| C{¿Es extensión válida?}
    C -- No --> D[Ignorar]
    C -- Sí --> E[Matar proceso actual]
    E --> F[Arrancar nuevo proceso]
    F --> G[Servidor actualizado]

    🧠 Reflexión

    1. ¿Por qué crees que no deberíamos usar Nodemon en un entorno de producción real?
    2. Si Node.js carga los archivos en memoria, ¿qué ventaja tiene esto para el rendimiento frente a lenguajes como PHP que leen el disco en cada petición?
    3. ¿Qué pasaría si Nodemon entra en un bucle infinito de reinicios (ej: tu código modifica un archivo que Nodemon está vigilando)?


    2. Instalación y primeros pasos

    Para usar Nodemon, necesitamos instalarlo a través de NPM (Node Package Manager). Tenemos dos caminos, y como profesionales, debemos saber cuál elegir.

    Instalación Global vs Local

    Existe un debate eterno, pero en entornos profesionales la respuesta suele ser una: Local.

    • Global (-g): Se instala en tu sistema operativo. Puedes usar nodemon en cualquier carpeta. Útil para scripts rápidos, peligroso para equipos (¿qué pasa si mi compañero tiene la v1 y yo la v3?).
    • Local (--save-dev): Se instala dentro de la carpeta node_modules del proyecto. Todos usan la misma versión. Esta es la recomendada.

    Comandos de instalación

    Ejemplo 2.1: Instalación Global (Para tu ordenador personal)

    npm install -g nodemon
# Verificación
nodemon --version

    Ejemplo 2.2: Instalación Local (Entorno Profesional)

    npm install --save-dev nodemon
# O su versión corta
npm i -D nodemon

    Consejo Pro: npx

    Si lo instalas localmente, no podrás escribir nodemon en la terminal directamente (te dirá "comando no encontrado"). Tendrás que usar npx nodemon o configurarlo en los scripts de NPM (veremos esto en el punto 4).

    Diagrama de Decisión de Instalación

    graph TD
    A[¿Cómo instalo Nodemon?] --> B{¿Es un proyecto compartido?}
    B -- Sí (Equipo/Git) --> C[Instalación Local]
    C --> D[npm install --save-dev nodemon]
    B -- No (Script rápido/Prueba) --> E{¿Lo usarás mucho?}
    E -- Sí --> F[Instalación Global]
    F --> G[npm install -g nodemon]
    E -- No --> H[Uso temporal con npx]
    H --> I[npx nodemon script.js]

    1. Si clonas un repositorio de GitHub que tiene Nodemon en devDependencies, ¿qué comando debes ejecutar para tenerlo disponible?
    2. ¿Por qué es importante que Nodemon no se instale en el servidor de producción?
    3. Investiga: ¿Qué ocurre si intentas ejecutar nodemon en una terminal de Windows Powershell y te da un error de "Políticas de ejecución"?


    3. Uso básico de Nodemon

    Una vez instalado, usarlo es tan sencillo como sustituir la palabra node por nodemon. Sin embargo, al usar TypeScript, tenemos una pequeña capa extra de complejidad.

    Ejecución básica

    Nodemon por defecto busca un archivo index.js, main.js o lo que defina tu package.json.

    Ejemplo 3.1: Ejecución directa de JavaScript

    Si ya has compilado tu TypeScript a JavaScript (en la carpeta dist o build): 

    npx nodemon dist/index.js

    Ejemplo 3.2: Ejecución con TypeScript (vía ts-node)

    Nodemon no entiende TypeScript nativamente, necesita un intérprete como ts-node. 

    # Opción A: Ejecutando ts-node a través de nodemon
npx nodemon --exec ts-node src/index.ts

# Opción B: Si tienes ts-node instalado, nodemon suele ser listo
# y detectarlo si configuras el archivo json (ver punto 5)

    Ejemplo 3.3: Reinicio Manual

    A veces Nodemon se "atonta" o quieres reiniciar sin guardar cambios (ej: para limpiar caché o reconectar BBDD). * Estando en la terminal donde corre nodemon, escribe rs y pulsa Enter. * Nodemon forzará el reinicio.

    Archivos observados (Watching)

    Por defecto, Nodemon vigila el directorio actual y subdirectorios, buscando extensiones .js, .mjs, .json. Si trabajamos con TypeScript, querremos que vigile .ts.

    Diagrama de Secuencia: Ciclo de vida básico

    sequenceDiagram
    participant Dev as Desarrollador
    participant NM as Nodemon
    participant App as Tu Aplicación (Node)

    Dev->>NM: npx nodemon index.js
    NM->>App: Inicia proceso (PID 1234)
    App-->>Dev: "Servidor escuchando en puerto 3000"

    Note over Dev, App: Pasa el tiempo...

    Dev->>Dev: Modifica archivo.js
    Dev->>NM: Guardar cambios (Evento OS)
    NM->>NM: Detecta cambio
    NM->>App: SIGUSR2 / Kill PID 1234
    App-->>NM: Proceso termina
    NM->>App: Inicia nuevo proceso (PID 1235)
    App-->>Dev: "Servidor escuchando en puerto 3000"

    Tabla: Comandos CLI útiles

    Flag / Comando Descripción Ejemplo
    --watch Vigila solo carpetas/archivos específicos. nodemon --watch src/ app.js
    --ext Define qué extensiones disparan el reinicio. nodemon --ext ts,json,html
    --delay Espera X segundos tras un cambio antes de reiniciar. nodemon --delay 2.5
    --exec Ejecuta un binario que no sea 'node'. nodemon --exec "python3"

    🧠 Reflexión

    1. Estás trabajando con TypeScript. Si ejecutas nodemon dist/index.js, ¿debes vigilar la carpeta src o la carpeta dist? ¿Por qué?
    2. ¿Qué utilidad tiene el flag --delay? Piensa en cuando haces "Guardar todo" en 5 archivos a la vez.
    3. Si tu aplicación escribe logs en un archivo app.log cada vez que recibe una petición, ¿qué problema podrías tener con Nodemon?


    4. Integración con NPM y package.json

    En el mundo profesional, rara vez escribimos comandos largos en la terminal. Usamos los scripts de NPM. Esto abstrae la complejidad: un desarrollador nuevo solo necesita saber npm run dev y no le importa si por debajo usas nodemon, ts-node, docker o magia negra.

    Creando Scripts Profesionales

    El archivo package.json es el centro de mando.

    Ejemplo 4.1: Configuración Estándar para JS

    {
  "name": "mi-api-daw",
  "scripts": {
    "start": "node dist/index.js",       // Producción
    "dev": "nodemon src/index.js"        // Desarrollo
  },
  "devDependencies": {
    "nodemon": "^3.0.1"
  }
}

    Ejemplo 4.2: Configuración para TypeScript (con ts-node)

    {
  "scripts": {
    "build": "tsc",
    "start": "node dist/index.js",
    // Nodemon llamará a ts-node para ejecutar el TS directamente
    "dev": "nodemon src/index.ts" 
  }
}
    Nota: Para que esto funcione fluido, a veces requerimos configurar el nodemon.json que veremos luego.

    Ejemplo 4.3: Scripts con parámetros

    A veces queremos pasar variables de entorno. 

    {
  "scripts": {
    "dev": "PORT=8080 nodemon src/index.ts"
  }
}

    Ventajas de no instalarlo globalmente

    Al usar npm run dev, NPM busca automáticamente en la carpeta ./node_modules/.bin/. Esto significa que no necesitas tener nodemon instalado en tu sistema, solo en el proyecto. Esto garantiza que todos los desarrolladores usen la misma versión de Nodemon definida en el package.json.

    5. Configuración de Nodemon (nodemon.json)

    Llenar el package.json de flags (--watch, --ext, --exec) ensucia mucho. La buena práctica es crear un archivo de configuración dedicado: nodemon.json en la raíz del proyecto. Nodemon lo leerá automáticamente.

    Propiedades Clave

    • watch: ¿Qué carpetas vigilo? (Normalmente src).
    • ext: ¿Qué extensiones reinician el server? (ts, js, json, env).
    • ignore: ¿Qué ignoro? (IMPORTANTE: ignorar tests, logs, git).
    • exec: ¿Cómo ejecuto el fichero? (Clave para TypeScript).

    Ejemplo 5.1: Configuración Básica

    // nodemon.json
{
  "watch": ["src"],
  "ext": "js,json",
  "ignore": ["src/**/*.spec.js"],
  "exec": "node ./src/index.js"
}

    Ejemplo 5.2: Configuración Avanzada para TypeScript

    Esta es la configuración "pata negra" para un proyecto DAW con TypeScript.

    // nodemon.json
{
  "watch": ["src"],
  "ext": "ts,json",
  "ignore": ["src/**/*.test.ts", "node_modules"],
  "exec": "ts-node ./src/index.ts"
}
    Con esto, en el package.json solo pones "dev": "nodemon" y él sabe qué hacer.

    Ejemplo 5.3: Múltiples mapas de ejecución

    Puedes decirle a Nodemon cómo comportarse según la extensión del archivo que ha cambiado.

    {
  "execMap": {
    "ts": "ts-node",
    "js": "node"
  }
}

    Diagrama de Clases (Configuración)

    classDiagram
    class NodemonConfig {
        +Array~String~ watch
        +String ext
        +Array~String~ ignore
        +String exec
        +Object env
        +Boolean legacyWatch
    }

    class ProyectoTS {

    Tabla: Propiedades vs Flags CLI

    ext --ext Lista de extensiones separadas por coma.
    env N/A (inline vars) Variables de entorno inyectadas.

    2. ¿Qué sucede si pones node_modules dentro de watch? (Spoiler: Tu ordenador despegará como un avión).
    3. ¿Cómo configurarías nodemon.json para que también reinicie el servidor si modificas el archivo .env?


    6. Uso de Nodemon en proyectos reales

    Vamos a aterrizar esto en escenarios que os vais a encontrar en las prácticas de empresa o en el proyecto final.

    Escenario A: Express + TypeScript

    Este es el estándar moderno en Node.js. Usamos ts-node para ejecución en memoria durante el desarrollo (es lento en producción, pero genial en dev).

    Ejemplo 6.1: Estructura de carpetas

    /mi-proyecto
  /src
    - app.ts (Express)
    - routes.ts
  - package.json
  - nodemon.json
  - tsconfig.json
    Nodemon vigila src. Cuando guardas routes.ts, ts-node recompila al vuelo en memoria y Express reinicia.

    Escenario B: Entornos con Docker

    Aquí viene un problema clásico. Docker corre en un contenedor (Linux virtualizado). Nodemon dentro de Docker a veces no recibe el evento de archivo guardado desde Windows/Mac.

    El problema del Polling en Docker

    Los sistemas de archivos virtuales a veces no propagan los eventos de cambio. Si usas Docker y Nodemon no reinicia, necesitas activar el modo Legacy Watch (Polling).

    Ejemplo 6.2: Configuración para Docker (Legacy Watch)

    Esto fuerza a Nodemon a "preguntar" cada X milisegundos si el archivo cambió, en lugar de esperar a que le avisen. Consume más CPU, pero es infalible en Docker.

    // nodemon.json para Docker
{
  "legacyWatch": true,
  "pollingInterval": 1000 
}
    O vía comando: nodemon -L

    Escenario C: Depuración (Debugging)

    Si quieres usar el debugger de VS Code o Chrome DevTools, necesitas pasarle el flag de inspección a Node, no a Nodemon.

    Ejemplo 6.3: Debugging

    nodemon --inspect src/index.js
    Esto abre el puerto 9229 para que puedas poner puntos de ruptura (breakpoints).

    Diagrama: Nodemon + Docker

    graph TD
    subgraph Host[Tu Ordenador]
        Code[Código Fuente]
    end

    subgraph Container[Contenedor Docker]
        Volume[Volumen Montado]
        NM[Nodemon -L]

    end

    Code -- Sincronización de Volumen --> Volume
    NM -- Polling (Pregunta cte.) --> Volume
    Volume -- Cambio detectado --> NM
    NM -- Reinicio --> Node

    Tabla: Tecnologías complementarias

    Tecnología Rol Interacción con Nodemon
    Express Framework Web Nodemon reinicia el servidor HTTP.
    TypeScript Lenguaje Requiere ts-node o paso de compilación previo.
    Docker Contenedor Requiere -L (legacy watch) a menudo.
    Dotenv Variables Env Conviene añadir .env a la lista de ext.

    🧠 Reflexión

    1. En un proyecto con Docker, ¿por qué preferimos montar un volumen con el código en lugar de copiarlo al construir la imagen durante la fase de desarrollo?
    2. Si usas Babel en lugar de TypeScript, ¿cambiaría la propiedad exec de tu nodemon.json?
    3. ¿Qué diferencia hay entre nodemon --inspect y node --inspect?


    7. Opciones avanzadas y rendimiento

    Cuando el proyecto crece, Nodemon puede volverse un cuello de botella si no se configura bien.

    Control de Reinicios y Señales

    Cuando Nodemon reinicia tu app, le envía una señal (normalmente SIGUSR2). Tu aplicación puede escuchar esta señal para cerrar conexiones a base de datos limpiamente antes de morir.

    Ejemplo 7.1: Cierre limpio (Graceful Shutdown)

    // En tu código Express
process.once('SIGUSR2', function () {
  server.close(function () {
    process.kill(process.pid, 'SIGUSR2');
  });
});

    Eventos de Nodemon

    Puedes ejecutar comandos cuando Nodemon detecta estados. Útil para limpiar consola o enviar notificaciones.

    Ejemplo 7.2: Limpiar consola al reiniciar

    {
  "events": {
    "restart": "cls || clear", // Limpia terminal windows/linux
    "crash": "echo '¡LA HEMOS LIADO!'"
  }
}

    Rendimiento: Debounce (Delay)

    Si haces "Guardar Todo" en VS Code, se guardan 10 archivos en milisegundos. Nodemon podría intentar reiniciar 10 veces seguidas. El delay agrupa esos cambios.

    Ejemplo 7.3: Retraso

    {
  "delay": 1500 // Espera 1.5s desde el último cambio antes de reiniciar
}

    8. Buenas prácticas y alternativas

    Para cerrar, vamos a ver cómo ser unos profesionales. Nodemon es el rey, pero hay nuevos aspirantes al trono.

    Buenas Prácticas

    1. Scope preciso: Usa watch solo en las carpetas necesarias (src). No vigiles todo el proyecto.
    2. Ignora lo irrelevante: tests, docs, uploads, git.
    3. Configuración en JSON: Mantén el package.json limpio.
    4. Solo Dev: Asegúrate de que es devDependency.

    Alternativas Modernas

    Node.js Nativo (--watch)

    Desde la versión 18/19, Node.js incluye un watcher nativo. Es más rápido y no requiere dependencias. 

    node --watch index.js
    Limitación: Aún está verde y tiene menos opciones de configuración que Nodemon.

    TSX (La opción veloz para TypeScript)

    Si usas TypeScript, ts-node puede ser lento. tsx (basado en esbuild) es increíblemente rápido y tiene watch mode. 

    npx tsx watch src/index.ts

    PM2 (Process Manager 2)

    PM2 es para producción. También tiene modo watch, pero su función es mantener la app viva si crashea y balancear carga. * Desarrollo: Nodemon / TSX. * Producción: PM2 / Kubernetes.

    Herramienta Entorno Soporte TS Configuración Velocidad
    Nodemon Desarrollo Vía plugin Alta Media
    Node --watch Desarrollo No nativo Baja Alta
    TSX Desarrollo Nativo Media Muy Alta
    PM2 Producción Vía plugin Muy Alta Alta

    Ejemplo 8.1: Migrando a Node --watch (El futuro)

    // package.json moderno (Node v20+)
{
  "scripts": {
    "dev": "node --watch --loader ts-node/esm src/index.ts"
  }
}
