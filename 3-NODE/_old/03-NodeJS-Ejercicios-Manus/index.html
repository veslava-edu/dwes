    Ejercicios Prácticos: Fundamentos de Node.js y TypeScript

    Narrativa del Proyecto: Nexus CLI Tools

    En Innovatech, la eficiencia operativa es clave. Se ha decidido crear un conjunto de utilidades de línea de comandos (CLI Tools) en Node.js y TypeScript, llamado Nexus CLI Tools, para que los equipos de DevOps y SysAdmin puedan realizar diagnósticos rápidos del servidor, gestionar configuraciones y manipular rutas de archivos de forma segura.

    Estos ejercicios te guiarán a través de la implementación de los módulos fundamentales de esta suite, asegurando que comprendas cómo Node.js interactúa con el sistema operativo y cómo manejar la configuración de forma profesional.

    1) Diagnóstico de Entorno: ¿Servidor o Navegador? | Nivel: Fácil

    1) Diagnóstico de Entorno: ¿Servidor o Navegador? | Nivel: Fácil

    Objetivo:

    Validar la comprensión de las diferencias fundamentales entre el entorno de ejecución del navegador y el de Node.js, identificando las APIs exclusivas de cada uno.

    Setup Inicial:

    No se requiere configuración inicial.

    Tarea a realizar:

    Analiza los siguientes fragmentos de código y determina si se ejecutarían correctamente en Node.js, en el navegador, o en ambos. Justifica tu respuesta basándote en la disponibilidad de los objetos globales (window, process, document, fs).

    Fragmento de Código ¿Node.js? ¿Navegador? Justificación
    console.log(window.location.href);
    console.log(process.pid);
    import { readFileSync } from 'fs';
    document.getElementById('app').innerHTML = 'Hola';
    setTimeout(() => {}, 1000);
    Aplicación en el Mundo Real:

    Saber dónde se ejecutará tu código es el primer paso para evitar errores de ReferenceError. Un desarrollador profesional debe saber qué APIs están disponibles en cada entorno para elegir las librerías correctas.

    VER Solución.
    Fragmento de Código ¿Node.js? ¿Navegador? Justificación
    console.log(window.location.href); ❌ No ✅ Sí window es un objeto global del navegador, no existe en Node.js.
    console.log(process.pid); ✅ Sí ❌ No process es un objeto global de Node.js que da acceso a información del proceso.
    import { readFileSync } from 'fs'; ✅ Sí ❌ No El módulo fs (File System) permite acceso al disco, lo cual está prohibido en el navegador por seguridad.
    document.getElementById('app').innerHTML = 'Hola'; ❌ No ✅ Sí document y el DOM son APIs del navegador.
    setTimeout(() => {}, 1000); ✅ Sí ✅ Sí Es una API estándar que existe en ambos entornos (aunque su implementación interna difiere).

    2) Utilidad de Diagnóstico: console.table | Nivel: Fácil

    2) Utilidad de Diagnóstico: console.table | Nivel: Fácil

    Objetivo:

    Aprender a usar los métodos avanzados del módulo console para presentar datos estructurados de forma legible en la terminal.

    Setup Inicial:

    Crea un archivo llamado diagnostico.ts.

    Tarea a realizar:

    El equipo de SysAdmin necesita una herramienta que muestre el estado de las últimas 3 peticiones fallidas a la API de Nexus.

    1. Define un array de objetos llamado fallos con la siguiente estructura: 
      interface Fallo {
  id: number;
  endpoint: string;
  status: number;
  timestamp: string;
}

const fallos: Fallo[] = [
  { id: 101, endpoint: '/api/users/1', status: 404, timestamp: '2024-01-01T10:00:00Z' },
  { id: 102, endpoint: '/api/auth/login', status: 500, timestamp: '2024-01-01T10:05:00Z' },
  { id: 103, endpoint: '/api/data/report', status: 401, timestamp: '2024-01-01T10:15:00Z' },
];
    2. Utiliza el método console.table para imprimir este array en la terminal de Node.js de forma que los SysAdmins puedan leerlo fácilmente.
    3. Añade una línea de código que mida el tiempo que tarda en ejecutarse la impresión de la tabla usando console.time y console.timeEnd.
    Aplicación en el Mundo Real:

    console.table es invaluable para la depuración y el logging en entornos de servidor, permitiendo visualizar grandes cantidades de datos de forma ordenada sin necesidad de herramientas externas.

    VER Solución. 
    // diagnostico.ts
interface Fallo {
  id: number;
  endpoint: string;
  status: number;
  timestamp: string;
}

const fallos: Fallo[] = [
  { id: 101, endpoint: '/api/users/1', status: 404, timestamp: '2024-01-01T10:00:00Z' },
  { id: 102, endpoint: '/api/auth/login', status: 500, timestamp: '2024-01-01T10:05:00Z' },
  { id: 103, endpoint: '/api/data/report', status: 401, timestamp: '2024-01-01T10:15:00Z' },
];

console.time('Tiempo de Diagnóstico');
console.log('--- Últimos Fallos de API ---');
console.table(fallos);
console.timeEnd('Tiempo de Diagnóstico');

    3) Configuración Segura: Variables de Entorno | Nivel: Fácil

    3) Configuración Segura: Variables de Entorno | Nivel: Fácil

    Objetivo:

    Aprender a acceder a las variables de entorno y a los argumentos de línea de comandos a través del objeto global process.

    Setup Inicial:

    Crea un archivo llamado config-server.ts.

    Tarea a realizar:

    La utilidad Nexus CLI Tools debe configurarse mediante variables de entorno para el puerto y el modo de operación.

    1. En config-server.ts, usa process.env para obtener el puerto (PORT) y el modo (NODE_ENV). Si PORT no está definido, usa 3000 por defecto. Si NODE_ENV no está definido, usa 'development'.
    2. Usa process.argv para detectar si el usuario ha pasado el argumento --verbose.
    3. Imprime un mensaje de configuración, y si el modo es 'development' O si se pasó el argumento --verbose, imprime también el ID del proceso (process.pid).

    Ejecución esperada: 

    $ PORT=8080 NODE_ENV=production npx ts-node config-server.ts
# Output: Servidor configurado: Puerto 8080, Modo production.

$ npx ts-node config-server.ts --verbose
# Output: Servidor configurado: Puerto 3000, Modo development.
# Output: [Verbose] PID: 12345

    Aplicación en el Mundo Real:

    El uso de process.env es la práctica estándar de seguridad para inyectar credenciales y configuraciones sensibles en aplicaciones de servidor, siguiendo el principio de "Configuración de 12 Factores".

    VER Solución. 
    // config-server.ts
// Acceso a variables de entorno
const puerto: number = parseInt(process.env.PORT || '3000', 10);
const modo: string = process.env.NODE_ENV || 'development';

// Acceso a argumentos de línea de comandos
const args: string[] = process.argv;
const isVerbose: boolean = args.includes('--verbose');

console.log(`Servidor configurado: Puerto ${puerto}, Modo ${modo}.`);

if (modo === 'development' || isVerbose) {
    console.log(`[Verbose] PID: ${process.pid}`);
    console.log(`[Verbose] Directorio de trabajo: ${process.cwd()}`);
}

    4) Gestión de Rutas: path.join | Nivel: Fácil

    4) Gestión de Rutas: path.join | Nivel: Fácil

    Objetivo:

    Utilizar el módulo path para construir rutas de archivos de forma segura y compatible con diferentes sistemas operativos (Windows, Linux, Mac).

    Setup Inicial:

    Crea un archivo llamado ruta-segura.ts.

    Tarea a realizar:

    El módulo de logs de Nexus CLI Tools necesita construir la ruta completa a un archivo de log diario.

    1. Importa el módulo path.
    2. Define las siguientes variables:
      • directorioBase: 'var/log/nexus'
      • fecha: '2024-01-01'
      • nombreArchivo: 'api-errors.log'
    3. Usa path.join() para construir la ruta completa al archivo de log: var/log/nexus/2024-01-01/api-errors.log.
    4. Imprime la ruta resultante.
    5. Usa path.resolve() para obtener la ruta absoluta de este archivo, asumiendo que el script se ejecuta desde la raíz del proyecto. Imprime la ruta absoluta.
    Aplicación en el Mundo Real:

    path.join es fundamental para evitar errores de ruta en entornos de producción donde el sistema operativo del servidor puede ser diferente al de desarrollo.

    VER Solución. 
    // ruta-segura.ts
import path from 'path';

const directorioBase: string = 'var/log/nexus';
const fecha: string = '2024-01-01';
const nombreArchivo: string = 'api-errors.log';

// 1. Construir la ruta relativa usando path.join
const rutaRelativa: string = path.join(directorioBase, fecha, nombreArchivo);
console.log(`Ruta Relativa (Cross-platform): ${rutaRelativa}`);

// 2. Obtener la ruta absoluta
const rutaAbsoluta: string = path.resolve(rutaRelativa);
console.log(`Ruta Absoluta: ${rutaAbsoluta}`);

/*
Ejemplo de salida en Linux:
Ruta Relativa (Cross-platform): var/log/nexus/2024-01-01/api-errors.log
Ruta Absoluta: /home/ubuntu/var/log/nexus/2024-01-01/api-errors.log
*/

    5) Monitorización de Recursos: Módulo os | Nivel: Fácil

    5) Monitorización de Recursos: Módulo os | Nivel: Fácil

    Objetivo:

    Utilizar el módulo os para obtener información básica sobre el hardware y el sistema operativo del servidor.

    Setup Inicial:

    Crea un archivo llamado monitor.ts.

    Tarea a realizar:

    Crea una función llamada reporteSistema() que imprima la siguiente información usando el módulo os:

    1. El nombre de la plataforma (ej: linux, win32).
    2. La arquitectura del CPU (ej: x64).
    3. El número total de núcleos de CPU disponibles.
    4. La cantidad de memoria libre en megabytes (MB).

    Pista: La memoria se reporta en bytes. Debes dividir el resultado de os.freemem() dos veces por 1024 para obtener MB.

    Aplicación en el Mundo Real:

    Los módulos os y process son la base para cualquier herramienta de monitorización de servidores, permitiendo a los desarrolladores tomar decisiones sobre el balanceo de carga y la optimización de recursos.

    VER Solución. 
    // monitor.ts
import * as os from 'os';

function reporteSistema(): void {
    console.log('--- Reporte Rápido del Sistema ---');

    // 1. Plataforma
    console.log(`Plataforma: ${os.platform()}`);

    // 2. Arquitectura
    console.log(`Arquitectura: ${os.arch()}`);

    // 3. Núcleos de CPU
    const nucleos: number = os.cpus().length;
    console.log(`Núcleos de CPU: ${nucleos}`);

    // 4. Memoria Libre (en MB)
    const memoriaLibreBytes: number = os.freemem();
    const memoriaLibreMB: string = (memoriaLibreBytes / 1024 / 1024).toFixed(2);
    console.log(`Memoria Libre: ${memoriaLibreMB} MB`);
}

reporteSistema();

    6) Depuración de Código: El Bug de la Ruta Absoluta | Nivel: Medio

    6) Depuración de Código: El Bug de la Ruta Absoluta | Nivel: Medio

    Objetivo:

    Encuentra y corrige el bug relacionado con la disponibilidad de variables globales en el contexto de ES Modules (ESM) de TypeScript.

    Setup Inicial:

    El siguiente código está en un archivo llamado bug-path.ts y está configurado para ejecutarse como un módulo ES (ESM).

    // bug-path.ts
import path from 'path';

function obtenerRutaAbsoluta(nombreArchivo: string): string {
    // BUG: __dirname no existe en ES Modules
    const rutaAbsoluta = path.join(__dirname, 'data', nombreArchivo); 
    return rutaAbsoluta;
}

console.log(obtenerRutaAbsoluta('config.json'));
    Tarea a realizar:

    Al ejecutar npx ts-node bug-path.ts, el código falla con un ReferenceError: __dirname is not defined.

    1. Identifica por qué __dirname no está disponible en este contexto (ESM).
    2. Corrige el archivo bug-path.ts para que la función obtenerRutaAbsoluta funcione correctamente, utilizando las APIs de Node.js para recrear __dirname (vistas en el material didáctico).
    3. La solución debe seguir usando import (ESM) y no require (CommonJS).
    Pista:

    Necesitarás importar fileURLToPath del módulo url y dirname del módulo path. La variable import.meta.url te da la URL del archivo actual.

    Aplicación en el Mundo Real:

    Este es un error común al migrar proyectos de CommonJS a ES Modules. Saber cómo recrear las variables de ruta es esencial para el desarrollo moderno en Node.js.

    VER Solución. 
    // bug-path.ts (CORREGIDO)
import path, { dirname } from 'path';
import { fileURLToPath } from 'url';

// Recreamos __dirname para el contexto de ES Modules
const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

function obtenerRutaAbsoluta(nombreArchivo: string): string {
    // Ahora __dirname está definido y se usa path.join correctamente
    const rutaAbsoluta = path.join(__dirname, 'data', nombreArchivo); 
    return rutaAbsoluta;
}

console.log(obtenerRutaAbsoluta('config.json'));

    7) Control de Flujo: Validación de Argumentos | Nivel: Medio

    7) Control de Flujo: Validación de Argumentos | Nivel: Medio

    Objetivo:

    Implementar una lógica de control de errores que use process.exit() para terminar la ejecución del programa si no se cumplen los requisitos de entrada.

    Setup Inicial:

    Crea un archivo llamado validador-cli.ts.

    Tarea a realizar:

    La utilidad Nexus CLI Tools requiere que el usuario especifique un argumento de modo (--mode=dev o --mode=prod).

    1. Usa process.argv para buscar un argumento que comience con --mode=.
    2. Si el argumento no se encuentra, imprime un mensaje de error claro (console.error) y termina el programa con un código de error (process.exit(1)).
    3. Si el argumento se encuentra, extrae el valor del modo (ej: dev o prod) e imprímelo.
    4. Si el modo es prod, imprime un mensaje de advertencia (console.warn) sobre la sensibilidad de la operación.
    Pista:

    Recuerda que process.argv contiene el binario de node y el nombre del archivo en las primeras dos posiciones.

    Aplicación en el Mundo Real:

    Los códigos de salida (exit codes) son cruciales en scripts de automatización (como CI/CD) para indicar si una tarea se completó con éxito (0) o falló (cualquier otro número).

    VER Solución. 
    // validador-cli.ts
const args: string[] = process.argv;
const modoArg: string | undefined = args.find(arg => arg.startsWith('--mode='));

if (!modoArg) {
    console.error('❌ ERROR FATAL: Se requiere el argumento --mode=dev o --mode=prod.');
    console.error('Uso: npx ts-node validador-cli.ts --mode=prod');
    process.exit(1); // Termina con código de error
}

// Extraer el valor del modo
const modo: string = modoArg.split('=')[1];

console.log(`✅ Modo de operación detectado: ${modo}`);

if (modo === 'prod') {
    console.warn('⚠️ ADVERTENCIA: Ejecutando en modo PRODUCCIÓN. Las operaciones son sensibles.');
}

process.exit(0); // Termina con éxito

    8) Análisis de Archivos: path.parse | Nivel: Medio

    8) Análisis de Archivos: path.parse | Nivel: Medio

    Objetivo:

    Utilizar path.parse() para desglosar una ruta de archivo en sus componentes y aplicar lógica de negocio basada en la extensión.

    Setup Inicial:

    Crea un archivo llamado analizador-archivos.ts.

    Tarea a realizar:

    La utilidad necesita procesar archivos de configuración, pero solo acepta archivos con extensión .json o .yaml.

    1. Importa el módulo path.
    2. Define una ruta de ejemplo: const rutaConfig = '/etc/nexus/config.yaml';
    3. Usa path.parse() para obtener un objeto con los componentes de la ruta.
    4. Usa la propiedad ext del objeto resultante para verificar si la extensión es .json o .yaml.
    5. Imprime un mensaje indicando si el archivo es válido para la configuración.
    Pista:

    El resultado de path.parse() es un objeto con las propiedades root, dir, base, ext y name.

    Aplicación en el Mundo Real:

    Esta técnica se usa en servidores de subida de archivos para validar el tipo de archivo antes de procesarlo, evitando problemas de seguridad y compatibilidad.

    VER Solución. 
    // analizador-archivos.ts
import path from 'path';

const rutaConfig: string = '/etc/nexus/config.yaml';

const infoRuta = path.parse(rutaConfig);

console.log('--- Análisis de Ruta ---');
console.table(infoRuta);

const extensionValida: boolean = infoRuta.ext === '.json' || infoRuta.ext === '.yaml';

if (extensionValida) {
    console.log(`✅ Archivo de configuración válido: ${infoRuta.name}${infoRuta.ext}`);
    console.log(`Ubicación: ${infoRuta.dir}`);
} else {
    console.error(`❌ Extensión no soportada: ${infoRuta.ext}. Solo se aceptan .json o .yaml.`);
}

    9) Investigación: La Contaminación del Objeto Global | Nivel: Alto

    9) Investigación: La Contaminación del Objeto Global | Nivel: Alto

    Objetivo:

    Investigar las implicaciones de seguridad y rendimiento de "contaminar" el objeto global (global en Node.js) y proponer alternativas modernas.

    Setup Inicial:

    No se requiere código inicial.

    Tarea a realizar:

    Realiza una investigación sobre por qué la práctica de asignar variables directamente a global (ej: global.miVariable = 'valor') se considera una mala práctica en el desarrollo de Node.js/TypeScript.

    1. Investiga y documenta al menos dos problemas principales (uno de seguridad y uno de rendimiento/mantenimiento) que surgen de la contaminación del objeto global.
    2. Propón dos alternativas modernas y seguras para compartir datos de configuración o estado a través de múltiples módulos (ej: Patrón Singleton, Inyección de Dependencias, Módulos de Configuración).
    3. Peer Review: Incluye una sección de Peer Review donde se pida a un compañero que revise tu documento y evalúe si las alternativas propuestas son adecuadas para un entorno de microservicios.
    Aplicación en el Mundo Real:

    En entornos de producción, la contaminación global puede llevar a colisiones de nombres, fugas de memoria y vulnerabilidades de seguridad. Entender esto es fundamental para escribir código robusto y escalable.

    VER Solución.

    Problemas de la Contaminación del Objeto Global

    1. Problema de Seguridad (Colisión de Nombres): Si dos librerías diferentes o dos partes de tu código definen la misma variable en el objeto global, una sobrescribirá a la otra sin previo aviso. Esto puede llevar a un comportamiento impredecible y, en el peor de los casos, a que una librería maliciosa o un atacante sobrescriba una variable crítica (como una clave de seguridad o un manejador de errores).
    2. Problema de Rendimiento y Mantenimiento: Las variables globales dificultan el Tree Shaking (eliminación de código muerto) por parte de los empaquetadores, ya que no pueden determinar si una variable global está siendo utilizada. Además, hacen que el código sea más difícil de probar (Testing Unitario), ya que cada prueba debe limpiar el estado global para no afectar a la siguiente.

    Alternativas Modernas y Seguras

    1. Módulos de Configuración Inmutables: Crear un módulo dedicado (config.ts) que exporte un objeto de configuración. Este objeto se carga una sola vez al inicio de la aplicación (usando variables de entorno) y se exporta como const. Esto asegura que la configuración sea de solo lectura y que su ámbito esté limitado a los módulos que la importan.
    2. Inyección de Dependencias (DI): En lugar de que un módulo acceda a una variable global, se le "inyecta" la dependencia (la configuración, el logger, la conexión a la base de datos) a través de su constructor o de un framework de DI. Esto hace que las dependencias sean explícitas y facilita el reemplazo de componentes para pruebas.
    Peer Review (Instrucciones para el compañero):
    • Revisa: ¿El autor ha justificado claramente por qué la contaminación global es un riesgo en un entorno multi-hilo o de microservicios?
    • Evalúa: ¿Cuál de las dos alternativas propuestas (Módulos de Configuración o DI) sería más escalable si tuviéramos 50 microservicios diferentes? Justifica tu elección.

    10) Reto de Codificación: Utilidad de Monitoreo de Procesos | Nivel: Alto

    10) Reto de Codificación: Utilidad de Monitoreo de Procesos | Nivel: Alto

    Objetivo:

    Combinar los módulos os y process para crear una utilidad CLI que reporte el estado de salud del servidor y del proceso de Node.js.

    Setup Inicial:

    Crea un archivo llamado health-check.ts.

    Tarea a realizar:

    Implementa una utilidad de monitoreo que imprima un informe completo de salud del sistema.

    1. Usa os.totalmem() y os.freemem() para calcular el porcentaje de memoria RAM utilizada por el sistema.
    2. Usa process.memoryUsage() para obtener el uso de memoria solo del proceso de Node.js (propiedad rss o heapUsed).
    3. Usa os.cpus() para obtener el número de núcleos y os.loadavg() para obtener la carga promedio del sistema en el último minuto.
    4. Imprime todos los resultados de forma clara, utilizando console.log y console.table donde sea apropiado.

    // health-check.ts
import * as os from 'os';
import { memoryUsage } from 'process';

function healthCheck(): void {
    console.log('--- INFORME DE SALUD DEL SERVIDOR (Nexus CLI Tools) ---');

    // 1. Uso de Memoria del Sistema
    const totalMem = os.totalmem();
    const freeMem = os.freemem();
    const usedMem = totalMem - freeMem;
    const percentUsed = ((usedMem / totalMem) * 100).toFixed(2);

    console.log(`\n[RAM del Sistema]`);
    console.log(`Total: ${(totalMem / 1024 / 1024 / 1024).toFixed(2)} GB`);
    console.log(`Usada: ${(usedMem / 1024 / 1024 / 1024).toFixed(2)} GB (${percentUsed}%)`);

    // 2. Uso de Memoria del Proceso Node.js
    const nodeMem = memoryUsage();
    console.log(`\n[Memoria del Proceso Node.js]`);
    console.table({
        'RSS (Total Asignada)': `${(nodeMem.rss / 1024 / 1024).toFixed(2)} MB`,
        'Heap Usada (JS)': `${(nodeMem.heapUsed / 1024 / 1024).toFixed(2)} MB`,
        'Heap Total (JS)': `${(nodeMem.heapTotal / 1024 / 1024).toFixed(2)} MB`,
    });

    // 3. Carga de CPU
    const nucleos = os.cpus().length;
    const loadAvg = os.loadavg(); // Carga promedio en 1, 5 y 15 minutos

    console.log(`\n[CPU y Carga]`);
    console.log(`Núcleos de CPU: ${nucleos}`);
    console.log(`Carga Promedio (1m, 5m, 15m): ${loadAvg.map(l => l.toFixed(2)).join(', ')}`);

    // Interpretación de la carga:
    if (loadAvg[0] > nucleos) {
        console.warn(`⚠️ ALERTA: La carga (1m: ${loadAvg[0].toFixed(2)}) es mayor que los núcleos (${nucleos}). El sistema está sobrecargado.`);
    } else {
        console.log('✅ Carga de CPU normal.');
    }
}

healthCheck();
