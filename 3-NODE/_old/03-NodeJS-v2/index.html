    Node.js: El Motor del Backend con TypeScript

    Introducción Atractiva

    Imaginad por un momento que sois pilotos de carreras. Durante años, habéis conducido un Fórmula 1 increíblemente rápido (JavaScript), pero con una limitación estricta: solo podíais conducir dentro de un circuito cerrado llamado Navegador Web. Podíais hacer maniobras espectaculares, interactuar con el público (DOM) y correr a gran velocidad, pero no podíais salir de la pista para ir al taller, cambiar los neumáticos o conducir por la ciudad.

    Node.js es el momento en el que los ingenieros sacaron ese motor V8 del coche de carreras y lo montaron en un camión todoterreno.

    Ahora, con ese mismo motor, podéis salir del circuito. Podéis acceder al sistema de archivos, conectaros a bases de datos, levantar servidores y manipular el sistema operativo. Ya no estáis limitados a la "ventanilla" del navegador. Y para asegurarnos de que este camión todoterreno se maneja con la precisión de un cirujano y la seguridad de un tanque, usaremos TypeScript: nuestro copiloto experto que no nos dejará cometer errores tontos.

    En este tema, dejaremos de ser "maquetadores de scripts" para convertirnos en Arquitectos de Software Backend.

    Conceptos Fundamentales

    Antes de arrancar los motores, definamos las piezas clave de nuestro vehículo.

    Definición: Node.js

    No es un lenguaje de programación, ni un framework. Es un entorno de ejecución (runtime) para JavaScript construido sobre el motor V8 de Google Chrome. Permite ejecutar código JS fuera del navegador, directamente sobre el sistema operativo.

    Definición: Motor V8

    Es el corazón de Google Chrome y de Node.js. Escrito en C++, compila el código JavaScript/TypeScript a código máquina nativo en tiempo de ejecución (JIT), logrando un rendimiento excepcional.

    Definición: TypeScript en Node

    Node.js, por sí mismo, no entiende TypeScript. Solo "habla" JavaScript. TypeScript es nuestra herramienta de desarrollo que añade tipos estáticos y seguridad. Debemos transpilar (traducir) el código TS a JS antes de que Node pueda ejecutarlo.

    Node.js Environment

    Browser vs Nodejs

    Aunque el lenguaje base es el mismo (JavaScript), el ecosistema donde vive es radicalmente opuesto. Es como hablar inglés: te sirve tanto en Londres (Navegador) como en Nueva York (Servidor), pero las leyes, las señales de tráfico y lo que puedes hacer en cada ciudad son diferentes.

    En el Navegador, vives en una "burbuja" de seguridad (Sandbox). No puedes tocar los archivos del usuario por privacidad. En Node.js, tienes las llaves del castillo: puedes leer archivos, borrar discos duros y abrir puertos de red.

    Diferencias Clave y Limitaciones

    El cambio de mentalidad principal es la ausencia del DOM (Document Object Model) y la presencia del Sistema Operativo.

    Ejemplo 1: Intentando acceder al DOM en Node (Error Clásico) 

    /**
 * archivo: error-dom.ts
 * Descripción: Intento fallido de usar objetos del navegador en Node.js
 */

try {
  // ❌ ERROR: 'document' y 'window' no existen en Node.js
  const titulo = document.getElementById('app');
  window.alert('Hola Backend');
} catch (error: any) {
  console.error('⚠️ Error detectado:', error.message);
  // Output: ReferenceError: document is not defined
}

    Ejemplo 2: Acceso al Sistema Operativo (Potencia de Node) 

    /**
 * archivo: info-sistema.ts
 * Descripción: Uso de módulos nativos para leer info del hardware.
 */
import * as os from 'os';

// ✅ ÉXITO: Accedemos a la RAM y CPU del servidor
const memoriaLibreMB = os.freemem() / 1024 / 1024;
const plataforma = os.platform();

console.log(`💻 Sistema: ${plataforma}`);
console.log(`🧠 Memoria Libre: ${memoriaLibreMB.toFixed(2)} MB`);

    Tablas Comparativas

    Característica Navegador (Browser) Node.js (Servidor)
    Acceso al Sistema Restringido (Sandbox). No lee archivos locales. Total. Puede leer/escribir archivos y red.
    Objeto Global window / document global / process.
    Control de Versión Depende del usuario (Chrome, Firefox, Safari). Tú decides la versión exacta (ej: Node 20 LTS).
    APIs Disponibles Navegador Node.js
    DOM (HTML) ✅ Sí ❌ No
    File System (fs) ❌ No ✅ Sí
    Fetch API ✅ Sí ✅ Sí (desde Node 18+)

    Consejo Profesional

    Nunca asumas que una librería de NPM funcionará en ambos lados. Si usa window, fallará en Node. Si usa fs, fallará en el navegador (a menos que uses empaquetadores complejos).

    Preguntas Reflexivas

    2. Si Node.js corre en el servidor, ¿quién es el "cliente" que interactúa con él?
    3. Investiga: ¿Qué es Libuv y por qué es crucial para la asincronía en Node.js?


    El REPL de Node.js (terminal interactiva)

    El REPL (Read-Eval-Print-Loop) es vuestro patio de recreo. Es una terminal interactiva que lee código, lo evalúa, imprime el resultado y vuelve a esperar (bucle). Ideal para probar funciones rápidas sin crear archivos.

    Para acceder, abrid vuestra terminal y escribid simplemente node.

    Ejemplo 1: Matemáticas y variables en REPL 

    $ node
> const salario = 1500;
undefined
> const bono = 200;
undefined
> salario + bono
1700
> .exit

    Ejemplo 2: Definiendo funciones al vuelo 

    $ node
> function saludo(nombre) { return `Hola ${nombre}`; }
undefined
> saludo("DAW")
'Hola DAW'

    Ojo con TypeScript en REPL

    El comando node espera JavaScript. Si queréis probar código TypeScript directamente en la terminal (con tipos), debéis usar la herramienta ts-node (ejecutando npx ts-node).

    Tablas Comparativas

    Comando REPL Acción
    .help Muestra la lista de comandos disponibles.
    .editor Entra en modo editor para escribir funciones multilínea.
    .break Cancela la entrada actual.
    .exit Sale del REPL (también Ctrl+D).
    Característica Script (node file.js) REPL (node)
    Persistencia El código se guarda en disco. El código se pierde al cerrar.
    Uso principal Aplicaciones, Servicios. Pruebas rápidas, Depuración.
    Contexto Módulo (Scope local). Global (Scope interactivo).

    Preguntas Reflexivas

    1. ¿En qué situación laboral usarías el REPL en lugar de crear un archivo de prueba?
    2. ¿Cómo accederías al resultado de la última operación en el REPL sin haberlo guardado en una variable? (Pista: investiga la variable _).
    3. ¿Por qué el REPL devuelve undefined después de declarar una variable con const?


    Objectos Globales

    En el navegador, el rey es window. En Node.js, el rey es global. Sin embargo, hay una serie de "falsos globales" que parecen estar en todas partes pero son específicos de cada módulo.

    Verdaderos Globales: global, process, console, setTimeout. Pseudo-Globales (Solo en CommonJS): __dirname, __filename, module, require.

    Ejemplo 1: El objeto process (Global) 

    /**
 * archivo: global-process.ts
 * Descripción: Acceso a variables de entorno y argumentos.
 */

// process está disponible sin importar nada
console.log(`🆔 ID del Proceso (PID): ${process.pid}`);
console.log(`📁 Directorio de ejecución (CWD): ${process.cwd()}`);
console.log(`👤 Usuario del sistema: ${process.env.USER || process.env.USERNAME}`);

    Ejemplo 2: __dirname en CommonJS vs ESM 

    /**
 * archivo: paths.ts
 * Nota: En TypeScript moderno (ESM), __dirname NO existe.
 */

// Forma Legacy (CommonJS) - NO RECOMENDADA en proyectos nuevos
// console.log(__dirname); 

// Forma Moderna (ES Modules)
import { fileURLToPath } from 'url';
import { dirname } from 'path';

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

console.log(`Ruta absoluta: ${__dirname}`);

    Tablas Comparativas

    Objeto Descripción Disponibilidad
    global El objeto raíz del entorno Node. Global real.
    process Información del proceso actual (PID, Env). Global real.
    console Salida estándar y depuración. Global real.
    __dirname Ruta de la carpeta del archivo actual. Solo CommonJS.
    Concepto Navegador (window) Node.js (global)
    Variables con var Se pegan a window automáticamente. No se pegan a global (scope de módulo).
    Temporizadores window.setTimeout global.setTimeout (retorna un objeto Timeout).

    1. ¿Por qué es mala práctica llenar el objeto global con nuestras propias variables?
    2. ¿Qué diferencia hay entre process.env en Node.js y el localStorage del navegador?
    3. ¿Cómo solucionarías el error ReferenceError: __dirname is not defined en un proyecto TypeScript moderno?


    Primer programa con Node.js

    Vamos a crear un "Hola Mundo" profesional. Usaremos TypeScript, un archivo de configuración y ejecución tipada.

    Paso 1: Inicializar proyecto 

    npm init -y
npm install typescript ts-node @types/node -D
npx tsc --init

    Ejemplo 1: Código Fuente (index.ts) 

    /**
 * index.ts
 * Un saludo tipado y profesional.
 */

interface Desarrollador {
  nombre: string;
  lenguajes: string[];
  activo: boolean;
}

const yo: Desarrollador = {
  nombre: "Estudiante DAW",
  lenguajes: ["JS", "TS", "PHP"],
  activo: true
};

  console.log(`📚 Stack tecnológico: ${dev.lenguajes.join(' - ')}`);

iniciarSistema(yo);

    Ejemplo 2: Ejecución 

    # Desarrollo (compila en memoria y ejecuta)
$ npx ts-node index.ts

# Producción (transpila a JS y luego ejecuta con node)
$ npx tsc
$ node index.js

    Módulos en Node.js

    Crear un módulo

    En el desarrollo profesional, dividir es vencer. Un archivo de 2000 líneas es inmantentible. Los módulos nos permiten encapsular lógica en archivos pequeños y reutilizables. Piensa en ellos como piezas de Lego: cada archivo es una pieza con una función específica.

    Un módulo es simplemente un archivo. Lo que defines dentro es privado por defecto, a menos que decidas exportarlo.

    Ejemplo 1: Módulo de Utilidades (utils.ts) 

    // utils.ts
// Esta constante es privada, nadie fuera de este archivo la ve.
const SECRET_API_KEY = "12345";

// Esta función será pública
export function formatearFecha(fecha: Date): string {
    return fecha.toLocaleDateString('es-ES');
}

    Ejemplo 2: Módulo Principal (app.ts) 

    // app.ts
import { formatearFecha } from './utils'; // Importamos la pieza de Lego

console.log(formatearFecha(new Date()));
// console.log(SECRET_API_KEY); // Error: No existe aquí

    Tablas Comparativas

    Concepto Monolito (Un archivo) Modular (Varios archivos)
    Mantenibilidad Difícil. Scroll infinito. Fácil. Archivos pequeños.
    Colaboración Conflictos constantes en Git. Trabajo en paralelo sencillo.
    Reutilización Copy-paste de código. Importar módulo.
    Visibilidad Descripción
    Privada Variables/Funciones no exportadas. Solo visibles dentro del archivo.
    Pública Variables/Funciones exportadas (export). Visibles por otros.

    Preguntas Reflexivas

    1. Si tienes una función conectarBD() que se usa en 10 archivos, ¿por qué es mejor tenerla en un módulo?
    2. ¿Qué es el principio de "Encapsulamiento" y cómo ayudan los módulos a cumplirlo?
    3. ¿Puede un módulo importar a otro módulo?


    Exportar e importar (module.exports y require)

    Este es el sistema clásico de Node.js, conocido como CommonJS (CJS). Aunque hoy en día preferimos ES Modules (el estándar), encontraréis CJS en millones de proyectos antiguos y archivos de configuración.

    Importante: CommonJS

    CommonJS es síncrono. Cuando haces require(), el programa se detiene hasta que el archivo se carga y lee.

    Ejemplo 1: Exportar estilo CommonJS 

    // matematicas.ts (configurado como CommonJS)
function sumar(a: number, b: number) { return a + b; }
function restar(a: number, b: number) { return a - b; }

// Se asigna un objeto a module.exports
module.exports = {
    sumar,
    restar
};

    Ejemplo 2: Importar estilo CommonJS en TS 

    // app.ts
// TS tiene una sintaxis especial para importar CJS con tipos
import matematicas = require('./matematicas');

console.log(matematicas.sumar(5, 5)); // 10

    Tablas Comparativas

    Acción CommonJS (Legacy Node) ES Modules (Moderno/TS)
    Exportar module.exports = ... export const ...
    Importar const x = require('./x') import x from './x'
    Carga Síncrona (Bloqueante) Asíncrona
    Sintaxis Ejemplo
    Require Básico const fs = require('fs');
    Require TS import fs = require('fs');

    Diagrama de Carga de Módulos (CJS)

    graph LR
    A[Main.js] -- require('./utils') --> B(Busca archivo utils.js)
    B -- Lee y Ejecuta --> C{¿Está en caché?}
    C -- Sí --> D[Devuelve exports de caché]
    C -- No --> E[Ejecuta código]
    E --> F[Guarda en caché]
    F --> G[Devuelve module.exports]

    1. ¿Por qué el sistema require síncrono no funciona bien en los navegadores web?

    Configuración necesaria para habilitar ES Modules

    Para usar la sintaxis moderna import/export y que Node.js la entienda nativamente (sin que TypeScript la convierta a require), debemos modernizar nuestro entorno. ES Modules (ESM) es el estándar oficial de JavaScript.

    Pasos Críticos: 1. package.json: Añadir "type": "module". 2. tsconfig.json: Usar NodeNext.

    Ejemplo 1: Configuración package.json 

    {
  "name": "mi-app-moderna",
  "version": "1.0.0",
  "type": "module",  // <--- ¡ESTO ES CRÍTICO!
  "scripts": {
    "start": "node dist/index.js"
  }
}

    Ejemplo 2: Configuración tsconfig.json 

    {
  "compilerOptions": {
    "target": "ES2022",       // Versión moderna de JS
    "module": "NodeNext",     // Sistema de módulos nativo de Node
    "moduleResolution": "NodeNext",
    "outDir": "./dist",
    "rootDir": "./src"
  }
}

    Extensiones de Archivo

    Cuando usas "type": "module", Node te obliga a poner la extensión .js en tus imports, incluso en TypeScript. import { x } from './utils.js'; (Sí, pones .js aunque el archivo sea .ts, porque TS compilará a JS).

    Tablas Comparativas

    Configuración Resultado
    "type": "commonjs" (o omitido) Node trata .js como CommonJS (require).
    "type": "module" Node trata .js como ESM (import).
    Extensión Explícita Comportamiento Forzado
    .mjs Siempre ES Module (incluso sin package.json).
    .cjs Siempre CommonJS (incluso con package.json module).

    Preguntas Reflexivas

    1. ¿Por qué la industria se está moviendo de CommonJS a ES Modules?
    2. ¿Qué error te da Node si intentas usar import sin configurar "type": "module"?
    3. ¿Cómo afecta esto al uso de variables globales como __dirname?


    Exportar varios elementos

    En ESM tenemos dos formas de exportar: Nombrada (Named) y Por Defecto (Default). La recomendación profesional es usar Exportaciones Nombradas para mantener la consistencia y facilitar el refactoring.

    Ejemplo 1: Exportaciones Nombradas (Recomendado) 

    // math.ts
export const PI = 3.1416;

export function areaCirculo(radio: number): number {
    return PI * radio * radio;
}

export class Calculadora { /* ... */ }

    Ejemplo 2: Importar varios elementos 

    // app.ts
import { PI, areaCirculo } from './math.js'; 

console.log(`El área es: ${areaCirculo(10)}`);

    Export Default

    export default permite exportar una sola cosa por archivo. Contra: Quien importa puede ponerle el nombre que quiera (import CosaRara from './math'), dificultando buscar dónde se usa.

    Tablas Comparativas

    Tipo Export Definición Importación
    Named export const A = 1; import { A } from './file';
    Default export default A; import CualquierNombre from './file';
    Característica Named Exports Default Exports
    Autocompletado Excelente (IDE sabe el nombre). Regular.
    Flexibilidad Exportar N cosas. Exportar 1 cosa.

    Preguntas Reflexivas

    1. ¿Por qué Google Style Guide prefiere los Named Exports sobre los Default?
    2. ¿Cómo harías para importar PI pero cambiándole el nombre a NumeroPi en el archivo de destino? (as).
    3. ¿Puedes mezclar exportaciones nombradas y por defecto en el mismo archivo?


    Sintaxis de desestructuración y require

    La desestructuración (Destructuring) es una característica de ES6 que nos permite extraer propiedades de un objeto directamente a variables. Esto es súper útil al importar módulos nativos o CommonJS.

    Ejemplo 1: Sin desestructuración (Verbosidad) 

    // Forma antigua
const fs = require('fs');

const data = fs.readFileSync('archivo.txt');
fs.writeFileSync('copia.txt', data);

    Ejemplo 2: Con desestructuración (Limpieza) 

    // Forma limpia
const { readFileSync, writeFileSync } = require('fs');

const data = readFileSync('archivo.txt');
writeFileSync('copia.txt', data);

    En TypeScript/ESM, los "Named Imports" funcionan visualmente igual que la desestructuración:

    import { join, resolve } from 'path'; // Parece desestructuración

    Módulos principales de Node.js

    Node.js viene con "pilas incluidas". No necesitas instalar nada para tareas básicas. Estos son los Core Modules.

    El módulo console

    Más allá de console.log. Es una herramienta de depuración poderosa conectada a stdout (salida estándar) y stderr (salida de error).

    Ejemplo 1: Tablas y Tiempos 

    import { Console } from 'console'; // Opcional, es global

const usuarios = [
    { id: 1, nombre: "Ana", rol: "Admin" },
    { id: 2, nombre: "Luis", rol: "User" }
];

console.table(usuarios); // ¡Muestra una tabla ASCII preciosa!

console.time("Bucle");
for(let i=0; i<1000000; i++) {}
console.timeEnd("Bucle"); // Output: Bucle: 2.45ms

    Ejemplo 2: Niveles de Log 

    console.log("Info normal");         // stdout
console.error("Error crítico");     // stderr (útil para logs de errores)
console.warn("Advertencia");        // stderr
console.trace("¿Quién me llamó?");  // Imprime la pila de llamadas

    Tablas Comparativas

    Método Uso Principal Salida
    log Información general. stdout
    error Errores que deben alertar. stderr
    dir Inspeccionar objetos profundos. stdout
    Browser Console Node Console
    Objetos interactivos y desplegables. Texto plano formateado.
    Colores CSS. Colores ANSI (terminal).

    2. ¿Cómo guardarías la salida de console.log en un archivo en lugar de la pantalla? (Redirección de streams).
    3. ¿Para qué sirve console.assert()?


    El módulo process

    process es el puente entre tu código y el proceso del sistema operativo. Controla el ciclo de vida de tu aplicación.

    Ejemplo 1: Variables de Entorno y Argumentos 

    // Ejecutar con: PORT=3000 node app.js --modo=dev

// Leer configuración del entorno (Claves API, Puertos)
const puerto = process.env.PORT || 8080;

// Leer argumentos de línea de comandos
const args = process.argv.slice(2); // Eliminamos los 2 primeros (node y script)

console.log(`Servidor en puerto ${puerto}`);
console.log(`Argumentos recibidos: ${args}`);

    Ejemplo 2: Finalizar el programa 

    if (process.env.DB_PASSWORD === undefined) {
    console.error("❌ Fatal: No hay contraseña de base de datos.");
    process.exit(1); // 1 significa Error. 0 significa Éxito.
}

    Tablas Comparativas

    Propiedad/Método Descripción
    process.env Diccionario con variables de entorno (PATH, USER, etc).
    process.argv Array de strings con los argumentos de ejecución.
    process.cwd() Devuelve la carpeta donde se ejecutó el comando (Current Working Directory).
    Exit Code Significado
    0 Todo salió bien (OK).
    1 Hubo un error no controlado.

    El módulo os

    Proporciona información sobre el sistema operativo y el hardware. Útil para diagnósticos y balanceo de carga.

    Ejemplo 1: Información del Servidor 

    import * as os from 'os';

console.log("Arquitectura:", os.arch()); // x64, arm64
console.log("Plataforma:", os.platform()); // linux, win32, darwin
console.log("CPUs:", os.cpus().length); // Número de núcleos

    Ejemplo 2: Memoria 

    const totalMem = os.totalmem() / (1024 ** 3); // GB
const freeMem = os.freemem() / (1024 ** 3);   // GB

console.log(`Memoria: ${freeMem.toFixed(1)} GB libres de ${totalMem.toFixed(1)} GB`);

    Tablas Comparativas

    Método Retorno
    os.homedir() Ruta de la carpeta de usuario (/home/juan o C:\Users\Juan).
    os.tmpdir() Ruta de la carpeta de archivos temporales.
    os.uptime() Segundos que lleva encendido el sistema.
    Uso Ejemplo Práctico
    Cluster Usar os.cpus() para lanzar tantos procesos Node como núcleos tenga la CPU.
    Diagnóstico Alertar si os.freemem() es muy baja.

    El módulo path

    Las rutas de archivos son un dolor de cabeza: Windows usa \ (barra invertida) y Linux/Mac usan / (barra normal). Si escribes las rutas a mano (carpeta/archivo.txt), tu código se romperá en Windows. path resuelve esto normalizando las rutas.

    Ejemplo 1: Unir rutas de forma segura (Cross-Platform) 

    import path from 'path';

// MAL: Concatenar strings
// const rutaMala = 'uploads' + '/' + 'imagen.png'; 

// BIEN: Usar path.join
// En Windows generará: uploads\imagen.png
// En Linux generará: uploads/imagen.png
const rutaSegura = path.join('uploads', '2025', 'imagen.png');

console.log(rutaSegura);

    Ejemplo 2: Analizar una ruta 

    const ruta = '/home/usuario/reporte.pdf';

const info = path.parse(ruta);

console.log(info.name); // reporte
console.log(info.ext);  // .pdf
console.log(info.dir);  // /home/usuario

    Tablas Comparativas

    Método Descripción Ejemplo
    path.join() Une segmentos de ruta usando el separador del SO. a/b
    path.resolve() Resuelve una ruta absoluta desde el directorio actual. /User/proy/a/b
    path.basename() Obtiene el nombre del archivo. archivo.txt
    Sistema Separador (path.sep)
    Windows \ (Backslash)
    POSIX (Linux/Mac) / (Slash)

    2. ¿Por qué es peligroso usar concatenación de strings (+) para rutas en una aplicación que se despliega en Linux pero se desarrolla en Windows?

    🎓 Enriquecimiento Pedagógico (Estrategia FP)

    Chicos, pensad en los módulos Core (os, path, process) como el cinturón de herramientas de Batman. - Batman no tiene que ir a la tienda a comprar un bat-gancho cada vez que lo necesita; ya lo lleva puesto (Node.js lo trae instalado). - path es vuestro traductor universal: asegura que vuestro código hable el dialecto de archivos correcto, ya sea en el Windows de vuestra casa o en el Linux de Amazon AWS. - process es vuestro panel de control: os dice quién sois, dónde estáis y os da el botón de eyección (exit).
