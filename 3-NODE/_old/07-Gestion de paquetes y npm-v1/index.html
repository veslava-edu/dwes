    Gestión de paquetes y npm

    Introducción: El Supermercado del Desarrollador

    Imagina que quieres construir una casa (tu aplicación). Podrías fabricar tú mismo cada ladrillo, fundir el vidrio para las ventanas y forjar los clavos uno a uno. Sería heroico, pero tardarías décadas. En el mundo profesional, vas a la ferretería y compras los ladrillos, las ventanas y los clavos ya hechos por especialistas.

    En el desarrollo de software con Node.js y TypeScript, esa ferretería gigantesca es npm.

    Hasta ahora, hemos escrito nuestro propio código. Pero el verdadero poder del desarrollo moderno reside en no reinventar la rueda. ¿Necesitas calcular fechas complejas? ¿Conectar con una base de datos? ¿Crear un servidor web? Alguien ya ha escrito ese código, lo ha probado y lo ha empaquetado para ti.

    Hoy aprenderemos a gestionar estas herramientas externas, conocidas como paquetes o dependencias, para potenciar nuestros proyectos TypeScript.

    Conceptos Fundamentales

    Definición: Paquete (Package)

    Es un directorio que contiene uno o más archivos de código (módulos), junto con un archivo package.json que describe su contenido. Es la unidad fundamental de código reutilizable en el ecosistema Node.js.

    Definición: Dependencia

    Es un paquete que tu proyecto necesita para funcionar. Si tu aplicación usa la librería axios para hacer peticiones HTTP, entonces axios es una dependencia de tu proyecto.

    1. Introducción a npm

    npm significa Node Package Manager. Es el gestor de paquetes por defecto que se instala automáticamente cuando instalas Node.js. No es solo una herramienta, es un ecosistema compuesto por tres partes fundamentales:

    1. El sitio web (npmjs.com): Donde buscamos paquetes y leemos documentación.
    2. El registro (Registry): Una base de datos pública gigantesca con millones de paquetes.
    3. La línea de comandos (CLI): La herramienta que usamos en la terminal para instalar y gestionar esos paquetes.

    ¿Por qué es vital en TypeScript?

    TypeScript necesita herramientas para transpilación (tsc), linters (eslint), y definiciones de tipos (@types/...). Todo esto se gestiona a través de npm.

    Ejemplos Prácticos

    Ejemplo 1.1: Verificando la instalación Antes de nada, comprobamos que tenemos la herramienta lista.

    # En tu terminal favorita
npm --version
# Salida esperada (ejemplo): 10.2.4

    Ejemplo 1.2: Buscando paquetes desde la terminal Aunque solemos usar la web, puedes buscar desde la consola.

    # Buscamos paquetes relacionados con 'typescript'
npm search typescript

    Ejemplo 1.3: Actualizando npm npm se actualiza con más frecuencia que Node.js. Es buena práctica tener la última versión estable.

    # npm es un paquete que se gestiona a sí mismo
npm install -g npm@latest

    Tablas Comparativas

    npm vs Otros Gestores

    Característica npm Yarn pnpm
    Origen El original, viene con Node. Creado por Facebook para mejorar velocidad. Enfocado en eficiencia de espacio en disco.
    Instalación Automática con Node.js. Requiere instalación extra. Requiere instalación extra.
    Estructura node_modules plano (versiones modernas). node_modules plano. node_modules con enlaces simbólicos (ahorra espacio).
    Uso en FP Estándar educativo. Muy común en empresas React. Tendencia actual por rapidez.

    Componentes de npm

    Componente Función Principal Analogía
    CLI Ejecutar comandos (install, init). El carrito de la compra.
    Registry Almacenar el código de los paquetes. Las estanterías del almacén.
    Website Descubrir paquetes y leer manuales. El catálogo online.

    2. Si npm es gratuito, ¿quién paga los servidores donde se alojan los millones de paquetes? (Investiga sobre npm Inc. y GitHub).
    3. ¿Qué riesgo podría tener depender de paquetes creados por desconocidos?


    2. Crear paquete con npm

    Para empezar a gestionar dependencias, primero debemos convertir nuestra carpeta de proyecto en un paquete npm. Esto no significa necesariamente que vayamos a subirlo a internet, sino que vamos a inicializar el sistema de gestión dentro de nuestra carpeta.

    El comando mágico es npm init. Este comando es como una entrevista de trabajo para tu proyecto: te hará preguntas sobre el nombre, versión, descripción, etc.

    Ejemplos Prácticos

    Ejemplo 2.1: Inicialización interactiva Te preguntará paso a paso.

    mkdir mi-proyecto-ts
cd mi-proyecto-ts
npm init

# Te preguntará:
# package name: (mi-proyecto-ts)
# version: (1.0.0)
# description: Proyecto de aprendizaje DAW
# entry point: (index.js) -> Aquí solemos poner dist/index.js en TS
# ...

    Ejemplo 2.2: Inicialización rápida (Modo "Sí a todo") Ideal para prototipos rápidos. Rellena todo con valores por defecto.

    npm init -y
# O también: npm init --yes

    Ejemplo 2.3: Inicialización con Scope (Ámbito) Si planeas publicar tu paquete, a veces usas un "scope" (como tu nombre de usuario).

    npm init --scope=@miusuario
# Esto creará un paquete llamado @miusuario/mi-proyecto

    Tablas Comparativas

    npm init vs npm init -y

    Comando npm init npm init -y
    Interacción Pregunta campo por campo. No pregunta nada, asume defaults.
    Personalización Alta desde el principio. Baja (tienes que editar el fichero luego).
    Velocidad Lento (1-2 minutos). Instantáneo.
    Uso recomendado Proyectos serios / Producción. Pruebas / Demos / Ejercicios de clase.

    Campos clave al iniciar

    Campo Significado Recomendación TypeScript
    entry point El archivo principal de ejecución. Apuntar al JS compilado (ej: ./dist/index.js).
    test command Comando para pasar tests. Usar Jest o Vitest (jest).
    author Creador del paquete. Tu nombre + email.

    Diagrama de Flujo: Inicialización

    graph TD
    A[Inicio] --> B{¿Carpeta vacía?}
    B -- Sí --> C[Ejecutar npm init]
    B -- No --> D[Cuidado: No sobrescribir]
    C --> E{¿Usar flag -y?}
    E -- Sí --> F[Generar package.json con defaults]
    E -- No --> G[Cuestionario interactivo]
    G --> H[Confirmar datos]
    H --> F
    F --> I[Proyecto listo para instalar dependencias]

    🧠 Reflexiona

    1. ¿Qué sucede si ejecutas npm init en una carpeta que ya tiene un package.json?
    2. ¿Por qué el nombre del paquete no puede contener mayúsculas ni espacios?
    3. ¿Qué utilidad tiene el campo "license" y por qué deberías poner "MIT" o "ISC" en proyectos open source?


    3. Introducción al formato JSON

    El archivo que genera npm (package.json) está escrito en JSON (JavaScript Object Notation). Es el formato estándar de intercambio de datos en la web hoy en día.

    JSON es estricto

    A diferencia de los objetos literales de JavaScript/TypeScript, JSON no perdona. - Las claves siempre deben ir entre comillas dobles ("clave"). - No puede haber comas al final del último elemento (trailing commas). - No admite comentarios (// o /* */).

    Ejemplos Prácticos

    Ejemplo 3.1: Objeto JSON válido Observa las comillas en claves y valores de texto.

    {
  "nombre": "Proyecto DAW",
  "activo": true,
  "participantes": 25
}

    Ejemplo 3.2: Estructura anidada (Arrays y Objetos) JSON soporta estructuras complejas.

    {
  "curso": "Desarrollo Web",
  "tecnologias": ["Node.js", "TypeScript", "Docker"],
  "profesor": {
    "nombre": "IA Docente",
    "id": 101
  }
}

    Ejemplo 3.3: Error común (JSON Inválido) Este código fallaría si lo pones en un validador JSON.

    // ESTO NO ES JSON VÁLIDO
{
  nombre: 'Proyecto', // Error: Clave sin comillas, comillas simples
  version: 1, // Error: Coma final (trailing comma) si es el último, a veces da problemas en parsers viejos
  // Comentario: JSON no admite comentarios
}

    Tablas Comparativas

    JSON vs Objeto JavaScript/TypeScript

    Característica JSON Objeto JS/TS
    Comillas en claves Obligatorias ("key"). Opcionales (key o "key").
    Comillas en strings Solo dobles ("valor"). Dobles, simples o backticks (', ", `).
    Comentarios No permitidos. Permitidos (//, /**/).
    Tipos de datos Texto, número, booleano, null, array, objeto. Todo lo anterior + Funciones, Undefined, Dates, etc.

    Usos de JSON

    Uso Descripción Ejemplo
    Configuración Guardar preferencias de herramientas. package.json, tsconfig.json, .eslintrc.
    APIs Enviar y recibir datos servidor-cliente. Respuestas REST API.
    Almacenamiento Bases de datos NoSQL. MongoDB (usa BSON, binario de JSON).

    🧠 Reflexiona

    1. Si JSON no admite funciones, ¿cómo definimos los scripts en package.json? (Pista: son strings que la terminal interpreta).
    2. ¿Por qué crees que JSON ganó la batalla a XML como formato de intercambio de datos?
    3. Intenta crear un archivo .json en VS Code y escribe un comentario. ¿Qué ocurre?

    El package.json es el DNI, el currículum y el manual de instrucciones de tu proyecto, todo en uno. Define quién es el proyecto, qué necesita para funcionar y qué sabe hacer.

    Campos Clave

    1. scripts: Alias para comandos largos. En TypeScript es vital para compilar (tsc) y ejecutar.
    2. dependencies/devDependencies: Listas de paquetes instalados.

    Ejemplos Prácticos

    Ejemplo 4.1: Scripts típicos en TypeScript Automatizamos tareas repetitivas.

    "scripts": {
  "build": "tsc",                 // Compila de TS a JS
  "start": "node dist/index.js",  // Ejecuta el JS compilado
  "dev": "ts-node src/index.ts",  // Ejecuta TS directamente (desarrollo)
  "test": "jest"                  // Pasa los tests
}

    Ejemplo 4.2: Control de Versiones (SemVer) La versión 1.2.3 significa: Mayor.Menor.Parche.

    "dependencies": {
  "express": "^4.18.2", // ^: Permite actualizar versiones Menores y Parches (4.19.0, 4.18.5)
  "axios": "~1.6.0",    // ~: Permite solo actualizaciones de Parche (1.6.1, 1.6.9)
  "react": "18.2.0"     // Exacta: No permite cambios.
}

    Ejemplo 4.3: Configuración de tipo de módulo Importante en Node.js moderno.

    // Define si usas 'require' (commonjs) o 'import' (module) por defecto
"type": "module", 
"engines": {
  "node": ">=18.0.0" // Requisito de versión de Node
}

    Tablas Comparativas

    Símbolos de Versión (SemVer)

    Símbolo Significado Ejemplo con 1.2.3 Se actualizará a...
    ^ (Caret) Compatible con la versión Mayor. ^1.2.3 1.9.9 (No sube a 2.0.0).
    ~ (Tilde) Compatible con la versión Menor. ~1.2.3 1.2.9 (No sube a 1.3.0).
    Nada Versión exacta. 1.2.3 1.2.3 (Fijo).
    * Cualquier versión. * La última absoluta (Peligroso).

    Scripts vs Comandos Directos

    Acción Vía Script (npm run ...) Vía Directa Ventaja Script
    Compilar TS npm run build ./node_modules/.bin/tsc Más corto, no necesitas saber la ruta del binario.
    Iniciar npm start node dist/index.js Abstracción: si cambias la ruta del archivo, solo editas el package.json.

    5. package-lock.json

    Si package.json es la lista de la compra ("Quiero leche"), el package-lock.json es el ticket de compra detallado ("Compré Leche Pascual, Lote 456, Caducidad 2025, Precio 1.20€").

    El problema de "En mi máquina funciona"

    El package.json suele usar rangos (^4.18.2). Si yo instalo hoy y tú instalas mañana, podríamos bajar subversiones diferentes y que el proyecto se rompa.

    El package-lock.json congela el árbol de dependencias exacto que se instaló. Garantiza que todos los desarrolladores del equipo tengan byte a byte los mismos paquetes.

    Regla de Oro

    NUNCA edites el package-lock.json a mano. Se genera automáticamente. SIEMPRE debes subirlo al repositorio git.

    Ejemplos Prácticos

    Ejemplo 5.1: Diferencia visual - package.json: "express": "^4.18.2" - package-lock.json:

    "node_modules/express": {
  "version": "4.18.2",
  "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
  "integrity": "sha512-5/PsL6iWk...",
  "dependencies": {
    "accepts": "~1.3.8",
    "array-flatten": "1.1.1",
    ...
  }
}

    Ejemplo 5.2: Integridad El campo integrity es un hash (sha512). Si alguien hackeara el registro de npm y cambiara el código de la librería, tu instalación fallaría porque el hash no coincidiría. Es seguridad pura.

    Ejemplo 5.3: Reproducibilidad en CI/CD Cuando despliegas en un servidor, npm lee el lockfile para instalar exactamente lo que probaste en tu local.

    Tablas Comparativas

    package.json vs package-lock.json

    Característica package.json package-lock.json
    Generado por Usuario (npm init) o npm. Automáticamente por npm.
    Edición Manual (frecuente). Prohibida (manual).
    Versiones Rangos (^, ~). Exactas y URLs de descarga.
    Propósito Definir requisitos del proyecto. Garantizar consistencia e integridad.

    🧠 Reflexiona

    1. Si borras la carpeta node_modules y ejecutas npm install, ¿qué archivo usa npm para decidir qué instalar, el json o el lock?
    2. ¿Por qué el package-lock.json es mucho más largo (miles de líneas) que el package.json?
    3. ¿Qué pasaría si tu compañero sube cambios al package.json pero olvida subir el package-lock.json?


    6. Instalar y desinstalar paquetes con npm

    Aquí es donde llenamos nuestro almacén local (node_modules) con las herramientas que necesitamos.

    Comandos Básicos

    • Instalar: npm install <paquete> (o el alias npm i).
    • Desinstalar: npm uninstall <paquete> (o npm un).

    Instalación Local vs Global

    • Local: Se instala en la carpeta node_modules de tu proyecto. Solo accesible ahí. Es lo recomendado para el 99% de los casos.
    • Global: Se instala en el sistema operativo. Accesible desde cualquier terminal. Útil para herramientas de CLI (como typescript o nodemon antiguamente), aunque hoy se prefiere usar npx.

    Diagrama: Flujo de Instalación

    graph TD
    A[npm install react] --> B{¿Está en caché local?}
    B -- Sí --> C[Copiar desde caché]
    B -- No --> D[Descargar desde Registry npm]
    D --> E[Guardar en caché]
    E --> C
    C --> F[Descomprimir en node_modules]
    F --> G[Actualizar package.json]
    G --> H[Generar/Actualizar package-lock.json]

    Ejemplos Prácticos

    Ejemplo 6.1: Instalar dependencias normales Esto añade la librería a dependencies en package.json.

    npm install express mongoose
# Instala Express y Mongoose (para bases de datos)

    Ejemplo 6.2: Instalar una versión específica A veces la última versión rompe cosas. Instalamos una antigua a propósito.

    npm install uuid@8.3.2
# Instala exactamente la versión 8.3.2 de uuid

    Ejemplo 6.3: Desinstalar y limpiar Si probamos una librería y no nos gusta, hay que borrarla para no dejar basura.

    npm uninstall moment
# Borra la carpeta de node_modules y la línea del package.json

    Tablas Comparativas

    Instalación Local vs Global

    Tipo Comando Ubicación Uso
    Local npm i paquete ./node_modules Librerías que tu código importa (import x from 'x').
    Global npm i -g paquete /usr/local/lib o %AppData% Herramientas de sistema (ej: npm, vercel).

    Flags útiles de instalación

    Flag Alias Acción
    --save (Ya no es necesario) Antes de npm 5, era obligatorio para guardar en package.json. Ahora es default.
    --save-dev -D Guarda en devDependencies.
    --global -g Instala en el sistema, no en el proyecto.
    --force - Fuerza la instalación ignorando conflictos (Peligroso).

    🧠 Reflexiona

    1. ¿Dónde se guardan físicamente los paquetes globales en tu ordenador?
    2. ¿Por qué es mala práctica instalar librerías como express de forma global?
    3. ¿Qué contiene la carpeta .bin dentro de node_modules?


    7. Uso avanzado de npm

    npm no es solo instalar y borrar. Tiene herramientas de auditoría, ejecución y limpieza.

    npx: El ejecutor de paquetes

    npx viene con npm. Permite ejecutar binarios de paquetes sin tener que instalarlos globalmente. Es perfecto para herramientas de un solo uso (como create-react-app o inicializadores).

    Scripts personalizados

    Ya vimos scripts, pero en TypeScript podemos crear cadenas de comandos complejas.

    Ejemplos Prácticos

    Ejemplo 7.1: Uso de npx Queremos usar cowsay (una vaca que habla) solo una vez. No quiero ensuciar mi PC instalándolo.

    npx cowsay "Hola DAW"
# Descarga temporalmente cowsay, lo ejecuta y lo borra de la caché inmediata.

    Ejemplo 7.2: Scripts avanzados (Chaining) Limpiar la carpeta dist, compilar y luego ejecutar.

    "scripts": {
  "clean": "rimraf dist", // rimraf es un comando para borrar carpetas cross-platform
  "build": "npm run clean && tsc",
  "start:prod": "npm run build && node dist/index.js"
}

    Ejemplo 7.3: Auditoría de seguridad npm comprueba si tus dependencias tienen agujeros de seguridad conocidos.

    npm audit
# Te dirá: "Found 2 vulnerabilities (1 moderate, 1 high)"
# Para arreglarlo automáticamente:
npm audit fix

    Tablas Comparativas

    npm vs npx

    Herramienta npm npx
    Nombre Node Package Manager. Node Package Execute.
    Función Gestionar (instalar/borrar). Ejecutar.
    Caso de uso "Quiero tener esta librería". "Quiero usar esta herramienta ahora".
    Persistencia Guarda archivos en disco. Temporal (o usa los locales de node_modules).

    Comandos de Mantenimiento

    Comando Descripción ¿Cuándo usarlo?
    npm audit Busca vulnerabilidades. Regularmente o antes de desplegar.
    npm outdated Muestra paquetes con versiones nuevas. Cuando quieras actualizar dependencias.
    npm update Actualiza paquetes respetando SemVer (^). Para mantener el proyecto al día.
    npm ci Clean Install. En servidores de despliegue (borra node_modules e instala desde lockfile).

    🧠 Reflexiona

    1. ¿Por qué npx es más seguro que instalar paquetes globales?
    2. Si npm audit encuentra una vulnerabilidad en una sub-dependencia (una dependencia de tu dependencia), ¿cómo lo solucionas?
    3. ¿Qué diferencia hay entre && (ej: tsc && node index) y un solo & en los scripts?


    8. Dependencias de desarrollo VS dependencias de producción

    ¿Cuál es la diferencia real?

    • Dependencias de Producción (dependencies): Son el código que tu aplicación ejecuta mientras el usuario la usa. Sin ellas, la app falla. Ejemplos: Express, bases de datos, utilidades de lógica.
    • Dependencias de Desarrollo (devDependencies): Son herramientas que tú, como programador, usas para escribir, probar o compilar el código. No se necesitan para que la app funcione una vez terminada. Ejemplos: TypeScript, Jest, ESLint, Prettier.

    La regla del compilado

    TypeScript se compila a JavaScript. El servidor ejecuta JavaScript. Por tanto, el compilador typescript NO hace falta en el servidor de producción, solo en tu máquina para generar el JS. Por eso es una devDependency.

    Ejemplos Prácticos

    Ejemplo 8.1: Instalando dependencias de producción Librerías que se importan en el código fuente de la app.

    npm install express dotenv cors
# Se añaden a "dependencies"

    Ejemplo 8.2: Instalando dependencias de desarrollo Herramientas de construcción y tipos. En TypeScript, los tipos (@types/...) siempre son de desarrollo, porque los tipos desaparecen al compilar a JS.

    npm install -D typescript @types/express @types/node nodemon
# Se añaden a "devDependencies"
# Nota: -D es lo mismo que --save-dev

    Ejemplo 8.3: Instalación limpia en producción Cuando subes tu código a un servidor (AWS, Heroku), quieres instalar solo lo necesario para ahorrar espacio y seguridad.

    # En el servidor de producción:
npm ci --only=production
# Esto ignorará todas las devDependencies. Tu servidor será más ligero.

    Dev vs Prod

    Característica dependencies devDependencies
    Comando npm i paquete npm i -D paquete
    Uso Runtime (Ejecución). Buildtime / Coding (Desarrollo).
    ¿Necesario en Prod? SÍ. NO.
    Ejemplo TS axios, express. typescript, @types/react.

    Impacto de confundirlas

    Error Consecuencia
    Poner express en devDependencies La app fallará en producción ("Module not found") porque no se instalará.
    Poner eslint en dependencies La app funcionará, pero el despliegue será más lento y ocupará más espacio innecesariamente.
