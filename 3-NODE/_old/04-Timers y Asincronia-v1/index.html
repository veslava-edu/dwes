    Timers, Event Loop y Asincronía en Node.js

    Introducción: El Restaurante de un Solo Camarero

    Imagina un restaurante muy popular, el "Node Bistro". Este restaurante tiene una peculiaridad: solo tiene un camarero (el Main Thread).

    En un restaurante tradicional (como Apache o entornos multi-thread clásicos), si tienes 100 mesas, contratas a 100 camareros. Si una mesa pide un asado que tarda 4 horas, ese camarero se queda parado en la cocina esperando el asado. Ineficiente, ¿verdad?

    En el "Node Bistro", nuestro único camarero es un ninja. Toma la nota de la Mesa 1, pega el pedido en la cocina (el System/Kernel o Thread Pool), y sin esperar ni un milisegundo, va a la Mesa 2. Cuando la cocina grita "¡Asado listo!", el camarero, en cuanto tiene un hueco libre, recoge el plato y lo sirve.

    Este camarero nunca se bloquea. Siempre está moviéndose. Esto es Node.js: una arquitectura basada en eventos, no bloqueante y extremadamente eficiente para operaciones de entrada/salida (I/O). Hoy vamos a abrir las tripas de este camarero para ver cómo gestiona el tiempo y las tareas.

    1. Asincronía y modelo de ejecución en Node.js

    Para entender TypeScript en el backend, primero debemos entender dónde vive. Node.js no ejecuta código como lo harías en C++ o Java tradicionalmente.

    Definición: Programación Asíncrona

    Es un patrón de programación que permite que una unidad de trabajo se ejecute por separado del hilo de ejecución principal. Cuando el trabajo se completa, notifica al hilo principal (generalmente mediante un callback, promesa o evento) para procesar el resultado.

    Síncrono vs Asíncrono: El Bloqueo

    En el mundo síncrono, el código se ejecuta línea por línea. Si la línea 5 lee un archivo gigante, la línea 6 espera a que termine. En el mundo asíncrono, lanzamos la tarea y seguimos.

    Ejemplo 1: Lectura Síncrona (Blocking) Esto es peligroso en servidores web, porque "congela" a nuestro único camarero.

    import * as fs from 'fs';

try {
  console.log('1. Inicio del programa');
  // ⚠️ Esto BLOQUEA el Event Loop hasta que termina de leer
  const data: string = fs.readFileSync('./archivo-gigante.txt', 'utf-8');
  console.log(`2. Archivo leído: ${data.length} caracteres`);
  console.log('3. Fin del programa');
} catch (error) {
  console.error('Error leyendo fichero', error);
}

    Ejemplo 2: Lectura Asíncrona (Non-Blocking) La forma "Node.js" de hacer las cosas.

    import * as fs from 'fs';

console.log('1. Inicio del programa');

// 🚀 El camarero deja la nota en cocina y sigue trabajando
fs.readFile('./archivo-gigante.txt', 'utf-8', (err: NodeJS.ErrnoException | null, data: string) => {
  if (err) {
    console.error('Error:', err);
    return;
  }
  console.log(`2. (Callback) Archivo leído: ${data.length} caracteres`);
});

console.log('3. Fin del programa');
// Salida esperada: 1 -> 3 -> 2

    Arquitectura Single-Threaded y Event-Driven

    Node.js corre en un solo hilo principal (V8 Engine). Esto significa que no puedes hacer dos cosas a la vez en el código JavaScript. Sin embargo, Node.js delega las tareas pesadas (I/O, Red, Criptografía) al sistema operativo o a un pool de hilos internos (libuv), permitiendo el paralelismo real fuera de tu código JS.

    sequenceDiagram
    participant JS as Main Thread (V8)
    participant Libuv as Libuv / OS
    participant DB as Base de Datos

    JS->>Libuv: Petición a Base de Datos (Async)
    Note right of JS: JS sigue ejecutando<br/>otras líneas de código
    Libuv->>DB: Consulta SQL real
    DB-->>Libuv: Resultados
    Libuv-->>JS: Evento: "Datos Listos" (Callback)

    Tabla Comparativa: Modelos de Concurrencia

    Característica Multi-Thread (Java/PHP clásico) Event-Driven (Node.js)
    Hilos Uno por petición (pueden ser miles). Uno solo principal para todo.
    Uso de Memoria Alto (cada hilo consume RAM). Bajo (muy eficiente).
    Context Switching Costoso para la CPU. Casi inexistente.
    Ideal para Tareas intensivas de CPU. Tareas intensivas de I/O (Web, APIs).

    2. El módulo Timers en Node.js

    Los temporizadores (Timers) no son parte del lenguaje JavaScript (ECMAScript). Son una API que proporciona el entorno (el navegador o Node.js). Aunque la sintaxis es casi idéntica, internamente funcionan de forma distinta debido al Event Loop.

    API Global vs Módulo

    En TypeScript/Node, las funciones de temporización son globales, pero también existen dentro del módulo timers.

    Definición: Timers

    Funciones que programan la ejecución de código en un momento futuro. En Node.js, no garantizan el tiempo exacto, sino el tiempo mínimo que pasará antes de la ejecución.

    Ejemplo 1: Uso Global (Lo estándar) 

    console.log('Inicio');
// No hace falta importar nada
setTimeout(() => {
    console.log('Han pasado al menos 1000ms');
}, 1000);

    Ejemplo 2: Uso con node:timers (Más explícito) Útil si queremos usar la versión basada en Promesas (que veremos luego). 

    import { setTimeout } from 'node:timers/promises';

async function espera() {
    console.log('Esperando...');
    await setTimeout(2000); // ⏱️ Espera asíncrona real
    console.log('Listo!');
}
espera();

    Diferencias con el Navegador

    En el navegador, setTimeout devuelve un número (ID). En Node.js, devuelve un objeto complejo de tipo NodeJS.Timeout.

    // En Node.js (TypeScript)
const timer: NodeJS.Timeout = setTimeout(() => {}, 1000);

// El objeto timer tiene métodos para controlar el comportamiento del Event Loop
// timer.ref();
// timer.unref();

    Reflexiona

    1. ¿Por qué setTimeout en Node.js devuelve un objeto y no un número entero como en Chrome?
    2. Si importo timers desde node:timers, ¿estoy usando el mismo mecanismo que el global?
    3. ¿Garantiza setTimeout(fn, 1000) que se ejecutará exactamente en el milisegundo 1000?


    3. Timers fundamentales

    Vamos a ver las herramientas básicas del tiempo. Como desarrolladores DAW, usar esto correctamente es vital para no saturar el servidor.

    setTimeout() y clearTimeout()

    Ejecuta una función una vez, tras un retraso mínimo.

    Ejemplo 1: Cancelación de un timer 

    const bomba: NodeJS.Timeout = setTimeout(() => {
    console.log('💥 BOOM!');
}, 3000);

// Decidimos cortar el cable rojo a los 2 segundos
setTimeout(() => {
    clearTimeout(bomba);
    console.log('😅 Bomba desactivada');
}, 2000);

    setInterval() y clearInterval()

    Ejecuta una función repetidamente cada X milisegundos.

    Ejemplo 2: Polling simulado 

    let intentos: number = 0;

const intervalo: NodeJS.Timer = setInterval(() => {
    intentos++;
    console.log(`Verificando base de datos... Intento ${intentos}`);

    if (intentos === 5) {
        console.log('🛑 Parando verificación.');
        clearInterval(intervalo);
    }
}, 1000);

    setImmediate() vs clearImmediate()

    Este es exclusivo de Node.js (no estándar en navegadores). Se ejecuta después de la fase actual de I/O del Event Loop. A menudo se confunde con setTimeout(..., 0).

    Ejemplo 3: setImmediate 

    console.log('Inicio');

setImmediate(() => {
    console.log('Ejecutado en la fase "Check" del Event Loop');
});

console.log('Fin');
// Salida: Inicio -> Fin -> Ejecutado...

    Tabla Comparativa: Cuándo se ejecutan

    Timer Comportamiento Fase del Event Loop
    setTimeout(fn, delay) Se ejecuta tras pasar delay ms. Timers Phase.
    setInterval(fn, delay) Se repite cada delay ms. Timers Phase.
    setImmediate(fn) Se ejecuta tras el ciclo de I/O actual. Check Phase.
    process.nextTick(fn) No es un timer real. Se ejecuta YA. Inicio de cada fase.

    Cuidado con setInterval

    Si la función que ejecuta setInterval tarda más tiempo que el intervalo configurado, las ejecuciones se amontonarán y saturarán el servidor. Para tareas pesadas, es mejor usar setTimeout recursivo.

    2. ¿Por qué setInterval puede ser peligroso en un servidor con mucha carga?
    3. ¿Cómo harías para que una tarea se repita indefinidamente pero esperando a que la anterior termine?


    4. Timers avanzados y control del Event Loop

    Node.js permite un control fino sobre cómo los timers interactúan con el ciclo de vida del proceso.

    Objeto Timeout: ref() y unref()

    Por defecto, si tienes un timer activo, Node.js no cerrará el proceso. Se quedará esperando. unref() permite que el timer esté activo pero no mantenga vivo el Event Loop. Si es lo único que queda pendiente, Node.js se cerrará.

    Ejemplo 1: Timer "Fantasma" con unref() Este script termina inmediatamente, aunque el timer esté a 5 segundos. 

    const timer: NodeJS.Timeout = setTimeout(() => {
    console.log('Esto nunca se verá si no hay nada más manteniendo el proceso vivo');
}, 5000);

// 👻 Le decimos a Node: "No esperes por este timer para cerrar"
timer.unref();

console.log('El programa terminará ya.');

    Ejemplo 2: Revivir un timer con ref() Podemos volver a darle importancia. 

    const timer: NodeJS.Timeout = setTimeout(() => {
    console.log('Ahora sí me verás');
}, 2000);

timer.unref(); // Lo ignoramos
// ... lógica condicional ...
timer.ref();   // Nos arrepentimos, ahora sí importa

    Precisión y Rendimiento

    Node.js no es un sistema de tiempo real (RTOS). Si el Event Loop está bloqueado procesando JSON o imágenes, los timers se retrasarán.

    Ejemplo 3: Midiendo el retraso (Lag) 

    const inicio: number = Date.now();

setTimeout(() => {
    const lag: number = Date.now() - inicio - 1000;
    console.log(`El timer se programó para 1000ms.`);
    console.log(`Se ejecutó con un retraso adicional de: ${lag}ms`);
}, 1000);

// Bloqueamos el hilo artificialmente
const start = Date.now();
while(Date.now() - start < 2000) {} // Bloqueo de 2 segundos

    Consejo Profesional

    Usa unref() para tareas de limpieza en segundo plano o métricas que no deben impedir que el servidor se reinicie o apague suavemente.

    Reflexiona

    1. ¿Para qué sirve unref() en un sistema de sockets que envía un 'heartbeat' cada 10 minutos?
    2. ¿Qué pasa si hago un unref() y luego lanzo una petición HTTP? ¿Se ejecutará el timer?
    3. ¿Es fiable usar setTimeout para medir el tiempo exacto de una canción?


    5. Introducción al Event Loop

    El Event Loop (Bucle de Eventos) es el corazón de Node.js. Es un bucle infinito que permite a Node realizar operaciones de I/O no bloqueantes.

    La metáfora del Tiovivo (Carrusel)

    Imagina un tiovivo que gira. En cada vuelta, el operador (Node.js) revisa diferentes cestas (Fases). 1. Cesta de relojes (Timers). 2. Cesta de tareas de red/ficheros (Poll). 3. Cesta de comprobaciones inmediatas (Check). 4. Cesta de cierre (Close).

    Si hay gente (tareas) en una cesta, las atiende. Si no, sigue girando. Si el tiovivo está vacío y no hay nadie esperando entrar, se para (el programa termina).

    Mito del Single-Thread

    Se dice que Node es single-thread. * Verdad: Tu código JS corre en un hilo. * Verdad: El Event Loop corre en ese mismo hilo. * Matiz: Las operaciones pesadas (leer disco, desencriptar) ocurren en hilos C++ de fondo (libuv Worker Pool).

    graph TD
    A[Tu Código JS] -->|Llama API Asíncrona| B(Node.js Bindings)
    B -->|Delega| C{Libuv / Event Loop}
    C -->|Tareas Ligeras| D[OS Kernel - Net/IO]
    C -->|Tareas Pesadas| E[Thread Pool - FS/Crypto]
    D -->|Callback| F[Cola de Eventos]
    E -->|Callback| F
    F -->|Event Loop ejecuta| A

    Definición: Event Loop

    Es el mecanismo que orquesta la ejecución de código síncrono y asíncrono. Monitorea la pila de llamadas (Call Stack) y la cola de tareas (Callback Queue). Si la pila está vacía, mueve tareas de la cola a la pila.

    2. ¿Quién ejecuta realmente la lectura de un fichero en el disco duro?
    3. ¿Por qué decimos que Node.js es "driven by events"?


    6. Event Loop en detalle y libuv

    Profundicemos. libuv es la librería en C que implementa el Event Loop y maneja el Thread Pool. Es la "magia" bajo el capó.

    Fases del Event Loop

    Cuando Node.js arranca, inicializa el Event Loop y procesa el script de entrada. Luego entra en el bucle con estas fases:

    1. Timers: Ejecuta callbacks de setTimeout y setInterval vencidos.
    2. Pending Callbacks: Errores de TCP, etc.
    3. Idle, Prepare: Uso interno.
    4. Poll (Encuesta): La fase más importante. Recupera nuevos eventos de I/O (lectura ficheros, peticiones entrantes). Si no hay timers, Node puede "dormir" aquí esperando datos.
    5. Check: Ejecuta setImmediate.
    6. Close Callbacks: socket.on('close', ...).

    Comportamiento Indeterminado

    Fuera de un ciclo de I/O (en el script principal), el orden entre setTimeout(0) y setImmediate es no determinista (depende del rendimiento del PC). Dentro de un callback de I/O, setImmediate siempre se ejecuta antes.

    7. Microtasks y prioridad de ejecución

    Aquí es donde los desarrolladores Junior suelen fallar en las entrevistas. No todas las tareas asíncronas son iguales. Existen las Macrotasks (Timers, I/O) y las Microtasks (Promesas, nextTick).

    La Cola VIP: Microtask Queue

    El Event Loop tiene una regla de oro: "Antes de pasar a la siguiente fase (ej: de Timers a Poll), vacía COMPLETAMENTE la cola de Microtasks".

    1. process.nextTick(): Tiene la máxima prioridad absoluta. Corta la fila.
    2. Promises (reject/resolve): Tienen prioridad sobre los timers, pero menos que nextTick.

    Ejemplo 1: Carreras de Prioridad Adivina el orden: 

    console.log('1. Inicio');

setTimeout(() => console.log('5. Timeout'), 0);

setImmediate(() => console.log('6. Immediate'));

Promise.resolve().then(() => console.log('4. Promesa'));

process.nextTick(() => console.log('3. Next Tick'));

console.log('2. Fin');

// Orden Real:
// 1. Inicio
// 2. Fin
// 3. Next Tick (Prioridad VIP Máxima)
// 4. Promesa (Prioridad VIP)
// 5. Timeout (Empieza el Event Loop real)
// 6. Immediate

    Ejemplo 2: Bloqueo por Microtasks (Starvation) Si abusas de nextTick, el Event Loop nunca avanzará a la fase de I/O. 

    function bucleInfinitoNextTick() {
    process.nextTick(() => {
        console.log('Bloqueando...');
        bucleInfinitoNextTick(); // Recursividad en microtask
    });
}
// ⚠️ Esto impedirá que cualquier timer o petición I/O se procese.
// bucleInfinitoNextTick();

    Regla de Oro

    Usa process.nextTick solo si necesitas ejecutar algo antes de que el Event Loop continúe, por ejemplo, para emitir un evento antes de que el usuario tenga oportunidad de escuchar otros. Para todo lo demás, usa setImmediate o Promises.

    Reflexiona

    2. ¿Por qué las Promesas se ejecutan antes que un setTimeout(0)?
    3. ¿Qué es el "IO Starvation" causado por process.nextTick?


    8. Bloqueo del Event Loop y paralelismo

    Como solo tenemos un camarero, si le pides que resuelva una ecuación matemática compleja (CPU Bound), no podrá atender más mesas.

    Tareas I/O-bound vs CPU-bound

    • I/O Bound: Leer ficheros, consultas a BD, peticiones HTTP. (Node.js es REY aquí).
    • CPU Bound: Cifrado de vídeos, cálculos matemáticos masivos, compresión zip síncrona. (Node.js sufre aquí).

    Ejemplo 1: El Bloqueo (Mala práctica) 

    import express from 'express'; // Imagina un servidor Express

const app = express();

app.get('/bloqueo', (req, res) => {
    // 🛑 CÁLCULO PESADO EN EL MAIN THREAD
    let count = 0;
    for (let i = 0; i < 5000000000; i++) {
        count += i;
    }
    res.send(`Fin del cálculo: ${count}`);
    // Mientras esto corre, NADIE más puede entrar a la web.
});

    Worker Threads: La Solución

    Para tareas CPU-bound, Node.js introdujo worker_threads. Permite crear hilos reales que comparten memoria.

    Ejemplo 2: Worker Threads (TypeScript) 

    import { Worker, isMainThread, parentPort } from 'worker_threads';

if (isMainThread) {
    // 🧠 Hilo Principal
    const worker = new Worker(__filename);
    worker.on('message', (msg) => console.log('Recibido del worker:', msg));
    worker.postMessage('¡Trabaja!');
    console.log('El hilo principal sigue libre');
} else {
    // 💪 Hilo Trabajador (Worker)
    parentPort?.on('message', (msg) => {
        // Hacemos el trabajo pesado aquí
        let count = 0;
        for (let i = 0; i < 1e9; i++) count += i;
        parentPort?.postMessage(count);
    });
}

    Partitioning

    Otra estrategia para no bloquear es el "partitioning": dividir una tarea grande en trozos pequeños usando setImmediate, dejando respirar al Event Loop entre trozo y trozo.

    Reflexiona

    1. Si Node.js es monohilo, ¿por qué existen los worker_threads?
    2. ¿Qué pasa con los usuarios de tu web si calculas la sucesión de Fibonacci de 1000 en el hilo principal?
    3. ¿Cuándo elegirías usar un Worker Thread frente a un proceso hijo (child_process)?


    9. Manejo avanzado de asincronía

    La evolución de la asincronía en JS ha sido: Callbacks -> Promises -> Async/Await.

    El Infierno de los Callbacks

    Anidar funciones hace el código ilegible y difícil de manejar errores.

    Promises y Async/Await

    TypeScript brilla aquí permitiendo tipar los resultados de las promesas.

    Ejemplo 1: Promisify (Convertir Callback a Promesa) Node.js tiene una utilidad nativa para esto. 

    import * as fs from 'fs';
import { promisify } from 'util';

const readFileAsync = promisify(fs.readFile);

async function leerArchivo() {
    try {
        const data = await readFileAsync('./archivo.txt', 'utf-8');
        console.log(data);
    } catch (error) {
        console.error('Fallo la lectura');
    }
}

    Ejemplo 2: Control de Concurrencia (Promise.all) Ejecutar 3 tareas a la vez y esperar a que terminen todas (paralelismo lógico). 

    async function obtenerDatosDashboard() {
    console.time('Dashboard');

    // Lanzamos las 3 a la vez. No esperamos una por una.
    const [usuarios, productos, ventas] = await Promise.all([
        fetch('/api/usuarios'),   // Tarda 2s
        fetch('/api/productos'),  // Tarda 1s
        fetch('/api/ventas')      // Tarda 3s
    ]);

    // Tiempo total: 3s (el más lento), no 6s (la suma).
    console.timeEnd('Dashboard');
}

    Async Loops

    Cuidado con usar forEach con async/await. forEach no espera promesas. Usa un bucle for...of o Promise.all con map.

    Reflexiona

    3. Transforma mentalmente un async/await a su versión con .then().


    10. Flujos asíncronos reales y buenas prácticas

    En el mundo real (DAW), no solo leemos un archivo. Procesamos flujos de datos continuos.

    Streams y Backpressure

    Si lees un archivo de 10GB en memoria, tu servidor explota. Los Streams leen trozo a trozo (chunks). Backpressure es cuando el sistema avisa de que "va muy rápido" y hay que frenar la lectura.

    Ejemplo 1: Piping (Tuberías) La forma más eficiente de servir un archivo en una API. 

    import * as fs from 'fs';
import * as http from 'http';

const server = http.createServer((req, res) => {
    // ❌ MAL: fs.readFileSync (Carga todo en RAM)

    // ✅ BIEN: Stream (Tubería directa disco -> red)
    const stream = fs.createReadStream('./video-4k.mp4');
    stream.pipe(res);
});

    Event Emitters

    Node.js es "Event Driven". Puedes crear tus propios emisores de eventos.

    Ejemplo 2: Custom Emitter en TypeScript 

    import { EventEmitter } from 'events';

// Definimos los eventos
interface MisEventos {
    'login': (user: string) => void;
    'error': (msg: string) => void;
}

class AuthSystem extends EventEmitter {
    login(user: string) {
        if (!user) {
            this.emit('error', 'Usuario vacío');
            return;
        }
        console.log('Procesando...');
        this.emit('login', user);
    }
}

const auth = new AuthSystem();
auth.on('login', (u) => console.log(`Bienvenido ${u}`));
auth.on('error', (e) => console.error(`Fallo: ${e}`));

auth.login('AlumnoDAW');

    Reglas de Oro para Backend Escalable

    1. Nunca bloquees el Event Loop: Cuidado con JSON.parse de objetos gigantes o bucles sincrónicos largos.
    2. Gestiona siempre los errores: Una promesa rechazada no capturada puede tumbar el proceso Node.js.
    3. Usa Streams: Para todo lo que sea mover datos de un lado a otro.
